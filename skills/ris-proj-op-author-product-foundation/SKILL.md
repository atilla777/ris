# Author a project product foundation

Own the **separately accepted, saved and document-checked product foundation**
in one selected project's `sources.product`. Apply the portable subject method;
own project inputs, permission, acceptance and the combined save-result. The
portable proposal is useful independently; this wrapper adds real project
acceptance and persistence, not a duplicate method or an initialization flow.
Direct invocation works without an initialization caller or execution-role
binding. Preserve the project's actual task and publication process.

## Prepare project and scope

1. Establish the selected project/current working copy, create or explicitly
   bounded update, subject, available inputs, acceptance authority and permitted
   write scope. Distinguish author-and-save-after-acceptance from proposal-only.
   Update needs existing content and a clear boundary; missing input does not
   become create. No roadmap, tracker record, full design or chosen stack is
   mandatory for this result.
2. Load and apply installed `ris-proj-lib-common`, including its dialogue,
   artifacts and quality resources before their respective actions. Load and
   apply installed `ris-proj-op-resolve-context` and its owned configuration/path
   resources for `sources.product` and applicable project rules. Check status,
   full selected-config validity, setting provenance, diagnostics and actual
   paths: update uses existing inputs, create a prospective authorized output.
   Source paths refer to this **current working copy**, not the skill installation
   or primary copy. Do not require workspace/shared roots, roles or a task adapter
   when unused; a configured adapter is not a reason to invoke it.
3. Inspect the product root/index/version, relevant concepts, existing decisions,
   available project documents/instructions and relevant implementation evidence.
   Reuse sufficient material and confirmed answers before asking questions.
   Preserve usable structure, identities, extensions and unrelated content.
   Record baseline bytes or absence for every prospective write, including
   navigation, decision evidence and affected existing logs, plus relevant
   read-only dependencies. Inspect actual path targets/ancestors and symlinks
   within the authorized area, not just lexical nesting.
4. Load and apply installed `ris-proj-op-manage-okf-bundle` for the explicit
   selected product root and bounded read/check scope, passing project/config
   provenance, rules and permissions. It applies `ris-port-op-manage-okf-bundle`
   and its installed pinned format resource. Check their availability before
   promising format-dependent work; never reproduce the format method or snapshot.
   Ordinary Markdown, legacy/unknown or versionless content is not silently
   declared/converted to OKF 0.2. A required migration or storage-protocol change
   outside this boundary blocks save pending separate agreement; useful proposal
   work may continue. Do not rewrite the whole product bundle to fit RIS.

## Apply the content owner

Load and actually apply installed `ris-port-op-formulate-product-foundation`
through the host loader or actual installed location. Pass create/update,
product/boundary, sourced materials and versions, existing content/decisions,
constraints and already confirmed answers/statuses. It owns the substantive
method and conditionally applies `ris-port-op-interview` for interdependent gaps.
Keep any interview and acceptance in one leading dialogue, forwarding already
available answers instead of asking them again. Naming/loading the base is not
a proposal; inspect and combine its actual handoff.

Assess sufficiency against project evidence: purpose, users, tasks, main
capabilities, boundaries, material constraints and unknown/deferred impact must
be substantive, not empty headings. Check the scoped delta and adjacent
consistency, sources/statuses and unresolved conflicts. Do not choose roadmap,
feature requirements, stack or architecture to complete the document. Record
the specific operations limited by deferred choices; sufficient local knowledge
does not make those operations ready. Missing dependency or material decision
blocks its dependent result, with useful independent content retained.

## Present and obtain separate acceptance

Prepare a concrete candidate using the project OKF owner for format, without
writing product files before acceptance. Present its complete actual content or
an exact accessible candidate, distinguishable version, precise files/sections
and source provenance. For update show old → new content and rationale. Include
necessary navigation, decision-evidence placement, conflicts, deferred matters
and their impact in the proposed scope. For a new bundle, a root `index.md`
declaring `okf_version: "0.2"` plus one sufficient typed concept (for example
`foundation.md`) is enough; the example filename is not mandatory. Use nested
indexes only for actual knowledge directories under the applicable RIS profile.
Existing suitable layouts do not need a new foundation file or empty areas.

Obtain an attributable **separate acceptance of this content, version and scope**
from the authorized person/channel. Permission to write, interview answers,
general initialization approval, a portable proposal, file presence and format
validation are not this decision. Refusal, absent acceptance or proposal-only
means **zero product writes**: return the unsaved candidate and exact remainder.
Do not ask again for each file already included in the accepted write scope.
Material post-acceptance changes need renewed acceptance of the affected part.

Use the project's accessible version/decision convention. If none exists, agree
a compact decision/provenance section with the result, including placement in
the shown scope. Identify the exact accepted content version/sections, actual
decision, known actor/date/channel and used material locators/versions, including
the applicable base/package revision or digest when available; do not invent
provenance or acceptance. A digest, if needed for recovery, excludes its own
evidence section. Record unavailable provenance and its impact explicitly.
No new mandatory journal, manifest or tracker is introduced. A version label
alone must not conceal ambiguous content. Missing accessible acceptance evidence
prevents claiming the full saved result complete; OKF `verified` is no substitute.

## Save, read back and recover

1. Immediately before writing, re-resolve actual paths and reread baseline
   files/absence and material dependencies. Compare bytes, permission, accepted
   scope/version and current applicability. Unexpected foreign changes stop
   dependent writes for reconciliation; never overwrite or roll them back.
   Follow actual project write protections; comparison/read-back detects
   conflicts but is not atomic CAS or a filesystem transaction. An unavailable
   required guarantee blocks the write, not permission to bypass it.
2. Apply `ris-proj-op-manage-okf-bundle` with explicit project/config provenance,
   **bundle root, create/edit operation, exact concepts/indexes/affected existing
   logs, read/write scope, rules and permissions**. Save only accepted content,
   accessible decision/provenance and necessary navigation/log updates. Preserve
   unrelated bytes, identities, links and extension fields. Index edits are
   navigation, not copies of the foundation. Do not create an absent log or
   migrate ordinary Markdown merely for uniformity.
3. Reread actual files and compare substantive content, version and decision to
   the accepted candidate; check unaffected content against the baseline. Apply
   the project OKF owner's scoped checks and resolve changed links (leading `/`
   from this bundle root, relative links from their file, cross-bundle targets
   explicitly). Check the entire created minimal bundle for create; bounded
   update checks changed concepts/indexes and affected links, not every neighbor.
   Separate mandatory OKF violations, recommendations and stricter applicable RIS
   profile requirements. An unrelated fault does not authorize repair; a fault
   preventing correct scoped save blocks it. Format success proves neither
   acceptance nor subject sufficiency, which remain this author's checks.

On failed, partial or ambiguous writes, stop further writes and inspect actual
effects **before retry**. Identify saved/unsaved content, decision/navigation and
check gaps with exact paths/versions. On resume reread real files, sources and
available decisions, reconcile conflicts, and perform only missing actions.
Reuse unchanged applicable acceptance without renewed approval or duplicate
history; materially changed content needs its own decision. Do not replay a
confirmed save merely because read-back is pending. An unknown effect or partial
index is not a completed saved result; no mandatory recovery ledger is added.

## Return and stop

Report `ok|blocked|conflict|error`, project/current-copy and config provenance,
create/update scope, exact content/version and acceptance address, sources,
actual changes, content/format/link/read-back checks and their limits. Distinguish
proposed, accepted, saved, checked, local and unpublished; identify ready portions,
deferred decisions, limited operations, unsaved parts and exact remaining work.
Full-result `ok` requires acceptance, save and read-back; an expressly limited
proposal result must be labeled as such, not silently substituted for authoring.

Stop here. Do not name/select or launch a next skill, run initialization, create
roadmap/features/tasks, implement the product, select stack/architecture, set up
build/test/format/CI, change config/global settings, install tools, create remotes,
commit/push or close tracker work. Local document checks do not establish remote
publication, live agent behavior or complete project readiness.
