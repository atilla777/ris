# Feature prerequisites for the requested action

Owned by feature requirements: apply when a feature action or its dependent child
needs stage-specific prerequisite evidence. This is a substantive gate, not a
lifecycle dispatcher, ready registry, claim engine or adapter encoding method.
The invoking owner keeps its own input/acceptance/claim/copy/native refusal gates.
Ordinary standalone/document-only/native bug work retains its existing contracts;
do not manufacture a parent feature for it.

Through the selected adapter read the confirmed feature's readable content and
typed directed blockers. Requirements prerequisites are independent readable
exact-ID references naming a needed accepted decision/contract and scope, not
necessarily native edges. Inspect them even when native blocks is empty. Read
actual required content and attributable scope/version acceptance using common's
published-input sufficient-basis convention (direct/inherited/mixed); inherited
material uses original accepted sources and checked derivation, not a new approval.
A file, link, raw closed, no blockers or saved plan
is not acceptance. A requirements prerequisite waits for the specified accepted
contract, not completion of that entire feature.

For requirements/interview/specification or preparation admission, check decisions
genuinely needed before that dependent action. Implementation prerequisites do not
automatically prevent independent requirements work. An active native edge may be
treated as execution-only for preparation only with fresh explicit scope/reason
evidence matched to both endpoints and that action; unknown existing edge scope
is not such evidence. Actual/unknown requirements blockers stop only the dependent
action. Preserve edges and native refusal.

For design/decomposition verify required accepted contracts for that action too.
Common's valid saved prepare policy basis is permitted acceptance evidence too;
check its exact historical scope/config/default/overrides, never infer it merely
from today's config or demand fictional human approval. It does not satisfy an
unresolved substantive prerequisite or grant execution authority.
A sufficiently defined accepted future result may remain unfinished while
decomposition describes dependent tasks with necessary implementation blocks;
unknown/disputed necessary contracts block only the dependent portion. Do not
mark unfinished results delivered or weaken accepted-input gates.

For execution (including a child), check required actual integrated results,
required accepted decisions and all native active/unresolved blocker guards.
Read the child's actual parent; if verified as a feature by scope/content/sources
(not membership alone), inspect its readable prerequisites, typed blockers and
needed result evidence too. Absence of child edges cannot bypass parent-feature
restrictions. Do not copy all parent edges to children, infer kind from IDs,
remove blocks, claim readiness from task existence or treat unknown as satisfied.
Parent constraints stop only dependent action; native execution refusal remains
binding even if prose suggests a satisfied result.

Return exact prerequisite ID, needed decision/result, evidence and remaining gap.
Refresh material facts before dependent writes; drift needs re-evaluation, not a
stored ready flag. Registration alone requires no spec/design/AC and grants no
later readiness. Graph agreement supplies neither acceptance nor execution authority.
