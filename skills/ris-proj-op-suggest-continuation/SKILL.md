# Suggest a continuation for selected work

Own only the sufficiency of the recommendation. This project-only operation
depends on the selected RIS project, settings, tracker where relevant and
actually available owners; no portable pair is needed. The human, calling
scenario or external workflow decides and executes transitions. Do not execute
the recommended operation or launch agents, even if the surrounding request
permits writes. Make zero persistent project, tracker or Git changes: no saved
report, claim/heartbeat, acceptance, create, commit, push, closure or reopening.
No default execution role is required.
Use minimum sufficient facts for one next action, human decision or exact blocker.
Recommending an owner is not certifying its inputs or repeating its readiness
checks; unknown facts must not become assertions of acceptance or availability.

## Establish a bounded subject and read dependencies

Ensure installed `ris-proj-lib-common` is available and apply its baseline and
conditional resources: dialogue before questions/decisions, quality before
assessing recommendation evidence. A short recommendation is not an execution
handoff; artifacts applies only under common's actual artifact/transfer/partial-
effect triggers, not merely because this operation returns a response.
Apply installed `ris-proj-op-resolve-context` and its owned configuration resource
when preparing selected-project settings/paths or the tasks adapter. Inspect
status, provenance and diagnostics before using the result. Resolve resources
from their actual installed owner, not a presumed sibling or source checkout.
Unavailable dependencies block their dependent recommendation, not independent
source observations. This skill combines and checks their contributions.

Establish project/current copy, desired level of work, and exact task/container
ID or explicit no-ID source/scope locator. With neither, ask only which ID or
source/scope to inspect. Do not silently choose another ID, a child of the
selected container, the latest session or the whole backlog. Requests to execute,
choose a feature, plan, review or retrospect belong to their owners; navigation
must not perform that work.

For ID/tracker facts load the explicitly selected or context-selected installed
adapter and apply only its supported bounded read operations. Establish exact
identity/type/kind and own outcome/scope, then read criteria, linked sources and
known material blockers as needed to distinguish the next result. A selected ID
needs no global all-status dump unless an explicit absence, duplicate or cross-scope
question requires it. Use the adapter's native compact identity/content forms;
with Beads use exact `show <id> --brief-deps --json` when own content is needed.
Omitted brief fields are unknown, not empty. Inspect composition and typed directed
edges (including closed records) when they can change the recommendation;
membership is not a blocker. When the inference depends on accepted inputs,
read their content/decisions and compare applicability. Status, a file or
publication does not establish acceptance.
Preserve feature vs explicit ordinary standalone kind; unsupported/historical/
malformed input is a diagnostic, never an implicit migration or invented epic.

Before suggesting feature selection for an epic, inspect its existing related
features and material saved results: is a feature actually missing, or does the
needed result advance an already selected feature? A stale epic description cannot
override current children/refs. Apply common's conditional published-input reading
method when those links/decisions can change the answer; do not stop at a missing
file in the current checkout or require a prior-chat receipt. If the selected
subject is explicitly the epic, retain that scope, explain the existing child's
exact identity and needed result, and make any child locator explicit rather
than silently changing the selected subject. Foreign assignment/blockers or a
proven unfinished flow remain constraints, not reasons to invent a new feature.

For no-ID work inspect the supplied authorized source and selected scope directly;
require neither an artificial bead nor a product directory. Preserve the exact
document/candidate path and version, session ID/export or OKF root and operation
scope as applicable: task ID cannot replace those locators. Shared local evidence
uses context's checked primary selection/provenance and copy association; missing
or conflicting association blocks only that dependent read. Do not scan for
arbitrary receipts. Local notes do not become remote inputs.

Expand history, composition, acceptance decisions and publication/channel evidence
only for a named question that can change the recommendation: for example same-owner
recovery versus a new result, competing operation/flow ownership, container scope
or a known pending effect. Do not routinely reconstruct every stage/channel.
Reuse applicable evidence and mark unknown or uninvestigated facts unknown.
Neither a stale success marker nor closed status proves the whole result. A
missing, ambiguous, stale or inaccessible source blocks only the conclusion
that requires it; state the exact gap and retain an independently justified
recommendation instead of guessing readiness. If material ambiguity remains
unavoidable, ask one focused question or return that decision to the caller.

## Match the needed result to an actual contract

Use available installed names/descriptions to form a bounded shortlist for this
subject. Read only fitting owners' actual input, result, permission and stop
contracts and conditionally relevant resource portions. Read these as evidence
for a recommendation, **not instructions to execute that operation**. Do not load
all owner methods, flow recovery resources or the backlog on every call.
Lifecycle maps are orientation, never a second dispatch table or state registry;
the installed owner's current contract governs applicability.

Distinguish these outcomes from inspectable facts, not presumed stage order:

1. **Unfinished same operation:** recommend continuation/reconciliation to its
   actual owner with the same subject, result locators and preserved effects.
2. **Proven unfinished scenario:** invocation/result evidence must establish that
   scenario and its remainder. Recommend resuming that same flow; its owner
   reconciles effects and chooses the missing stage. Do not select an internal
   stage or copy recovery. A worktree/plan or assignee alone does not establish
   a running scenario or ownership.
3. **Next needed result:** match the evidenced remaining need to an owner. If the
   distinction from unfinished work depends on prior success, inspect that result
   and only the acceptance/channels material to the distinction; otherwise leave
   downstream readiness checks to its owner. Never assert unproven stage success.
   Published proposals are not accepted design or implementation permission;
   closed children are not container acceptance or authority to close it.
   For an early feature inspect explicit scope/identity, actual document sources
   and any supplied copy association, not raw status or JSON. Apply common's
   published-inputs convention/bounded legacy discovery. Name the first evidenced
   preparation gap: safe same-ID copy (purpose feature-preparation), conflicting
   document identity/destination, missing actual accepted requirements or design.
   Apply actual rights/foreign claim and action-specific blockers before suggesting
   an effect; execution-only prerequisites do not automatically ban requirements
   clarification. Unknown copy facts remain an exact evidence gap, not a claim
   that no copy exists. Read only the fitting preparation/spec/design owner's
   actual contract; recommend an explicitly limited result, not run-task readiness
   from ID existence. Missing actual design acceptance is a gap, not merely
   missing design.md; an accepted nonoverlapping inline section is valid.
   Missing/old/malformed JSON alone is no blocker; preserve old data without migration.
   For an existing feature distinguish, where material: accepted requirements
   with design missing/proposed; both separately accepted with work composition
   not yet determined; an already determined sufficient one-task or child-task
   composition; and a known unfinished operation/flow, conflict, blocker or foreign
   assignment. Inspect exact content and separate decisions before relying on
   acceptance. Both accepted inputs with undetermined composition support a
   decomposition-owner recommendation, **not** implementation readiness or an
   obligation to create children: that owner checks the one-task case and all
   decomposition gates. A defined accepted future prerequisite may permit
   decomposition with necessary directed blocks while dependent execution stays
   blocked; an unknown/disputed contract stops only the dependent portion, not
   independently sufficient preparation. Never recommend execution from task
   existence or planning permission. An empty child list alone does not show
   decomposition is missing; inspect any saved one-task/coverage result when known. Requirements
   without accepted design cannot be advertised as decomposition-ready. Unreadable
   actual documents/decisions leave an exact input gap, not inferred acceptance.
   These are examples of needed results to match against current owner contracts,
   not an exhaustive lifecycle stage table.
4. **Return to caller:** for nested/component invocations return the bounded
   recommendation and evidence to the caller; do not take over its dialogue,
   transitions or combined result or silently change full/limited mode.
5. **Human decision:** state the one necessary unresolved goal, scope, acceptance
   or rights decision and meaningful alternatives with consequences. Recommend
   one only when supported; do not decide or accept unseen content for the human.
6. **Missing/incompatible owner:** return the exact contract, command, input or
   capability gap and responsible decision needed. Do not invent a skill, alias,
   ref or long workaround performing the missing responsibility.

Partial publication and interrupted/unknown effects are not new work. Recommend
the corresponding owner reconcile its actual channel before retry; never blind
create/push from an old flag. Known IDs/publications and unchanged decisions
remain inputs; changed material inputs need their owner's focused reconciliation.
For bug work distinguish the requested result from actual evidence: an unregistered
message needs registration; an exact registered native bug without sufficient
current report/criteria needs investigation or a precise evidence/authority gap;
a sufficient authorized basis can support a fix-flow recommendation. Read relevant
installed register/investigate/fix contracts as evidence, never execute them.
Research readiness alone does not accept behavior or grant fix authority. Retrieve
full report text from description or exact published file and inspect any snapshot/
decisions relevant to the recommendation. Proven ongoing fix/execution follows its
same scenario owner (execute-task owns post-transfer recovery), not a newly selected
internal stage. Insufficient evidence is not closure; disposition differs from
fix-completion. Preserve exact ID/type, use ordinary bug reads, never convert it or
invent feature payloads. These are facts to match to contracts, not a dispatch table.
Closed pending-publication work stays closed, without reclose. Retain an explicitly
selected container's scope. When its complete nonempty direct-child set is all
closed and no active parent blockers remain, recommend ordinary container close,
not a new acceptance/Git/review audit. This is a recommendation, not close authority
or fresh whole-result acceptance. Zero-child features keep own-result gates;
explicit substantive verification stays distinct. Report actual missing work or
blockers; never switch to executing a child or automatically close its parent.

## Verify the recommendation, report and stop

First check **necessity**, separately from command compatibility: name the missing
result, the material current facts/decisions inspected, and why an existing saved
result does not already satisfy it. If a linked source could change this choice,
read it or return that precise evidence gap before recommending the operation.
Finding a compatible installed command cannot prove its result is needed. Do not
audit unrelated history or repeat the executing owner's entire readiness check.

Before a slash prompt inspect the **actual installed command's explicit target** and
confirm it targets that owner, exists in this client and accepts the proposed
ID/locator and scope. Command and skill names need not match; never construct a
slash name from a skill name. Source-only/future names are not installed commands. Use a
short natural-language instruction with exact locator when slash syntax is
inapplicable to an available compatible owner, not to bypass an absent owner.
Missing command blocks the slash form; report that gap explicitly. Compare prompt
and evidence to required owner inputs: subject/kind, versions/decisions, actual
snapshot or history/root locator where required, mode, scope and authority.
Add project/config/primary/permissions only when needed to avoid ambiguity;
never manufacture authority. Supply known required locators and disclose missing
inputs; recommending that the owner validate/reconcile them does not certify them.
The executing owner still checks current readiness, acceptance, rights, ownership,
blockers and write guarantees.

Return compactly in the person's language:

- One usable prompt plus a short evidence-based reason; or the necessary human
  decision with material alternatives; or an exact blocker (`blocked`, `conflict`
  for contradictory facts, `error` for failed reads). `ok` covers recommendation
  sufficiency only, never downstream completion or execution readiness.
- Exact subject/scope, a usable locator and the facts supporting this recommendation;
  include versions/decision/channel evidence and checked owner/command locations
  only where the conclusion or proposed prompt depends on them. Add project/config/
  current-copy and primary provenance when used or needed to disambiguate.
  Preserve real partial effects and their exact recovery remainder.
  Mark unknown/uninvestigated applicable channel facts explicitly. Apply common's
  recoverable-result rules under their actual triggers; this is no exemption from
  them and no reason to reconstruct unrelated history or repeat another owner's
  acceptance checks.
- Limits, unknown/unperformed checks, missing inputs and exact remaining result.
  A short natural answer needs no formal block. Make clear that no work was
  executed (`changes: []` if structured); this response is not saved or automatically
  discoverable in another session. A nested result goes to its caller.

A recommendation is neither permission nor proof of readiness. Stop after the
response; do not claim work, save it, launch the prompt or start another stage.
