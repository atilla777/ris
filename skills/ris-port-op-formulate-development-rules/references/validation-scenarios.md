# Author validation scenarios

Read only when validating this skill's source/behavior, not on ordinary rule
authoring. Use installed resources outside the RIS source tree; record package
digests, environment/model, inputs/answers, actual output and before/after files.
Structure checks do not replace agent execution. Tool recommendations need
documentary evidence; these scenarios do not run or certify project toolchains.

1. New Rails web app, sufficient decisions: propose a small supported minimum,
   test/system distinction, version/lock/build inputs and security limitations;
   no project files, RIS config, tracker or mandatory interview.
2. Existing DragonRuby game, bounded testing amendment: retain confirmed style,
   SDK/runtime and task/publication policy; use runtime tests with compatibility
   limits, not MRI/RSpec/Bundler/headless promises. Show old → new norm only.
3. New Odin game: native check/test/build and package coverage, memory-report
   policy, no invented fmt/package manager; no ECS/renderer selection.
4. Unknown target/runtime/CI dependencies: actually apply conditional interview,
   reuse sourced answers and ask prerequisite decisions before runner choices;
   preserve explicitly deferred gaps rather than select tools without evidence.
5. Unsupported/version-sensitive formatter: research or visibly defer binding
   selection; a host parser result never certifies shipped-runtime compatibility.
6. Update without old norms/boundary: block dependent result, no silent create.
7. Related architecture conflict or old code: scope transition/neighbor decision,
   no architectural rewrite, compliance audit or migration backlog.
8. Natural positive requests in English/Russian; adjacent CI installation, code
   audit, library extraction, feature design and impact requests plus irrelevant
   requests: correct selection, no operation takeover.

Inspect that the ordinary case loads foundation + one applicable profile, not
all profiles/another author's instructions; confirm zero file/record changes.
