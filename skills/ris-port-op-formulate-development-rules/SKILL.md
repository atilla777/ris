# Formulate engineering rules

Own the **checked read-only content proposal**. Work under the actual project's
instructions, including outside RIS: no configuration, document layout, tracker,
`ris-proj-lib-common` or `ris-proj-op-resolve-context` dependency. A project caller owns acceptance,
format, storage and the combined result. Do not write files/records, install or
configure tools, execute project checks to certify compliance, change code/CI,
accept norms for the person or start another lifecycle operation. Read code and
configuration only to establish relevant facts. A proposed command is not an
installed tool or a successful check.

## Establish inputs and scope

Establish create/update, the engineering subject and explicit change boundary,
purpose/nearest goal, constraints, actual or discussed stack, supplied/accessibly
inspected sources with currency/status, existing rules/tool settings, related
architecture/process obligations and confirmed answers. No fixed input schema
or filenames are required. Create needs only purpose, goal, constraints and
known/discussed stack; no full product, roadmap or future design. Distinguish no
code yet from inaccessible existing code. Update requires existing norms and
an explicit boundary; missing input blocks update, never becomes create.

Preserve unaffected norms, identities, exceptions, tools and the existing task,
permission and publication process. Separate observed settings from accepted
policy: a config file does not authorize changing the rules. Keep confirmed
decisions, facts, assumptions, proposals, examples and unknown/disputed/deferred
questions distinct. Conflicting/stale evidence limits dependent norms only.

## Resources and unresolved decisions

Read [the engineering foundation](references/foundation.md), applying only the
selected scope in update. Read **only applicable** profiles:
[Rails web](references/rails.md), [DragonRuby games](references/dragonruby.md),
[Odin games](references/odin.md). Resolve resources from this installed folder,
not the source repository. Mixed projects load only affected profiles; other
stacks use the common method plus researched facts, not an invented profile.

If material choices remain, read [the decision map](references/interview-tree.md).
For interdependent unknown decisions, load and actually apply installed
`ris-port-op-interview` with bounded topic, branches/prerequisites, sourced known
answers/status and intended rules result. Integrate its handoff into one
dialogue. Do not repeat confirmed answers or reproduce its interview method.
Ask a single clarification directly; no mandatory interview when inputs suffice.
Missing interview/resource availability blocks dependent decisions, not all
independent content. Deferral retains an open question and known return trigger.
This base owns subject sufficiency after the handoff.

## Formulate, customize and check

1. Inspect relevant evidence: runtime/compiler/framework versions, dependency
   records, build targets, existing lint/format/test commands and CI environment.
   Research material uncertainty against technical documentation for the actual
   version/platform. Record source, observation date/version, rationale and
   limitations. If compatibility cannot be confirmed, state it before proposing
   a binding choice; do not invent flags, version support or headless runners.
2. Choose a justified **minimum** for the nearest work and conditional additions
   only when their trigger exists. For each candidate tool/practice record:
   purpose/risk, existing equivalent, applicable version/runtime/platform,
   evidence, proposed usage/check result, cost and limitations. A working
   equivalent takes precedence over profile defaults; replacement needs a
   concrete deficiency, tradeoff and explicit decision. Latest-version upgrades,
   duplicate formatters and universal coverage percentages are not defaults.
3. Customize versions/targets, command scope, diagnostic policy, style exclusions,
   test layers/data/seeds, local versus CI checks, security/dependency checks,
   documentation/review evidence and readiness expectations to project facts.
   Make significant norms actionable: requirement, applicability, rationale,
   observable verification and exception/change authority. Unknown material
   choices stay open, not placeholders in normative text. Proposed selections
   remain candidates until accepted by the caller's authority.
4. Cover supported versions and reproducible dependency/build inputs; consistent
   style/format/static checks; behavior/regression/integration tests; relevant
   security and dependency risks; documentation, review, CI and change DoD.
   Scale verification to risk, not a catalogue of tools. Preserve task/permission/
   publication rules verbatim in meaning; a quality gate does not grant merge,
   release, tracker or deployment authority. See the foundation for subject
   sufficiency and failure signals.
5. Reference related architecture obligations as their single source of truth;
   propose how tests, diagnostics or review support them, without copying or
   changing their independently owned norms. Flag any version/tool decision
   affecting architectural properties and the needed adjacent agreement. An
   accepted limited scope may retain a visible dependency; do not claim overall
   consistency with an unresolved conflict. No automatic second subject skill.
6. For update return the exact old → proposed norm delta and rationale. For old
   code propose a scoped transition policy and explicit temporary exceptions
   where needed; do not promise an audit, full compliance or migration backlog.
   Check sufficient coverage in scope, reproducibility, real tool applicability,
   noncontradictory gates/commands and preserved neighboring/process rules.

## Return and stop

Return operation/scope, evidence with version/currency/status, substantive
normative proposal or bounded amendment, justified selected minimum and
triggered additions, customization decisions, reused confirmed answers,
candidate versus conditional choices, verification/exception expectations,
unknowns/deferred triggers, adjacent conflicts and independently usable parts.
Include document-sufficiency checks and their limits, unavailable sources and
unconfirmed tool compatibility. A partial result names the exact missing
input/decision rather than looking like a complete generic template.

State that the proposal was **neither accepted nor saved**, tools were not
configured and implementation compliance was not checked. Stop at this result;
do not request final acceptance or persist even if the person agrees. Those
actions belong to the project author/caller.
