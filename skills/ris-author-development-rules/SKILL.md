# Author project engineering rules

Own the **accepted, saved and document-checked engineering scope** in one
selected project's rules bundle. Apply the portable method for content; own
project inputs, acceptance, persistence and combined verification. This is a
project wrapper, not a two-author scenario. Do not call the architecture author,
choose a next skill, audit compliance, enumerate delivery impact, extract a
library or change product, code, tooling, CI, configuration or tracker. Preserve
the project's task, permission and publication process. Saving does not publish
Git or tracker history, install a recommended tool or prove its checks passed.

## Prepare the selected scope

1. Establish the target project/current working-copy root, create/update,
   engineering subject/boundary, writer/acceptance authority and whether saving
   after acceptance is permitted or only a proposal is requested. A request to
   author rules permits preparing them, not accepting them for the person.
   Create needs purpose, nearest goal, constraints and known/discussed stack;
   no product, roadmap, tracker or full future design is mandatory. Update also
   needs existing rules and an explicit boundary; missing input blocks update,
   never silently becomes create.
2. Load and apply installed `ris-common`, including dialogue, artifacts and
   quality resources before their respective actions. Load and actually apply
   `ris-context` and its configuration resource: require `sources.rules` as
   update input/create prospective output. Check status, provenance, paths,
   diagnostics and permissions. Sources belong to the **current worktree**, not
   installation/primary-copy root. No workspace paths or execution roles are
   required for this operation. Do not load a task adapter merely because it
   is configured.
3. Inspect the rules root/index/version, selected engineering/process documents,
   relevant architecture obligations and actual versions/tool settings. Preserve
   usable layout, identities, unknown extension fields and existing delivery
   norms. Record baseline bytes/absence for prospective writes, including indexes,
   affected existing logs and decision evidence; identify read-only dependencies
   to recheck. Ordinary Markdown, 0.1, future/versionless formats and a 0.2 root
   with unconverted target concepts are not silently valid 0.2 inputs. A required
   conversion beyond this scope or change of storage protocol blocks the save
   until separately authorized; return a proposal and preserve existing material.
4. Load and actually apply installed project `ris-okf`, passing the established
   project/config provenance, explicit rules root, operation, bounded concepts/
   indexes, applicable rules and permissions. It applies `ris-okf-base` and its
   base-owned pinned specification; content/acceptance stay here. Unavailable
   dependencies/resources block their dependent action, not permission to
   imitate the method or claim format conformance.

## Apply the engineering method

Load and actually apply installed `ris-formulate-development-rules-base` with
create/update and boundary, purpose/nearest goal, constraints, actual/proposed
stack, sourced existing rules/config/tool evidence, related architecture and
process obligations, exceptions and confirmed answers. Its resources resolve
from its own installed folder. It selects only applicable profiles and
conditionally applies `ris-interview-base` to interdependent unknown decisions;
keep one dialogue and reuse answers. Do not copy its methodology or treat the
name/load as the substantive content result.

Inspect the proposal's actionable norms, justified minimum/triggered additions,
project customizations, sources/compatibility limits, statuses, exact update
delta, exception/transition policy and documentary checks. Retain existing
working tools unless a concrete deficiency and replacement decision justify
change. Version-sensitive flags, host formatter compatibility, headless runners
and CI availability require actual evidence or visible deferral. Do not publish
all profile alternatives or unfilled placeholders as rules.

Check sufficient engineering coverage **within scope**, against project facts
and related norms. Architecture owns what must hold; engineering owns how
versions/practices/tools support it. Reference rather than independently copy
architecture obligations. Show any necessary neighboring amendment or agreement,
without changing that area. A limited result may be explicitly accepted with a
visible dependency; do not claim overall consistency while a conflict remains.
Rules can govern new/touched legacy work without claiming existing code complies
or producing a migration backlog. Recommendations are not configured gates.

## Present, accept, save and check

For a first bundle, **only if a layout illustration is useful**, read
`assets/rules-example/index.md` and `assets/rules-example/development.md` from
installed `ris-common`. This non-binding example does not replace the base/profile
or require reading the architecture example/author. Do not copy its whole
bundle or example status into project rules. Existing bounded updates need no
example.

1. Assemble the concrete candidate in the project's language using `ris-okf`.
   Show normative content (update: old → new norms), exact files/sections,
   necessary navigation changes, candidate version and source-material identity.
   Explain exceptions, deferred decisions, compatibility gaps and conflicts
   **before acceptance**. Do not write drafts to normative paths.
2. Obtain explicit acceptance of **this content, version and scope** from the
   authorized person/channel. Interview answers, permission to create, existing
   files, a base proposal and format checks do not substitute. If declined,
   absent or proposal-only, make zero normative writes and return the proposal.
   A substantive post-acceptance change requires renewed acceptance of that part.
3. Use the project's accessible decision/version convention, no mandatory new
   manifest/tracker. If none exists, propose a concise decision/provenance section
   in a scoped engineering concept: candidate revision, exact normative scope,
   actual acceptance decision and known actor/date/source version. Present this
   evidence placement with the candidate. The version must identify shown content;
   use an accessible revision or digest when needed for recovery, with evidence
   outside hashed content to avoid self-reference. Persist the actually used
   base/profile package revision or resource digest from available evidence;
   retrieve through permitted tools or supplied package identity, never invent
   it or omit an unavailable-provenance limitation. Do not use OKF `verified`
   to imply code compliance or replace scoped acceptance. Inaccessible acceptance
   evidence prevents claiming the combined saved result complete.
4. Immediately before saving, reread baseline files/absence and related read-only
   dependencies, compare bytes and confirm paths remain authorized. Unexpected
   change stops dependent writes: reconcile content and acceptance, not overwrite
   foreign work. Follow the project's concurrency protocol; comparison detects
   conflict but is not atomic CAS or universal race protection. Missing a required
   guarantee blocks the dependent write. Keep short write windows separate from
   interview/acceptance discussion.
5. Save only accepted engineering norms, decision evidence and necessary indexes/
   affected existing logs via `ris-okf`. One rules bundle: architecture/ADR are
   nested knowledge, not separate roots. First create uses a minimal root
   `index.md` with `okf_version: "0.2"` and sufficient typed concepts; index every
   real knowledge directory under RIS. Nested indexes have no frontmatter;
   concepts have a nonempty string `type`. Preserve usable existing structure,
   create no empty documents or absent architecture area. Common-index changes
   are navigation only: retain neighbors/extension fields/text; do not duplicate
   norms or rewrite process rules. No new log is mandatory.
6. Reread saved files; compare accepted content/version/decision, and unaffected
   bytes against baseline. Apply `ris-okf` checks, resolve changed links (leading
   `/` from rules root, relative from their file; cross-bundle targets explicitly).
   New minimal bundle: check the entire created bundle and RIS directory indexes.
   Adding engineering to existing rules or updating it: check changed concepts/
   indexes and affected links only, without claiming the unchecked whole valid.
   Separate mandatory OKF violations from advice and stricter RIS requirements.
   An unrelated invalid/unchecked concept gives no permission to repair it; a
   fault directly preventing a correct scoped save blocks that save. This wrapper
   still owns subject sufficiency, not only formatting.

On failed, partial or ambiguous writes stop further writes and reread actual
state before a retry. Report exact saved/unsaved parts, current versions and
missing navigation/evidence/checks. Do not blindly retry, roll back foreign work
or call a partially indexed result complete. Reconcile actual persisted content
and prior acceptance before a later authorized attempt.

## Return and stop

Report `ok|blocked|conflict|error`, selected project/current root and context
provenance, operation/scope, actual document/decision addresses, version and
source provenance, saved changes, subject and scoped OKF/RIS checks, neighboring
conflicts, deferred questions and limitations. Distinguish proposed, accepted
and saved; promised-result `ok` requires all three plus read-back checks.
An unchanged retry returns existing accepted content only after verifying its
decision/version/files, without inferred new approval or duplicate history.
Proposal-only completion is not accepted/saved rules. Document checks establish
neither configured/passing tools, implementation compliance, delivery readiness
nor remote publication. Stop here; template updates never update project norms.
