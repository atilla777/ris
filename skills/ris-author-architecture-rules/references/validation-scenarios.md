# Author validation scenarios

For maintainers verifying this skill, not a mandatory authoring resource.
Execute with installed dependencies/resources and inspect actual calls,
dialogue and project bytes before/after; a routing answer or structural search
alone is not execution evidence. Record package digest, environment/model,
permissions, candidate/decision and scoped checks. Test decisions are fixture
authority, not real-user approval of another project's rules.

| Case | Inputs and observation |
|---|---|
| Create | Small new Rails project; no product/tracker, default rules path. Supply minimal purpose/stack, leave material interdependent boundaries unknown. Verify base/profile/interview actually applied, confirmed answers reused, candidate shown and no writes before final acceptance. Continue with fixture-owner acceptance; inspect minimal OKF root, nested index, sufficient concepts and accessible scoped decision. |
| Update/worktree | Existing DragonRuby rules in a different configured path and real Git worktree. Change only class-owned-state reset norm. Keep existing state/save rules, engineering/process documents and extension fields byte-identical except authorized delta/evidence/navigation. Confirm worktree paths, scoped version/decision and format claim; primary copy must remain unchanged. |
| Related conflict | Architecture proposal forbids a dependency required by engineering. Show conflict and needed neighboring amendment without writing that area or claiming overall consistency. A fixture owner may accept only the limited result with that dependency explicit. |
| No acceptance | Owner declines or requests only a proposal. Normative files, indexes and decision evidence remain unchanged. |
| Stale baseline | After presenting candidate, change a target/index or relevant related rule externally. Accept old candidate. Verify reread detects change and stops dependent writes, preserving new bytes; reconciliation/reacceptance precedes further save. |
| Partial | Make a later accepted write fail after one succeeds. Inspect persisted state; report saved/unsaved paths and incomplete check/evidence, no blind retries or false success. Restore write access only for a fresh reconciled attempt. |
| Format | Update ordinary Markdown, 0.1, unknown version and declared 0.2 with an unconverted target. No silent migration. Separately test a usable 0.2 target with unrelated unconverted engineering concept: bounded result may succeed, never whole-bundle claim/foreign repair. |
| Missing inputs/resources | Missing update rules or boundary does not become create. Missing base, common/context or pinned OKF resource blocks its dependent work; no copied substitute or completion claim. |
| Installed isolation | Install folders/resources outside source repository. Only applicable base profile loads; no engineering author, tracker or specs wrapper. Rules remain usable after installed source materials change or are removed. |
| Selection | Natural requests to establish project boundaries or revise one normative lifetime rule select this wrapper; portable text-only method, feature design, audit, CI setup, library extraction, impact and unrelated requests retain their own owners. |

The common demonstration rules bundle belongs to the separate packaging work;
these scenarios do not install that sample as project norms or require it.
