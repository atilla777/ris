# TDD-реализация задачи RIS

## Согласованный объём

Пользователь принял этот объём в обсуждении 13 октября 2026 года и затем явно
поручил продолжить реализацию. Это самостоятельное улучшение пакета, не новая
продуктовая фича с искусственным эпиком. Задача: `ris-cbs`.

База сравнения — `e386a85`: завершённая поставка `ris-bf4` уже интегрирована.
Основания: [архитектура](../../concepts/01-architecture.md),

## Требования

1. Сохранить автономный `ris-implement-base`: обычная реализация по умолчанию,
   опциональный режим TDD по явному требованию вызывающего, заданию или правилам
   проекта. Тесты и их запуск не становятся опциональными вместе с TDD.
2. Заменить `ris-implement-task` на `ris-tdd-implement-task` без скрытого alias.
   Проектная обёртка всегда требует TDD от базы и проверяет его свидетельства;
   не копирует сам алгоритм. Прямое применение базы без RIS сохраняется.
3. В TDD менять поведение небольшими вертикальными циклами: тест, реально
   наблюдаемый RED по ожидаемой причине до реализации, минимальная реализация,
   подтверждённый GREEN, при необходимости локальный REFACTOR с проверками.
   Ошибка окружения не RED; test-last не подменяет TDD. Невозможность цикла
   блокирует зависимое изменение, а не вызывает молчаливую смену режима.
4. Рефакторинг без изменения поведения сохраняет существующие зелёные тесты;
   сопутствующая документация проверяется своим способом. Чисто текстовая работа
   не требует искусственного RED и не является целью TDD-обёртки.
5. Тесты проверяют наблюдаемое поведение через устойчивые границы, с независимо
   обоснованными ожиданиями. Запускается минимальный достаточный набор новых и
   существующих затронутых проверок, включая потребителей изменённых контрактов.
   Полный suite — по правилам проекта или обоснованной области влияния.
6. Условные подробности TDD и сложного состава проверяемого снимка принадлежат
   `references/` базы; особенности task-specific/worktree-копии — ресурсу
   обёртки. Условия чтения явные, пути installed-relative. Основной контракт
   сохраняет критические гарантии и достаточность обычного вызова.
7. Адаптер задач владеет протоколом feature record; обёртка требует проверенных
   входов и проверяет принятие/применимость к текущему коду и общим контрактам,
   не повторяя формат и исторические payload. Claim, сохранность чужой работы,
   документация и точная идентичность проверенного снимка сохраняются.
8. Worktree-инструкции потребителей абстрактны: проверка пригодности текущей
   копии, связи с задачей и current/primary roots. Подготовка владеет своими
   решениями, выбранный `worktrees/1` адаптер — командами и инструментальными
   деталями. Реализация не создаёт/ремонтирует копии и не подключает подготовку.
9. Отчёт по умолчанию — `workspace.tasks/<ID>/implementation.md` в основной
   копии; явный путь, затем соглашение проекта имеют приоритет. История и чужие
   заметки сохраняются; read-back обязателен. Новые настройки `ris.yaml`,
   обязательные субагенты реализации и отдельный тестовый скил не вводятся.

## Принятый технический подход

Методика реализации имеет полезное самостоятельное применение, поэтому база
сохраняется отдельно. Проектная обёртка владеет claim-aware code/tests/docs
результатом и его сохранением. Режим — смысловой вход базы, не выдуманный
аргумент загрузчика или новый формат конфигурации.

`references/tdd.md` загружается в режиме TDD перед изменением поведения;
`references/publication-snapshot.md` — при посторонних dirty-файлах, исключениях
или неоднозначности состава снимка; `references/current-copy.md` обёртки — для
task-specific/отдельной копии либо смены копии. Ни один ресурс не содержит
чужого алгоритма подготовки или CLI worktree.

Переименовать source и installed обёртку, синхронизировать ресурсы базы, README
и действующие нормативные ссылки. Исторические спецификации/отчёты не переписывать.
Обновлённая фактическая карта описывает локальное состояние поставки; Git-
интеграция и публикация устанавливаются отдельно по фактическим свидетельствам.

## Критерии приёмки

| ID | Проверяемый результат |
|---|---|
| AC-001 | База без RIS выполняет обычный режим; TDD-ресурс не загружается без условия. |
| AC-002 | Новый функционал/исправление в TDD имеет наблюдаемые ожидаемый RED и GREEN; ошибка runner не принимается за RED, обход test-last отсутствует. |
| AC-003 | Тесты содержательны; выбран и запущен затронутый набор, обязательные проверки не скрыты; рефакторинг не создаёт искусственный RED. |
| AC-004 | Ресурсы доступны из установленной папки без source repo; обычный запрос не загружает редкие ветки; сложный snapshot не смешивает код с локальным контекстом. |
| AC-005 | Обёртка реально применяет базу в TDD, guards задачи/claim/входов/docs сохранены, protocol/CLI логика остаётся у адаптеров. |
| AC-006 | Default/override пути отчёта работают, история сохраняется; primary-root нужен только для соответствующих shared-path действий. |
| AC-007 | Новое имя, source/install и действующие ссылки согласованы; старого установленного alias нет, исторические документы сохранены. |
| AC-008 | Проверены структура, выбор/выполнение и условные ветки; независимое ревью без высоких/средних замечаний, ограничения свидетельств явные. |

## Исключения

Не вводить универсальный delivery-оркестратор, вариант проектного исполнителя
без TDD, миграцию feature records, настройку среды пользователя, автоматическое
ревью/публикацию/закрытие из скила реализации или ремонт worktree.
