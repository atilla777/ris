# Сквозная связность RIS — требования v1

**Статус:** согласованные требования обсуждения 15 октября 2026 года,
сохранение и публикация разрешены отдельно. [Решение v1](acceptance.md#требования-v1).
Подготовка — `ris-bxc`, не feature-record и не задача реализации.
[Аудит](audit.md) описывает baseline; [D1](design.md) — предложенный, **не принятый** дизайн.
Наличие документов не означает реализации новых контрактов.

## 1. Результат и границы

В проекте под RIS новая сессия должна продолжать выбранную работу по короткому
поручению, восстанавливая существенные решения и версии без прежнего чата.
Для большинства проектных атомарных операций над существующей работой обычный
вход — `/<команда операции> <ID задачи или контейнера>`.
Команда загружает фактически установленный скил; её наличие проверяется,
а будущие имена не выдаются за доступные команды.

Операция сама находит проектные правила, настройки/defaults, задачу и относящиеся
источники. Она проверяет содержательную готовность, а не только наличие файлов.
Дополнительный ввод нужен для действительно отсутствующего решения, неоднозначности,
нестандартного scope/исключения или неустановленных полномочий. Короткий вызов
достаточен для начала проверки, но не гарантирует успешного выполнения.

Охват: цели/знания и правила → roadmap/эпик → выбор/требования/дизайн → задачи →
подготовка/план/реализация/документация → review/исправления → Git-публикация →
проверка результата/завершение/публикация трекера → ретроспектива. Учитываются
пересмотр и прерывания; обязательная стадия или отдельный скил ради симметрии
не вводится. Источники продукта остаются авторскими.

## 2. Владельцы и самостоятельность

Атомарная операция имеет собственный полезный результат и остановку; это не
ограничение одним действием. Применение базы/адаптера, принятие и сохранение
могут составлять один результат. Комплексный скил владеет цепочкой самостоятельных
операций, переходами, правами и достаточностью совокупного результата.
Он применяет владельцев, а не копирует их алгоритмы или только упоминает имена.

Самостоятельные задачи и task-контейнеры поддерживаются без искусственного эпика
или feature-record. Не каждая операция применима к каждому типу записи.
Ребёнок имеет собственные результат, границы, критерии и точные ссылки на
принятые входы; копировать всю родительскую спецификацию не требуется.
Структурный `parent` допустим, связанные источники читать можно. Недостаточная
собственная постановка — пробел подготовки, а не требование передать историю чата.

Ребёнок не проверяет и не завершает родителя. Завершение контейнера — отдельная
атомарная операция по явно выбранному ID, вызываемая человеком, сценарием или
внешним workflow. Она проверяет обязательный состав и общий результат, а не только
закрытые статусы. Закрытие не поднимается по предкам и не запускается автоматически
после последнего ребёнка. Общие критерии не размножаются по всем детям.

## 3. Итог и навигация

Итог каждой операции восстанавливаем: фактический результат/идентичность,
адрес либо проверяемое соглашение обнаружения, существенные версии/решения,
saved/accepted/published факты, ограничения и незавершённость.
Отчёт не является вторым трекером и не заменяет источники истины.

**Первоначальная идея обязательного next-skill prompt в каждом атомарном отчёте
отменена решениями обсуждения.** Атомарная операция не обязана выбирать следующего
владельца; вложенный результат возвращается вызывающему. Переходы принадлежат
сценарию/внешнему workflow. Ручной пользователь может отдельно вызвать read-only
навигацию, чей самостоятельный результат — обоснованный короткий промпт продолжения
или точная блокировка. Это не универсальный исполнитель SDLC.

Навигация различает: продолжение той же операции; следующий результат после
успеха; незавершённый сценарий; возврат управления; нужное человеческое решение;
отсутствие совместимого владельца. Она читает текущие факты и применимые контракты,
не создаёт второй изменяемый roadmap/registry, не дублирует recovery-алгоритмы,
не принимает решения и не запускает рекомендуемое действие.

Промпт содержит реальный ID и фактическую операцию; project/scope/permission
добавляются только при необходимости. Рекомендация не является разрешением или
доказательством готовности. Выдуманные ID, команды, refs и длинные обходные
алгоритмы вместо отсутствующего владельца недопустимы.

## 4. Публикация и композиция

Прямой вызов **законченной планировочной операции** по умолчанию доводит её
результат до предусмотренной публикации. Roadmap/эпик и декомпозиция публикуют
трекер; требования/дизайн — принятые документы и отдельные решения в Git,
а связанные записи/refs и трекер — когда входят в обещанный результат.
Git-коммит не создаётся для эпика ради единообразия. Требования могут быть
законченным результатом до дизайна; их публикация не запускает дизайн.

Планировочный скил отвечает за достаточность целого и **вызывает** переиспользуемого
владельца публикации. Техническая процедура, проверка назначения/полного outgoing
scope, сохранность чужого, remote read-back и сверка неоднозначных эффектов
принадлежат этому владельцу, не копируются в каждом планировщике.
Нужно сначала оценить существующих Git-владельца и адаптер трекера, а не заранее
создавать ещё один publisher. Git и трекер остаются разными проверяемыми каналами.

Явно ограниченное поручение пользователя/сценария может требовать только локальный
или промежуточный вклад. В таком случае публикационный переход принадлежит
вызывающему. Ограничение передаётся явно: субагент или присутствие Gas City
сами по себе не меняют смысл вызова. План leaf-задачи и операции реализации,
документации/review не публикуют Git самостоятельно; публикация изменения —
в конце согласованного цикла разработки. Completion и tracker publication
проверяются отдельно.

Полномочия следуют из поручения, контракта и правил проекта; общий вызов не
принимает невидимое содержание и не разрешает неизвестную исходящую историю.
Недоступная публикация даёт частичный/заблокированный полный результат,
а не фиктивный успех. Возможный прямой push/иная политика целевого проекта
не переопределяется этим требованием.

## 5. Восстановление и ограничения

Повтор проверяет фактические эффекты и текущую применимость. Он сохраняет
подтверждённые IDs/публикации и неизменённые принятия; продолжает недостающую
операцию, не воспроизводит слепо всю цепочку. Изменённые входы возвращаются
соответствующему владельцу для адресного пересмотра; unaffected evidence сохраняется.
Неоднозначный push сначала проверяется удалённым чтением.

Права, claim, blockers и требуемая защита записи устанавливаются заново.
Историческое окно не становится действующим; claim/worktree/read-back не CAS.
Closed не означает принятие полного результата. Контейнер не переоткрывается
для восстановления чужой незавершённой публикации.

До ID или при read-only ответе существенный результат не считается автоматически
доступным новой сессии: вызывающий использует разрешённый существующий источник
или сообщает точный отсутствующий вход. Новый обязательный draft store, bead
или формат handoff не вводится. Локальный файл пригоден лишь в окружении,
где доступен; его не объявляют удалённым входом другой копии.

Переносимые операции не получают обязательных RIS/Beads-зависимостей. История
сессии, явный OKF-root и иные предметные locator остаются входами своих операций.
Совместимость с конкретным Gas City не подтверждена: здесь требуется пригодность
для внешней оркестрации без скрытого выбора маршрута.

## 6. Критерии приёмки будущего изменения

Все критерии проверяются чтением контрактов, статической сверкой и независимым
ревью; это не runtime PASS поведения агента.

| ID | Условие и наблюдаемый результат |
|---|---|
| AC-001 | Для существующей проектной задачи применимая атомарная операция восстанавливает обязательные входы по команде+ID из конфигурации/defaults и устойчивых источников; доступные факты не переносятся на пользователя |
| AC-002 | При missing/ambiguous/stale input блокируется зависимая часть, названы конкретный пробел/решение и независимо полезный результат; готовность не выдумана |
| AC-003 | Standalone-задача и task-контейнер получают применимый маршрут без искусственного эпика/feature-record; неверный тип даёт диагностику |
| AC-004 | Созданный/проверенный ребёнок имеет собственный достаточный контракт и точные входные ссылки; parent остаётся структурой, ребёнок не управляет его завершением |
| AC-005 | Отдельное завершение явно выбранного контейнера проверяет общий результат/состав/blockers, не выводит принятие из closed детей и не закрывает предков |
| AC-006 | Атомарные отчёты имеют обнаружимый результат, версии/решения и честные состояния каналов; обязательный следующий скил не назначается, вложенный итог возвращается вызывающему |
| AC-007 | Отдельная read-only навигация выдаёт обоснованный короткий вызов либо точную блокировку; не выполняет переход, не копирует recovery и не создаёт второй источник состояния |
| AC-008 | Для прямого законченного планировочного результата предусмотрены сохранение, проверка и необходимые публикации; локальное сохранение не выдаётся за полный опубликованный результат |
| AC-009 | Публикацию исполняет переиспользуемый владелец с проверяемым результатом; вызывающий проверяет целое без копирования алгоритма; Git/трекер не смешаны |
| AC-010 | Явно ограниченный вклад и полный вызов различимы; вложенность/Gas City не меняют режим скрыто; leaf-операции не публикуют промежуточный Git самостоятельно |
| AC-011 | После частичного эффекта/прерывания сверяются реальные результаты и возобновляется недостающее; нет повторного create/push/принятия по устаревшему маркеру |
| AC-012 | Пересмотр требований/дизайна/rules/package проверяет применимость, сохраняет неизменённые решения/evidence и возвращает материальное отклонение его владельцу |
| AC-013 | При передаче заново проверяются права/claim/blockers/гарантии; старое окно, статус и существование worktree не объявляются допуском |
| AC-014 | Промпты используют реальные установленные имена/IDs/refs, не маскируют недостаточный handoff; переносимые/no-ID операции сохраняют автономные locator |
| AC-015 | Для атомарного и сценарного пути есть полная карта output→required input; сценарий применяет владельцев и проверяет их вклад, а не только называет имена |
| AC-016 | Изменённые нормы, skills/resources/commands и установка согласованы; статические проверки и независимое review без high/medium, без agent behavioral tests и без заявления живой проверки |

## 7. Исключения и следующие решения

Эта подготовка не реализует требования, не меняет текущие skills/commands/config/
нормы и не выполняет миграцию именования `ris-1fq` или installer. Состояния задач
читаются в Beads, исторические решения не переписываются.
Новые workflow engine, универсальная схема состояния/отчёта, registry, обязательный
этап SDLC, автоматический deployment и интеграция Gas City не входят в поставку.

Имена новых операций, точная переработка существующих владельцев, безопасное
обнаружение primary/copy и порядок реализации — отдельно принимаемый дизайн D1.
Требования v1 не являются принятием D1 или разрешением начать реализацию.
