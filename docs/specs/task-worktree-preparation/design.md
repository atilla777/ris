## Дизайн

### 1. Компоненты и зависимости

Поставляются четыре исходных скила с ресурсами и синхронными установленными копиями:

- `ris-prepare-worktree-base` — автономная методика подготовки и проверки рабочей
  копии: выбор создания/повторного использования, сохранность, подготовка разрешённого
  окружения, общий результат и восстановление. Не требует RIS, трекера или `.sdlc/`.
- `ris-prepare-task-worktree` — проектный владелец: `ris-common`, `ris-context`,
  выбранный task-адаптер, подтверждение задачи/захвата, извлечение правил и путей;
  применяет базу и проверяет совокупный результат, не копируя её методику.
- `ris-git-worktree-adapter` — ограниченные операции стандартного Git.
- `ris-worktrunk-adapter` — те же операции через Worktrunk; владеет его версиями,
  настройками, JSON и инструментальными особенностями.

База загружает только выбранный адаптер перед его операциями. Адаптеры получают
точные входы и правила фактического проекта; не требуют RIS-конфигурации, Beads,
базы или знания следующих этапов. Прямой вызов каждого компонента поддерживается.
База отвечает за переносимый результат, адаптер — за конкретный инструментальный
эффект. Отдельная база оправдана полезным прямым применением вне RIS; ещё один
общий скил или обязательный программный оркестратор не вводится.

### 2. Входы, выбор инструмента и владение состоянием

Вход базы: репозиторий, необходимые корни, идентичность работы и основание её связи
с копией, выбранный адаптер, ветка/путь, исходная ревизия либо правило её выбора,
права чтения/записи, проектные ограничения и разрешённая подготовка окружения.
Вне RIS эти значения передаются напрямую: нет поиска `ris.yaml`, обязательного
task ID, захвата или каталога заметок. Идентичность работы нужна при проверке
принадлежности копии, но не обязана быть записью трекера.

RIS-обёртка требует точный task ID и actor. Перед мутациями проверяет открытую
незаблокированную задачу и через явно поддерживаемую операцию task-адаптера
получает разрешённый захват либо подтверждает свой. Чужой захват — конфликт.
После захвата и перед новыми порциями изменений перечитывает владение/блокировки.
База получает подтверждённые входы, но не объявляет claim межпроцессной блокировкой.

Выбор инструмента: явный запрос, иначе однозначное правило проекта, иначе Git.
Наличие `wt` не означает выбор Worktrunk. `ris.yaml` v2 не расширяется; выбор
можно передать явно или закрепить проектным правилом. Default RIS-адреса:
`task/<ID>` и `workspace.worktrees/<ID>`; явная либо ранее подтверждённая связь
имеет приоритет. Имена проверяются без произвольного lossy-преобразования.

Трекер владеет задачей/захватом, Git — refs и регистрацией worktree, проектные
правила — настройками, база — проверкой результата. Новый изменяемый реестр
задач/worktree и поля в feature-record для рабочих копий не создаются.
Имя ветки само по себе не доказывает принадлежность: нужна согласованная связь,
доступное предыдущее свидетельство либо явное подтверждение текущей копии.

### 3. Контракт адаптеров `worktrees/1`

Это смысловой контракт, а не новый RIS CLI. Владелец переносимой семантики —
`ris-prepare-worktree-base/references/worktrees-contract.md`; адаптеры содержат
достаточное отображение своих операций на CLI и объявляют поддержку/ограничения.

- `worktrees.list`: полный состав зарегистрированных копий или явная неполнота;
  пути, ветки/detached, HEAD, lock/prunable и доступные диагностические состояния.
- `worktrees.read`: одна точная копия, её связь с репозиторием, branch/HEAD,
  индекс/изменения/untracked и незавершённые Git-операции; неизвестное не равно чистому.
- `worktrees.create`: уже согласованные абсолютный путь, ветка, точный base commit,
  разрешение и ожидание отсутствия. Возвращает фактический эффект и независимое
  чтение Git; при неоднозначном ответе сначала сверяет состояние, не создаёт повторно.

Адаптер не захватывает задачу, не решает принадлежность чужих файлов, не готовит
технический план и не принимает весь результат. Создание не является транзакцией
с трекером и окружением; Git защищает отдельные refs/операции, но не всю цепочку.
Заявление строгой конкурентной уникальности требует внешнего окна координации;
force, reset существующей ветки, clobber и автоматический repair/prune исключены.
Неудача не разрешает перейти на другой адаптер без нового выбора.

Git использует стабильный `worktree list --porcelain -z`, точные status/ref-проверки
и создание с явными веткой, путём и commit. Независимо от инструмента окончательная
проверка опирается на Git, а не только на exit code или текст CLI.

Worktrunk: проверка фактической версии/возможностей; опорная версия первой поставки
0.68.0. Для list задаётся schema 2 одноразовым override; null/пропуск не превращаются
в успешную проверку. Путь создания задаётся одноразовым `worktree-path` override,
не записью пользовательской конфигурации; возможность `switch --path` не требуется.
Используются явные branch/base, `--no-cd` и JSON там, где доступны. После вызова
проверяются фактические путь/ветка/HEAD. Несовпадение с личным шаблоном Worktrunk
не является конфликтом, если согласованная связь и фактическая Git-регистрация верны.
Версии вне проверенной матрицы не объявляются совместимыми без проверок возможностей.

### 4. Создание, повторное использование и окружение

До захвата и создания выполняется доступный preflight инструмента, путей,
конфликтов и необходимой подготовки. Новая ветка: выбрать установленный проектом
remote и основную ветку, обновить её сведения, разрешить точный commit и передать
его адаптеру. Явная ревизия имеет приоритет. Ошибка обновления блокирует создание;
локальная основная ветка не переключается и не сбрасывается.

Повторный запуск сначала сверяет прежние эффекты. Для той же подтверждённой копии
сохраняет HEAD, индекс, файлы и путь; сообщает отставание/изменения, но не обновляет
её автоматически. Существующая ветка без копии может использоваться только при
подтверждённой связи и явном согласовании её текущей ревизии; новый base не применяется
к ней через reset. Неоднозначная связь, чужие данные, повреждение, недоступная копия
или незавершённая операция дают конкретное препятствие без автоматического ремонта.

База владеет подготовкой окружения по точному разрешённому набору действий,
предусловий, ожидаемых результатов и способов проверки. Нет универсального
автоматического install/copy/start. Это не обязательный новый формат конфигурации:
подходят доступные проектные команды/скрипты и явно согласованные hooks.

Перед Worktrunk-мутацией адаптер проверяет эффективные user/project hooks и их
побочные эффекты. Режим без дополнительных Worktrunk-hooks допустим лишь когда
проект разрешает их не запускать; он не означает обход обязательных Git-hooks.
Нужные hooks выполняются только в разрешённой области и с проверяемым результатом.
Фоновый процесс не означает готовность: необходимы наблюдаемое завершение/код
возврата либо проверенный сигнал готовности для сервиса. Если обязательное действие
не удаётся контролировать или проверить, результат остаётся blocked/error.

Копирование — только согласованный состав, без overwrite существующих файлов.
Общая база трекера, `.sdlc/tasks/` основной копии, вложенные worktree и другое
общее изменяемое состояние не копируются как независимое окружение. При использовании
`copy-ignored` перед записью проверяется фактический выбранный состав и исключения;
его default «все ignored» не считается разрешением.

### 5. Результат, сохранение и частичные эффекты

База возвращает status, связь работы/копии, пути/корни, branch/HEAD, base для нового
создания, состояния индекса/файлов, выбранный инструмент и версию, отдельные verdict
рабочей копии и окружения, фактические effects, проверки и конкретное восстановление.
Эквивалентный структурированный Markdown достаточен; универсальный JSON всех скилов
не вводится. Нет утверждения о готовности требований/дизайна к реализации.

RIS-обёртка добавляет task/actor/claim и заново проверенный контекст через ris-context.
По отдельному разрешению сохраняет свидетельство в
`workspace.tasks/<ID>/worktree.md` основной копии; иначе возвращает его в ответе.
Существующее свидетельство читается и сохраняется история, чужой текст не заменяется.
Это проверяемая рабочая заметка, не второй реестр и не удалённый обязательный вход.
База вне RIS пишет свидетельство только по явно переданному разрешённому адресу.

При сбое сохраняет и перечисляет захват, ветку/копию и завершённые setup-действия;
не освобождает claim, не удаляет worktree и не делает rollback молча. Повтор сначала
перечитывает task/копию/окружение. Успех одного этапа не скрывает сбой другого.
Короткие внешние окна применяются только где нужна соответствующая гарантия;
между обсуждениями или длительной подготовкой они не удерживаются.

### 6. Изменения потребителей и совместимость

Из `ris-plan-task` и `ris-implement-task` удаляется собственная подготовка worktree
и соответствующее обещание в description. Они не загружают новую базу/обёртку/
адаптеры: читают текущую копию, проверяют task-связь там, где она необходима,
доступные код/контракты и корни; недостаточный вход сообщают без запуска подготовки.
Планирование без мутаций не требует захвата или отдельной копии. Реализация
сохраняет своё разрешённое получение/проверку claim перед файловыми изменениями;
подготовка копии и claim — разные ответственности.

Совместимы независимые прямые вызовы в текущей подходящей копии; прежний составной
запрос «спланируй и создай worktree» больше не обещается одним скилом планирования.
Порядок самостоятельных операций определяет пользователь/внешний workflow;
будущий delivery-сценарий и команда не поставляются этой фичей.

Синхронизируются изменённые source/install копии, README, описание текущего состава
в `docs/concepts/ris-sdlc-mvp-skills.md` и затронутая текущая архитектурная карта
`docs/rules/architecture/`; конкретные страницы выбираются по фактическому влиянию.
Нормативные принципы и исторические принятые спецификации не переписываются ради
нового состояния. Текущие карты обновляются лишь по проверенной интеграции.
Других активных accepted designs с конфликтующим владельцем в полной выборке нет;
закрытая `ris-npn` — источник прежней поставки, не новая зависимая задача.

### 7. Проверки и покрытие

Проверки выполняются на изолированных настоящих Git-репозиториях и временных
Beads-проектах через установленный CLI, без пробных мутаций текущей базы RIS.
Для каждого результата фиксируются входы, версия, реальные вызовы и file/ref oracle.

| AC | Test seam и наблюдаемый результат |
|---|---|
| 001–002 | Прямой RIS-вызов с точным ID; чужой claim, закрытая/заблокированная задача; отказ до файловых мутаций, успешный claim/read-back. |
| 003 | Одинаковые адаптерные сценарии Git и Worktrunk 0.68.0; отсутствующий/несовместимый выбранный CLI без fallback. |
| 004–005 | Remote с продвинувшейся основной веткой, offline fetch, явный commit, нестандартная ветка, пути с пробелами; точные base/branch/path, отсутствие reset основной копии. |
| 006–007 | Повтор с staged/unstaged/untracked и своими commits; сравнение байтов, индекса и refs до/после. Занятый путь, чужая связь, prunable и незавершённые операции не исправляются автоматически. |
| 008–009 | Разрешённый setup success/failure, контролируемый фоновой результат, копирование allowlist; неизменность tracker/shared notes и файлов вне scope. |
| 010–011 | Реальное read-back и повтор после частичного создания/setup-сбоя; точный self-contained handoff и сохранённые эффекты. |
| 012 | Прямые planning/implementation вызовы без подготовки; проверка отсутствия новой зависимости/создания, сохранённый claim guard, второй RIS-проект с другими путями. |

Отдельный автономный сценарий базы вне RIS проверяет создание/повтор и окружение
без ris.yaml, Beads, RIS-common/context и `.sdlc/`. Адаптеры проверяются напрямую.
Source/install parity, выбор скилов и стоимость обычной загрузки проверяются вместе
с независимым ревью границ и достаточности результатов. Непроверенные версии/ветки
не считаются пройденными. Архитектурное решение фиксируется здесь и проверяется
независимым ревью; отдельный ADR без дополнительного основания не требуется.
