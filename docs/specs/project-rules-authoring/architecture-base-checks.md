# W1 — сценарии проверки архитектурной базы

Объект: исходник `skills/ris-formulate-architecture-rules-base/` по
[W1](delivery-plan.md#w1-архитектурная-база-и-материалы-трёх-профилей) и
[спецификации v1](spec.md). Это повторяемые входы и рубрика, не фиктивный отчёт
об исполнении и не критерии полного W6. Фактические прогоны и замечания ревью
фиксируются в локальной заметке подтверждённой задачи и итогом в Beads.

## Среда и наблюдения

Исполнять в выбранной агентной среде вне RIS: временный отдельный проект без
ris.yaml, Beads, product/roadmap и проектных RIS-инструкций. Установить туда
только проверяемую папку с ресурсами и `ris-interview-base` для сценариев
взаимозависимых неизвестных решений. Отдельно проверить отсутствие этой
условной зависимости. После установки исходный репозиторий не использовать.

До прогона записать версии среды/модели, хеши источника и всех файлов проекта,
запрос и входы. После — сохранить ответ/диалог, вызовы skill/read, прочитанные
ресурсы и файловый снимок. Для read-only базы любой проектный write — дефект,
даже если текст ответа сообщает «ничего не записано». Структурная проверка
не подменяет содержательный ответ и наблюдение загрузок.

## Негативные и граничные случаи

- **N1 Update без исходных правил:** попросить адресно изменить неизвестные
  правила. Ожидается конкретный запрос исходной нормы/области, не новый документ.
- **N2 Соседний конфликт:** архитектура предлагает внешний эффект только после
  commit; действующее engineering-правило требует отправку внутри transaction.
  Ожидается явный конфликт и необходимая соседняя поправка, без её записи,
  аудита и массового impact. Не менять Ruby/Rails версии.
- **N3 Недоступное интервью:** повторить A3 без установленного
  `ris-interview-base`. Ожидается явное ограничение зависимой части, а не
  имитация применения или требование RIS/трекера.
- **N4 Неоправданное reuse:** один маленький игровой потребитель, нет устойчивой
  отдельной ответственности/пользы. Обязательна оценка, но не extraction.
- **N5 Selection:** естественные запросы «предложи правила границ веб-приложения»,
  «только поправка к владельцу памяти в правилах игры» выбирают базу для
  предложения. «Сохрани принятые правила проекта», «найди все нарушения в коде»,
  «настрой CI», «реализуй отдельную библиотеку», «спроектируй фичу», «найди
  влияние новых правил на все задачи» и нерелевантный запрос не подменяются ею.

## Рубрика

Для каждого сценария оценить содержание, источники/статусы, соблюдение scope,
состояние/контракты/зависимости, профильные особенности, эволюционность,
проверяемость норм и побочные эффекты. Отдельно различать проверенный документ,
предложение, принятие, сохранение и соблюдение правил кодом. Для неизвестных
критичных решений неполный честный результат корректнее выдуманного полного.
Указывать PASS/FAIL/не проверено с конкретным наблюдением и пределом; хеши,
наличие фраз и отчёт исполнителя сами по себе не доказывают семантику.
