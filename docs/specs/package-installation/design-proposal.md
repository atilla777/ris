# Эскиз механизма установки RIS

**Статус:** эскиз на основе интервью, не полный принятый технический дизайн.
Требования: [spec.md](spec.md). Границы подтверждения: [acceptance.md](acceptance.md).
После отдельного принятия D1 актуальный дизайн — [design.md](design.md),
декомпозиция — [delivery-plan.md](delivery-plan.md). Ниже сохранён исходный
эскиз; перечисленные открытые вопросы больше не являются пробелами D1.

## Подтверждённая конструкция

- Один shell-установщик выполняет `install`, `update`, `uninstall`.
- Скил `ris-manage-installation` определяет запрос и параметры, использует
  установщик и сообщает результат. Команда `/ris-manage` — тонкий вход в скил.
- README описывает получение установщика и первоначальную установку из GitHub
  до появления RIS в проекте. Независимого алгоритма копирования в инструкциях нет.
- Источники остаются в `skills/` и `commands/opencode/`; копируются полные
  каталоги скилов и команды одной ревизии.
- Установка — обычные файлы в проектных каталогах OpenCode; все пакетные
  `ris-*` заменяемы и включаются в Git проекта. Установщик не коммитит.
- Служебный файл фиксирует источник и точный установленный коммит.
- Загрузку, замену и восстановление можно переиспользовать при добавлении
  harness; особенности OpenCode должны быть отделены от этого механизма.
- Базовый скил не выделяется: нет самостоятельной переносимой предметной
  методики, полезной отдельно от управления самим RIS. Независимость от
  `ris.yaml` и Beads обеспечивается одним скилом управления пакетом.

## Предложенный порядок замены

1. Проверить незавершённую прежнюю операцию; при наличии восстановить прежнее
   состояние до обработки нового запроса.
2. Однозначно разрешить выбранную версию в полный commit ID.
3. Скачать и проверить весь комплект во временной области.
4. Сохранить прежние управляемые файлы и служебное состояние.
5. Заменить весь управляемый набор комплектом выбранного коммита.
6. Проверить результат, зафиксировать завершение и удалить ненужную резервную копию.

Ошибка после начала замены запускает восстановление. При повторной ошибке
восстановления данные не уничтожаются и успех не сообщается. В момент прерывания
набор может быть неполным: набор каталогов не объявляется атомарно заменяемым.
Работа с обновлёнными инструкциями начинается после перезапуска OpenCode.

## Решения для полного технического дизайна

Следующие пункты ещё не выбраны; реализация не должна трактовать их как готовый API:

1. Путь единственного установщика и способ его поставки. Выполняемая копия должна
   переживать обновление или удаление собственного скила; первоначальное получение
   через README должно использовать тот же механизм, а не отдельный алгоритм.
2. Точный CLI, зависимости shell-скрипта для Linux/macOS, получение GitHub-ревизии
   и полного набора файлов. Не предполагать наличие GNU-утилит на macOS.
3. Путь и формат служебного файла; временной области, резервной копии и журнала
   восстановления. Временное состояние не должно смешиваться с обычной поставкой.
4. Состояния операции и точка фиксации; восстановление при прерывании между
   отдельными файловыми действиями, в том числе во время самого восстановления.
   Уточнить применимость восстановления к первой установке и удалению, а также
   отсутствие установки при `update` и повторное `uninstall`.
5. Защита от двух одновременно запущенных установщиков в одном проекте;
   выбор точной области OpenCode, включая существующие варианты `skill(s)` и
   `command(s)`, и исключение остающихся альтернативных пакетных копий.
6. Проверка целевого корня, симлинков и пересечений временной области с рабочими
   файлами; сохранность файлов вне управляемой области. Для источника RIS особенно
   важно не перепутать `skills/` с `.opencode/skills/`.
7. Поддерживаемая версия/возможности OpenCode и проверка обнаружения размещённых
   файлов. Текущая документация и историческая версия из README — разные основания.
8. Минимальные детерминированные seams для файловых отказов/прерываний, проверки
   обеих ОС, состава выбранного коммита и самостоятельного bootstrap. Инструкции
   агентов проверяются ревью, без поведенческих агентских тестов.

## Дальнейшая подготовка

После публикации требований и решения завершить полный дизайн с указанными
решениями и отдельно принять его. Затем определить достаточный состав работ
и зависимости в Beads. Не создавать искусственные задачи по числу слоёв или
файлов; одна задача реализации допустима, если она даёт весь проверяемый результат.
Реализацию запускать отдельным согласованным поручением.
