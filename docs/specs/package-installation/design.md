## 1. Исходное состояние и ответственность

Baseline: `77520fadff989423d2de754219f9523bc166ed25`. В проекте есть исходные
`skills/`, `commands/opencode/` и установленные `.opencode/skills/`,
`.opencode/command/`; автоматического установщика нет. README и карта
`docs/rules/architecture/repository.md` различают исходники и копии.
Полная all-state выборка Beads: 40 task, 2 SDLC epic; иной активной поставки
установки и общего несовместимого контракта не найдено. Product-вход — решения
интервью, а не отсутствующий docs/product/. Фактические правила не меняются
под будущую архитектуру; после реализации карта и README синхронизируются.

Единственный файловый механизм — самодостаточный
`skills/ris-manage-installation/scripts/ris-install.sh`. Он не загружает
ресурсы соседних скилов, не читает ris.yaml, не вызывает bd/OpenCode.
Скил управляет намерением/параметрами и проверенным сообщением; `/ris-manage`
только загружает скил и передаёт `$ARGUMENTS`. README объясняет bootstrap,
не содержит второго установщика. Отдельная portable база не нужна.

## 2. Зависимости и CLI

Runtime: Bash 3.2+, Git 2.20+, `flock`, стандартные Unix-утилиты
`cp`, `mv`, `rm`, `mkdir`, `mktemp`, `tar`, `cmp`, `diff`, `id`.
Без GNU-only ключей, jq, Python или пакетного менеджера во время работы.
На Linux flock предоставляет util-linux; на macOS — пакет Homebrew `flock`
(discoteq/flock 0.4.0). Недостающие зависимости только сообщаются, не ставятся.
`curl` нужен лишь для первоначального скачивания скрипта по README.

```sh
bash <script> install --project /absolute/project [--ref <tag-or-full-commit>]
bash <script> update --project /absolute/project [--ref <tag-or-full-commit>]
bash <script> uninstall --project /absolute/project
```

`--project` обязателен; существующий каталог разрешается в физический корень,
аргументы и имена с пробелами передаются раздельно/в кавычках. Git-репозиторий
цели не обязателен. Harness v1 фиксирован: OpenCode, флаг выбора пока не нужен.
`--ref` — точный тег или полный 40-hex SHA, не произвольное Git-выражение/ветка;
отсутствие означает remote HEAD, не жёстко заданное `main`. Hex-тег при совпадении
с синтаксисом полного SHA трактуется как SHA. `uninstall --ref` — ошибка.
Неизвестные/повторённые аргументы — ошибка до изменения установки.

Код 0 означает проверенный результат и завершённую уборку; ненулевой — ошибка
или незавершённая уборка. Сообщение всегда различает: не изменено, восстановлено,
нужно повторить восстановление, применено/уборка не закончена. На успехе
выводятся операция, физический корень, источник, полный SHA (кроме удаления),
число скилов/команд и напоминание перезапустить OpenCode. JSON API не вводится.

`install` полностью заменяет и существующий пакет. `update` требует служебный
файл либо хотя бы один управляемый элемент старой ручной установки; иначе
выход с предложением `install`. Повторный `uninstall` без установки — успешный
no-op, сеть не нужна. Все операции сначала обслуживают незавершённую транзакцию.

## 3. Получение единой ревизии и bootstrap

Фиксированный источник: `https://github.com/atilla777/ris.git`; публичного
`--source` нет. Во временном каталоге вне цели выполняется Git clone без checkout.
Из clone фиксируется remote HEAD либо точный тег с разрешением annotated tag,
либо проверенный полный SHA commit-объекта; всё дальнейшее читается по этому SHA.
Проверка не опирается на повторное чтение изменяемого тега/ветки. Не выполняются
код/хуки пакета, инициализация submodule или установка зависимостей скилов.

Из Git tree берутся все `skills/ris-*/` целиком и
`commands/opencode/ris-*.md`. Проверяются полные каталоги с SKILL.md и
совпадающим именем, обычные файлы/каталоги, отсутствие submodule и симлинков,
наличие скила управления, команды и самого установщика. Данные staging должны
совпасть с tree/manifest выбранного SHA, включая executable bits скриптов.
Служебное состояние создаётся самим установщиком, не берётся из чужого проекта.
Неизвестный/неполный старый commit без средств управления отвергается до замены.

README даёт скачивание этого же скрипта с GitHub raw во временный файл, проверку
успеха загрузки и запуск Bash с явным `--project`; не `curl | sh`. Для pinning
используется raw URL того же SHA/тега и `--ref`; по умолчанию bootstrap получает
скрипт основной ветки, а installer фиксирует актуальный remote HEAD.
Версия выполняющего движка и устанавливаемого комплекта могут различаться при
update/pinning; служебный SHA всегда описывает комплект. Неподдерживаемый формат
восстановления останавливает запись, bootstrap README остаётся доступен.

До изменения собственных файлов установщик делает исполняемую временную копию
самого себя вне цели и продолжает из неё; внутренний переход выполняется один
раз. После этого ни один шаг не зависит от установленного script/skill.
Это обеспечивает завершение update/uninstall, затрагивающих самого установщика.

## 4. Область управления и состояние

OpenCode-specific функции только перечисляют managed paths и отображают
staging в целевые каталоги; получение Git, transaction/rollback общие.
Это функции одного скрипта, не новая система plugins/adapters.

Управляемые элементы верхнего уровня:

- `.opencode/skills/ris-*` — каталог скила целиком, включая старую ссылку
  на такой каталог; совпадающий объект неправильного типа блокирует замену;
- `.opencode/command/ris-*.md` — файл команды или ссылка на него;
- `.opencode/ris-installation` — служебный файл.

Новая установка пишет только `.opencode/skills/` и `.opencode/command/`.
Сторонние элементы и сами непустые родительские каталоги не удаляются.
Альтернативные `skill/`, `commands/`, глобальные, родительские, `.agents/`,
`.claude/` и config-defined пути не меняются;
скил сообщает о известном затенении вне области, а не исправляет его скрыто.

Служебный файл — простой текст фиксированной схемы:

```text
format=1
source=https://github.com/atilla777/ris.git
revision=<full-40-hex-commit>
harness=opencode
```

Парсится как данные, никогда не `source`/`eval`. Не хранит абсолютных путей,
перечня принадлежащих файлов, времени или отдельной истории установок.
Установленные файлы и этот файл доступны Git, игнорирующие правила не меняются.
Уже существующее внешнее игнорирование не обходится `git add -f`: вывод содержит
подсказку проверить обычный `git status`, а установщик не выполняет Git цели.

Корень `.opencode` и два управляемых каталога должны быть обычными
каталогами, не симлинками. Старый managed элемент может быть симлинком: он
копируется как ссылка без разыменования и удаляется как ссылка; его внешний
target не затрагивается. Вложенные ссылки старого пакета также не обходятся.
Спецфайлы и невозможность безопасного backup блокируют замену до удаления.
Для успешно восстановленного состояния сравниваются типы, содержимое и modes,
а не inode, ctime, ACL или extended attributes; последние v1 не переносит.

## 5. Сериализация и журнал

Один OS-user и один физический root обслуживаются одним движком одновременно.
Kernel advisory lock через `flock -n <fd>` освобождается при завершении процесса,
включая SIGKILL, без PID-lock/stale-break протокола. Второй запуск с занятой
блокировкой сообщает busy и ничего не меняет.

Файл lock находится вне проекта: `/tmp/ris-install-locks-<uid>/<key>.lock`,
key = Git hash физического абсолютного пути root. Каталог private (0700),
проверяется принадлежность текущему uid и отсутствие подмены ссылками; lock не
удаляется на выходе, чтобы не создать второй inode для того же root. Это пустой
служебный lock, не история backup и не файл проекта. Защита распространяется
на cooperating installer processes этого OS-user на локальной машине;
сторонние правки пакета во время операции не поддерживаются.

Журнал и единственный backup: `.opencode/.ris-install-transaction/`.
Каталог private, не ссылка, схема 1; неизвестное/повреждённое состояние
сохраняется, зависимая операция останавливается с его точным путём.
Перед первой модификацией установки снимается snapshot всех managed элементов
и служебного файла с учётом отсутствующих элементов. Список managed paths
валидируется относительно двух фиксированных родителей и одного служебного
файла, не исполняется.
Backup копируется без dereference; оригиналы до его готовности не перемещаются.

Состояния/маркеры публикуются temp+rename на той же файловой системе:

| Состояние | Действие следующего запуска под lock |
|---|---|
| journal отсутствует | Обычная операция |
| snapshot строится, `prepared` ещё нет | Установка не менялась; удалить неполный snapshot |
| `prepared`, нет `committed`/`rolled-back` | Восстановить snapshot до нового запроса |
| `committed` | Результат уже применён; закончить уборку, не откатывать |
| `rolled-back` | Прежний результат уже восстановлен; только закончить уборку |

После ready snapshot ставится `prepared`; только затем удаляются все managed
элементы, копируется новый комплект и атомарно записывается версия (для удаления
новый набор пуст). Проверяется весь результат и неизменность чужих файлов;
после успешной проверки ставится `committed` — это точка фиксации. Затем backup
удаляется. Если уборка прервана, терминальный маркер удаляется последним, чтобы
следующий запуск никогда не принял частично убранный backup за восстанавливаемый.

До committed любая обнаруженная ошибка вызывает rollback: удалить текущие
managed элементы, скопировать неизменяемый snapshot обратно, проверить результат.
Backup не расходуется перемещением. Повтор rollback после его прерывания
даёт то же прежнее состояние. После полной проверки атомарно ставится
`rolled-back`; только затем разрешено удалять backup/journal, причём
`rolled-back` убирается последним. При прерывании этой уборки повторного
восстановления из частично удалённого backup нет. Одновременные committed
и rolled-back — повреждение журнала, не угадываемый успешный результат.
Первая установка восстанавливается к отсутствию пакета, удаление — к прежнему
пакету. Ошибка rollback оставляет backup/journal; новый запрос не начинается.

SIGINT/SIGTERM/обычные ошибки обрабатываются явно, не только `set -e`.
SIGKILL не ловится: первый следующий запуск, получивший lock, исполняет таблицу
восстановления до сети и нового install/update/uninstall. При восстановлении
полностью удалённого executable пользователь применяет README bootstrap.
Движок использует локальную поддерживаемую схему без сети; текущий сценарий
не гарантирует работу после потери/порчи носителя или crash ОС с незафиксированными
записями. Процессные прерывания на работающей FS входят в контракт.

## 6. Проверки до разбиения задач

Это план свидетельств, не результаты ещё не реализованной поставки.
Файловые тесты работают с временными проектами и двумя Git fixture-ревизиями
с разным составом/ресурсами, annotated tag и executable script.
Тестовый Git shim перенаправляет только фиксированный upstream URL на fixture;
публичный CLI не приобретает `--source` или fault-injection flags.
Fault shims файловых утилит задают ошибку/контролируемую остановку на границах.

| Seams / oracle | AC |
|---|---|
| Реальный CLI: пустой проект → целый Git-tree комплект; default HEAD, tag, SHA; состояние/байты/modes совпали | 001, 002 |
| Повтор/ручной пакет/локальная правка/две ревизии → точный новый набор в управляемой области, выбывшее отсутствует | 003, 004, 005 |
| Sentinel сторонних навыков/команд/config/docs/ris-* вне области, в т.ч. skill/ и commands/, внешние targets старых ссылок → типы/байты неизменны | 006, 015 |
| Git/fetch/validation отказ до prepared → прежний набор и version без изменений | 007 |
| Отказ после prepared, частичной замены и до commit marker → byte/mode-equivalent snapshot; отказ rollback сохраняет backup и ненулевой exit | 008 |
| SIGKILL после prepared/частичной замены, затем новый CLI; SIGKILL во время rollback → сначала старый snapshot, затем запрос | 009 |
| Kill до prepared, после committed/rolled-back и при обеих cleanup; отсутствие backup после успеха, повтор uninstall, rollback install/uninstall | 010, 011 |
| CLI из временного self-copy удаляет/обновляет исходный script; lock contender busy, после SIGKILL lock снова доступен | 008–011 |
| Одни файловые сценарии в Linux и macOS CI с GNU/BSD userland, Bash 3.2-compatible синтаксис и обе реализации flock | 012 |
| Чтение SKILL/команды/README, source/install parity, единственный script, инструкции без ris.yaml/bd/побочных инициализаций | 013, 014, 015 |

В каждый файл-тест включаются отсутствие ложного успеха и сохранность sentinels.
Не нужна декартова матрица всех ошибок на каждом файле: обязательны перечисленные
фазовые границы, interrupted rollback и обе терминальные cleanup. Test harness может
использовать Python stdlib как dev-only средство, не runtime-зависимость.
Код реализуется TDD. Поведение агентов не тестируется; инструкции проверяются
чтением и независимым ревью. macOS check нельзя заменить Linux-результатом.
CI запускает только детерминированные файлы/CLI, не OpenCode-сессии.

## 7. Совместимость и влияние

Целевой проверяемый discovery-контракт — OpenCode 1.18.33. Текущая документация
Skills описывает skills/, Commands показывает commands/; pinned upstream
`v1.18.33/packages/opencode/src/config/command.ts` явно читает
`{command,commands}/**/*.md`. Поэтому согласованный command/ сохраняется.
Совместимость иных версий/клиентов не объявляется автоматически. Discovery
проверяется чтением pinned loader и размещения/frontmatter, без живого агента.
При обнаружении изменения loader требуется точечная корректировка дизайна.

Источники, прочитанные 15.10.2026:

- https://opencode.ai/docs/skills/
- https://opencode.ai/docs/commands/
- https://raw.githubusercontent.com/anomalyco/opencode/v1.18.33/packages/opencode/src/config/command.ts
- https://formulae.brew.sh/formula/flock (macOS package 0.4.0).

Публичные решения — CLI, схема version/journal, namespace. Они локальны новой
фиче и фиксируются этим design.md: отдельный ADR не нужен, независимое review
обязательно. Выбраны Git вместо GitHub API/curl-archive (один способ получения
ревизии), flock вместо PID-lock (надёжный restart ценой одной macOS-зависимости),
копируемый snapshot вместо rename-only backup (повторяемый rollback).
Полного будущего harness API нет. Инициализация, автоматический update,
global cleanup, выборочная установка и Git-публикация самим installer исключены.
