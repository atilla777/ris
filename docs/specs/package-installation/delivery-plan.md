# package-installation — декомпозиция P1

Статус: декомпозиция по отдельно принятому D1, сохранена 15.10.2026.
Разрешение: поручение пользователя довести до декомпозиции и затем опубликовать.
Входы: требования v1 `docs/specs/package-installation/spec.md`, AC-001–015,
отдельное решение [acceptance.md, «Требования v1»](acceptance.md#требования-v1);
принятый [design.md](design.md) и отдельное решение
[acceptance.md, «Дизайн D1»](acceptance.md#дизайн-d1).
Реализованного установщика/management skill нет; нынешние source/install копии
и источники команд — существующая база, их не нужно создавать повторно.

## Контейнер поставки

Самостоятельный обычный task «Устанавливать, обновлять и удалять RIS в OpenCode»,
slug package-installation, без искусственной привязки к SDLC-эпикам. `ris-0pr`
остаётся подготовкой, а не переименовывается в реализацию. Stable delivery key:
`ris:package-installation:delivery:v1`. Под ним — два результата ниже.
Это project-specific задачи Beads, не объявление ris.feature-record/1 с ещё
неопубликованными refs. После публикации документы и реальные SHA должны быть
доступны исполнителю без этого чата и локальных файлов.

## W1. Управлять полным жизненным циклом пакета через один CLI

**Результат:** самодостаточный shell-установщик, README bootstrap для человека
или агента до RIS и детерминированные файловые проверки Linux/macOS. Через CLI
доступны первая/повторная/ручная установка, выбор HEAD/tag/SHA, полная замена,
удаление, self-update/uninstall, rollback/resume и single-writer lock.

**Область:** script в будущем скиле управления (пока как runtime source),
детерминированный test harness/fixture, минимальный OS CI, соответствующая
README bootstrap/CLI/deps секция. До W2 пакетный тест использует fixture с
полным минимальным скилом управления и командой: текущий исходный репозиторий
ещё не содержит их, поэтому W1 не объявляет production bootstrap принятым.
В W1 нет агента/команды, ris.yaml, Beads-интеграции или проектной инициализации.

**Контракты:** D1 §§2–5; фиксированный upstream, CLI, schema=1 version/journal,
управляемые пути и flock, snapshot и commit point. Test seams D1 §6.
Stable key после подтверждения контейнера: `ris:package-installation:<ID>:v1:W1`.

**Критерии:** TDD и реальные CLI-файловые результаты подтверждают
`package-installation#AC-001–012`, `#AC-014` в bootstrap/CLI-части и `#AC-015`.
Сравниваются полный набор/байты/modes/SHA; сторонние sentinels не меняются;
ошибки/прерывания и повторный rollback не теряют snapshot, busy lock не пишет;
нет постоянной истории backup и ложного успеха. Проходы обеих ОС обязательны,
инструкции README проверяются чтением/независимым review, не живым агентом.
Acceptance production-пакета остаётся за общим проверенным snapshot W2.

## W2. Предоставить установленное управление пакетом в OpenCode

**Результат:** пользователь вызывает `/ris-manage` или скил
`ris-manage-installation` и получает корректные инструкции запуска единственного
W1 CLI, работающие без инициализации RIS, включая обновление/удаление самого себя.

**Область:** SKILL.md, только необходимые условные resources, тонкая
`commands/opencode/ris-manage.md`, синхронные `.opencode` копии, README
интерфейс/перезапуск и актуальная карта архитектуры после реализации.
Применить авторские методы RIS для source skill и customize-opencode для
установленных инструкций/команды. Второй механизм установки, новая portable
база, автоматическая инициализация и тесты поведения агента исключены.

**Контракты:** D1 §§1–4, 7, W1 CLI; команда передаёт `$ARGUMENTS`; редкие
ошибки/прерывания не заставляют загружать весь SDLC процесс и адаптеры.
Stable key после подтверждения контейнера: `ris:package-installation:<ID>:v1:W2`.

**Критерии:** чтение и независимое review покрывают `package-installation#AC-013`,
`#AC-014` и инструкционную часть `#AC-015`; source/install parity и доступность
вложенного script/ресурсов. На одной интегрированной revision с реальными
скилом/командой выполнить детерминированный CLI lifecycle и сверку manifest
W1 применительно ко всему пакету: состав, точный SHA, self-update/uninstall,
сохранность чужих файлов, восстановление и отсутствие скрытой инициализации.
В отчёте AC-001–015 указать применимые результаты W1 и затронутые перепроверки
на итоговом snapshot; не повторять все фазовые тесты без изменений механизма.
Не выдавать статическое review инструкций за live-agent наблюдения.

## Связи, полнота и общий результат

Направленный blocker: **W2 → W1**, потому что инструкции управления и проверка
production-пакета требуют конкретного готового CLI/recovery-контракта. Draft
текста W2 возможен раньше, но весь проверяемый результат — после W1.
Иных blocker/связей с SDLC-эпиками нет, циклов нет. Parent-child — только
принадлежность контейнеру и не дублируется blocks.

Два результата обоснованы: W1 пригоден для ручного/README использования и
независимо проверяет рискованный файловый механизм на fixture; W2 добавляет
пакетный агентский вход и проверяет реальную совместную поставку. Делить install,
update, uninstall и recovery на отдельные задачи нельзя: они один протокол
данных. Отдельных задач на тесты, review, docs или приёмку нет.

| Покрытие | Владелец |
|---|---|
| AC-001–012 | W1 механизм и OS-checks; W2 применимость к реальному комплекту |
| AC-013 | W2 skill/command/единственный runtime |
| AC-014 | W1 bootstrap/deps/CLI, W2 полный вход/перезапуск и совместная сверка |
| AC-015 | W1 файловые sentinels, W2 инструкции и общий snapshot |

Все 15 требований охвачены; D1 принят отдельно, контрактных пробелов нет.
Окончательные design/decision/decomposition проходят финальное review. По поручению
«потом публикуй» Git-публикация следует после подготовки декомпозиции, затем
создаются задачи с действительными опубликованными ссылками и публикуется Dolt.
Реальные ID проверяются в Beads по stable key контейнера и W1/W2, не
выдумываются заранее и не требуют второго файлового реестра. Готовность
конкретного task проверяется по опубликованным входам и текущим blockers.
Git push не закрывает контейнер реализации; ris-0pr завершается отдельно после
результата подготовки. Запуск W1/W2 — только отдельным поручением пользователя.
