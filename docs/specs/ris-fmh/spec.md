Keywords: prepare-feature, auto, compact, full, one-task

Это спецификация будущего изменения, не уже установленной возможности.
Поручение 26.10.2026 разрешает анализ, подготовку документов/плана Beads,

## Требования S1

### Цель и входы

RIS тратит на подготовку ресурсы, соразмерные сложности разработки, сохраняя
достаточные входы и качество. Расширяется существующий
`ris-proj-flow-prepare-feature`, не создаётся другой сквозной workflow.
Compact — подготовка продуктовой фичи, в том числе меняющей продуктовую логику,
не обход ограниченного допуска Fast.

Поддерживаются три входа:

1. Существующий Feature ID, в том числе предварительная фича из Roadmap.
2. Подтверждённый Epic ID + выбранная новая идея: регистрация внутри этого эпика.
3. Выбранная самостоятельная идея: регистрация непосредственно в Beads без
   обязательного эпика и предварительного Roadmap.

Если цель ещё не выбрана, сохраняется существующая read-only помощь в выборе;
явно выбранная новая идея не перенаправляется обязательно в планирование эпика.
Перед регистрацией сверяются относящиеся записи во всех состояниях, включая
возможные совпадения вне указанного эпика. Совпадение переиспользуется с тем же ID;
неоднозначность/конфликт не считается отсутствием. Известный ID не создаётся снова.
Closed/started/foreign записи не переоткрываются, не переносятся и не переписываются
автоматически. Ранней регистрации достаточно title/краткой цели и устойчивой
retry identity; spec/design/AC/эпик ещё не обязательны.

### Глубина подготовки

- `auto` по умолчанию, `compact` или `full`. Явное указание человека приоритетно;
  старый вызов без режима означает `auto`. Неизвестное/противоречивое указание
  уточняется, не заменяется молча. Это параметр поручения, не новое поле/статус
  Beads и не новая настройка конфигурации.
- Auto выбирает Compact, когда результат достаточно определён и разумно
  исполняется одной работой. Учитываются определённость требований, принятые
  product/rules/архитектура, готовые механизмы движка/библиотек, независимые
  результаты, масштаб/архитектурный риск и координация исполнителей.
  Full выбирается по конкретным основаниям для дополнительного проектирования,
  разбиения или координации, не по наличию нового пакета, числу файлов или
  изменению продуктовой логики как таковому.
- Explicit Compact не позволяет скрыть существенную неопределённость или риск.
  Агент называет конкретный пробел и последствия и согласует только необходимое
  расширение; не переключается молча на Full и не перезапускает подготовку.
  Пригодные ID/copy/ответы/документы/решения сохраняются. Небольшое уточнение
  само по себе не требует Full. Явный Full не понижается.
- Выбор встроен в обычное чтение входов/диалог. Нет агента-классификатора,
  отдельного этапа оценки, балльной матрицы или промежуточного артефакта.
  Причина глубины кратко сообщается, не становится readiness gate.

### Compact и Full

Compact использует существующие `sources.product`, `sources.rules`, принятые
решения, актуальный код и проверенные возможности фреймворка/библиотек.
Вопросы — только по существенным пробелам; готовые механизмы не проектируются заново.
Достаточный `spec.md` содержит цель, границы/исключения, необходимое наблюдаемое
поведение, AC с how-to-check, новые решения и краткий технический подход в отдельной
различимой области. Применимые контракты цитируются вместо пересказа архитектуры.
`design.md`/ADR создаются только когда добавляют полезную информацию, не ради формы.
По умолчанию исполняемая единица — сама фича Beads без детей; объективная
необходимость самостоятельных результатов разрешается по общему принципу ниже,
не обходится запретом на детей или скрытым переключением глубины.

Full сохраняет полноценную существующую методику: по необходимости глубокий
диалог, достаточное проектирование, весь состав результатов/связей и координацию.
Full не означает обязательную длинную анкету, design.md или детей: достаточность,
не заполнение разделов, определяет объём.

В обеих ветках сохраняются независимо достаточные requirements/design scopes,
direct/inherited/mixed/policy основания и scope-specific explicit approval overrides.
`auto` глубины **не равен** `workflows.prepare_feature.auto_accept`: boolean
управляет принятием, не глубиной. Независимое review полного финального snapshot,
затронутые проверки, claim/ownership, одна safe own copy до writes, native guards/
non-force, Git → same-ID reconciliation → verified composition → отдельная Dolt
сохраняются. Результат пригоден существующему execute-task; prepare не начинает
реализацию и не закрывает работу. TDD/review/publication/completion исполнения неизменны.

### Декомпозиция в обоих режимах и прямом вызове

**Дочерняя задача — самостоятельный проверяемый результат, не технический шаг.**
Сначала рассматривается one-task feature. Разбиение требует содержательного
обоснования: независимые результаты, значимые зависимости между ними, необходимая
параллельная работа либо чрезмерный для одного исполнительского контекста объём.
Нет лимитов количества детей, порогов строк/файлов или обязательного отчёта;
основание split достаточно дать в существующем результате операции.

Установка пакета, конфигурация, подключение API, тесты и прочие последовательные
действия одного исполнителя не становятся отдельными задачами лишь из-за своей
технической природы. Самостоятельная инфраструктурная/миграционная/исследовательская
единица допустима при собственном проверяемом результате и объяснённой необходимости,
не как переименованный этап той же работы. Тесты/combined check принадлежат
соответствующему результату и сами по себе не требуют отдельной задачи.

One-task использует Feature ID без дублирующего ребёнка. Проверяются достаточные
scope/criteria, весь фактический all-status child set и directed blockers.
Multi-task сохраняет coverage всех AC, own outcomes/contracts/seams, назначенное
место combined check и лишь необходимые directed blocks без циклов.
Очевидное разбиение не перепринимается; material scope/delivery/obligations — человеку.
Существующие дети не удаляются ради компактности, native refusal не обходится.

### Совместимость и recovery

Roadmap/plan-epic-features остаются владельцами предварительных эпиков/фич,
не получают обязательного выбора Compact/Full и не становятся гейтом standalone
идеи. Существующие фичи/эпики/принятые документы/решения сохраняются без миграции
и маркера режима/готовности. Direct specify/design/decompose сохраняют scoped результаты.
Resume восстанавливает реальные документы/basis/copy/graph/публикации; новое явное
указание глубины приоритетно, иначе доступное прежнее поручение либо auto по текущим
фактам. Переоценка не отменяет принятого, не уменьшает обязательный состав и не
повторяет подтверждённые эффекты. Нет новых skills/roles/states, JSON-реестров,
workflow-журналов, обязательных metadata/служебных файлов или дублирующей методики.

### Критерии приёмки и how-to-check

Инструкции проверяются чтением/diff и независимым review; условия ниже — предмет
содержательного review, **не сценарии запуска тестовых агентов**.

| Критерий | Проверяемый результат и способ проверки |
| --- | --- |
| AC-001 | Проследить три входа: existing ID без дубля; Epic ID + идея с проверенным родителем; standalone без эпика/Roadmap. Прочитать all-status dedup/reuse/conflict/early-minimum ветки и соответствие native task adapter. |
| AC-002 | Проверить default auto, explicit compact/full, ошибочный режим и отличие от boolean auto_accept. Нет новой config/tracker schema; explicit full сохраняется. |
| AC-003 | Из достаточных требований/готового механизма следует Compact; из конкретного риска/координации — обоснованный Full. Explicit Compact при пробеле требует причины/минимального согласуемого расширения, без скрытой эскалации, классификатора или артефакта оценки. |
| AC-004 | Compact требует лишь sufficient spec с AC/how-to-check и independently selectable inline approach; переиспользует product/rules/code/framework. Нет обязательной анкеты/design.md/ADR или изобретения готового механизма. Full сохраняет нужную глубину без квот. |
| AC-005 | Portable/project decomposition применяют independent-result/one-task-first для обеих глубин/direct calls. Нет step-only задач/лимита детей; real split обоснован, coverage/combined check/necessary edges и существующий состав сохранены. |
| AC-006 | Оба результата сохраняют прежние acceptance/review/copy/ownership/check/Git/same-ID/Dolt gates и подходят execute-task без его изменения; prepare не реализует и не закрывает. |
| AC-007 | Partial/resume после документов, Git, reconciliation и частичного состава делает только остаток, сохраняет ID/basis/foreign work. Старые достаточные фичи не требуют mode/readiness marker/миграции. |
| AC-008 | При известных требованиях i18next + небольшая Phaser 4 игра выводятся одна standalone feature, короткий spec/approach/AC; без искусственного эпика/design.md/детей «пакет → config → API → tests». Проверить выводимость из инструкций; не устанавливать библиотеку и не утверждать проверенную совместимость конкретных версий. |
| AC-009 | Source owners, затронутые commands/help/catalog/product/rules и установка согласованы в этой поставке. Нет нового workflow/набора Compact skills/states/files/metadata. Affected static/link/dependency/parity checks и independent review полного integrated snapshot; обычные программные тесты/TDD — если меняется исполняемая программа. |

Численная экономия времени/токенов не заявляется без наблюдений. Сокращение
предписанного процесса при достаточных входах не является runtime benchmark.

## Дизайн D1

Существующий prepare — единственный владелец глубины и combined result.
Обычные аргументы поручения содержат optional depth `auto|compact|full`;
новой настройки ris.yaml/dispatcher нет. Выбор и пересмотр происходят в текущем
авторском контексте при исследовании достаточности входов. Три input routes
сводятся к одному confirmed ID через limited registration specify и adapter.
ID/epic/duplicate conflict останавливает dependent write, не создаёт замену для
обхода closed/ownership/prerequisites.

Далее обе глубины применяют одних owners: requirements formulation/save,
sufficient design/save, review, publisher, same-ID reconciliation, decomposition.
Различаются объём содержательной проработки и условные ветки. Compact — не новый
split-алгоритм: existing decomposition owner сначала проверяет sufficient one-task
outcome и фактический child/blocker set. Полный multi-unit метод применяется при
обоснованной необходимости либо существующем составе, требующем сверки.
Coverage и native safety не условны. Portable partitioning остаётся у
`ris-port-op-decompose-feature-spec`, project wrapper интегрирует реальные записи,
не копирует метод. Полный necessary состав проверяется даже при коротком пути.

Common published-inputs владеет acceptance/discovery/recovery; context/copy/Git/
Beads/Dolt algorithms остаются у нынешних owners. Новый portable base для project
orchestration и Compact-набор скиллов не нужны. Редкие углубления читаются условно,
не создают обязательный дополнительный пакет загрузки. Depth method — у flow,
partitioning — у portable decomposition; docs объясняют, не копируют алгоритмы.

Будущая единая поставка включает необходимые source edits existing owners,
`commands/opencode/risp-prepare-feature.md`, затронутые help/catalog/README/product/
rules/AGENTS и source/install synchronization. Процесс execute-task не меняется;
совместимость проверяется чтением его текущих one-task/inline-basis входов,
не новым режимом исполнения. Beads adapter не меняется только ради глубины;
расширение без конкретного дефекта не планируется. Программные валидаторы меняются
лишь при реально затронутом программном контракте, не для симуляции поведения агента.

Combined check всех AC-001–009 на одной integrated revision принадлежит самой
`ris-fmh`: inputs → depth/escalation → spec/approach → one-task/justified split →
unchanged execution inputs → partial/resume, включая command/help и parity.
Самостоятельных результатов для задач «документы», «тесты», «синхронизация» нет.
Разбиение этой поставки не нужно: один ограниченный контракт существующей подготовки,
понятные владельцы и одна combined check, без необходимой параллельной координации.
Единица исполнения — сама feature, без детей/новых blocks; порядок технических
правок выбирает будущий исполнитель, отдельный implementation plan не требуется.
