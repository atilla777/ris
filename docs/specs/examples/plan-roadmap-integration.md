# Пример прикладного скила: ris-plan-roadmap

[Оглавление](../README.md)

Документ задаёт самодостаточный ориентир реализации прикладного скила roadmap после автора скилов. Он сохраняет согласованную методику roadmap и показывает её связь с общей архитектурой. Это не автоматически установленный скил и не требование изменить существующий файл без отдельного задания.

## 1. Назначение и граница

Получить компактный roadmap проекта до выбранной цели: основные результаты, границы MVP, ограниченные эпики, зависимости и рекомендацию следующего эпика.

Не формировать подробные задачи реализации всех фич, не выбирать заранее все технические решения, не создавать второй трекер, не назначать исполнителей и не начинать реализацию.

Для уже готовой спецификации одной фичи с запросом на задачи нужен другой скил, а не roadmap проекта.

## 2. Входы и подготовка

`ris-context` готовит нужные каталоги `sources.concepts`, `sources.rules`, при необходимости `sources.specs` из defaults либо проектного `ris.yaml`. Проектная конфигурация не сливается с defaults; пути нельзя переопределять в задании. Конкретную концепцию скил выбирает из входов и связей документов. Эпики roadmap являются результатом в трекере, а не по настроенному пути файла. Для `update` потребитель читает существующие эпики через согласованный адаптер.

Входы задания: цель в `run.parameters.goal`, режим `create` или `update` в `run.parameters.mode` и разрешение записи в `run.write`. При отсутствии цели скил предлагает границы на основании контекста, отличая предложение от принятого решения.

Обеспечить `ris-common`, выполнить `ris-context`, прочитать выбранную концепцию и применимые правила. Для чтения/сохранения эпиков подключить действительно доступный адаптер задач по отдельному контракту; при его отсутствии зависимая операция блокируется. `ris-context` не осуществляет операции трекера и не доказывает существование адаптера. Назначения и статусы через этот скил не изменяются.

Наблюдаемое состояние продукта устанавливается по доступным подтверждениям, а не выводится из целевой концепции. При недостатке данных соответствующая часть roadmap помечается как основанная на допущении.

## 3. Предметная методика

### Шаг 1. Исходная точка и цель

Установить, что уже существует, какой результат нужен пользователю и какие ограничения существенны. Разделить факты, принятые требования, предложения и неизвестное.

При обновлении сначала сохранить понимание действующих идентификаторов и подтверждённых завершённых результатов. Не переопределять завершённый эпик задним числом ради красивого нового плана.

### Шаг 2. Сценарии и минимальные возможности

Выделить основные пользовательские сценарии и минимальный набор возможностей для выбранной цели. MVP должен быть связанным результатом, а не просто первым фрагментом полного списка пожеланий.

Отделить необходимое от следующего развития и явно указать исключения. Не включать инфраструктуру только потому, что она может пригодиться в будущем.

### Шаг 3. Первый небольшой сквозной результат

Найти минимальный проверяемый путь от действия пользователя до результата. Обосновать, какую неопределённость и риск он снимает. Для существующего продукта это может быть улучшение одного сценария, а не новый фундамент всей системы.

Не подменять сквозной результат горизонтальной очередью «сначала вся база, потом все API, затем весь интерфейс», если зависимости не требуют именно такого порядка.

### Шаг 4. Ограниченные эпики

Для каждого эпика определить полезный результат, область, существенные исключения и наблюдаемый признак завершения. Будущие эпики описывать крупнее; ближайший — достаточно для последующего уточнения.

Не превращать эпик в неограниченную тему «сделать систему» и не декомпозировать каждый до реализации отдельных файлов. Для исследовательского эпика результатом может быть снятая неопределённость с проверяемым заключением.

### Шаг 5. Зависимости и порядок

Различить обязательную зависимость и приоритет. Для зависимости пояснить, какой результат нужен следующему эпику. Проверить отсутствие циклов и опоры на несуществующие результаты.

Учитывать риск и стоимость поздней проверки предположений. Возможную параллельность обозначить как предложение при независимости результатов; она не означает автоматического запуска сессий.

### Шаг 6. Покрытие цели

Сопоставить сценарии выбранной цели с эпиками. Выявить пропуски, необоснованные эпики и скрытые исключения. Численные ограничения и запреты не смягчать при переносе.

Существенные нерешённые вопросы вынести в соответствующий раздел. Неблокирующее неизвестное не должно превращать весь roadmap в бесконечное интервью.

### Шаг 7. Результат и следующий эпик

Подготовить содержание эпиков roadmap, проверить его полноту и при разрешении сохранить через подходящий адаптер задач после проверки его операций. Рекомендовать следующий эпик с основанием выбора. Отдельно обозначить, готов ли он к уточнению; не объявлять его готовым к реализации только из-за включения в roadmap.

Остановиться до подробного workflow эпика, создания задач и кодирования.

## 4. Ориентир структуры результата

```markdown
# Эпики roadmap (пример структуры содержания, не шаблон отдельного файла)

## Цель и исходное состояние
## Границы MVP и исключения
## Первый сквозной результат
## Эпики: результат, область, критерий завершения
## Зависимости и предлагаемый порядок
## Открытые вопросы и допущения
## Рекомендуемый следующий эпик
```

Принятый формат трекера имеет приоритет над оформлением этого примера, если сохраняется требуемое содержание. Эпики принадлежат трекеру; не вести рядом независимые статусы в документах.

## 5. Сохранение и передача

Использовать выбранный и проверенный адаптер задач для операций с эпиками; не записывать запасной `ROADMAP.md` после ошибки трекера. Не менять `ris.yaml`. Этот пример не реализует адаптер или `ris-plan-roadmap`.

При разрешении только на эпики roadmap не изменять другие задачи, глоссарий, правила и код. Обсуждённые решения о составе и порядке эпиков должны быть отражены в их данных или доступных однозначных входах, на которые они ссылаются.

В режиме без записи выдать подготовленный текст и отметить, что он не сохранён в трекере. Предложение не выдавать за утверждённый план.

## 6. Проверка и риски

Проверить покрытие выбранной цели, границы эпиков, отсутствие циклов зависимостей, различение принятого и предложенного, сохранение значимых ограничений, адрес результата и допустимость изменений.

Типичный обход: «эпики очевидны, достаточно заголовков». Корректное действие: для каждого установить результат и проверяемую границу, не уходя в задачи реализации.

Признак нарушения: план состоит только из технических слоёв без наблюдаемых результатов. Реакция: пересмотреть разбиение по сценариям либо обосновать необходимые технические предшественники.

Признак нарушения: рекомендации уже породили назначения в трекере. Реакция: остановить расширение области, сообщить реальные изменения и не скрывать их за отчётом о roadmap.

## 7. Примеры задания

```text
Используй ris-plan-roadmap. Изучи выбранный проект и предложи roadmap
до MVP для собственного использования. Файлы и задачи не изменяй.
```

```text
Используй ris-plan-roadmap. Актуализируй эпики roadmap по текущей концепции
и подтверждённому состоянию проекта. Сохрани только эти эпики через
настроенный адаптер. Не меняй конфигурацию, другие задачи и код.
```

Это естественно-языковые задания, не специальные команды среды. Они используют один скил с разными разрешениями.

Приёмка будущего скила охватывает создание и обновление в двух проектах через адаптер, режим без записи, сохранение идентификаторов, отсутствие резервного файла и остановку перед следующим этапом. Эти проверки не являются приёмкой `ris-context`.
