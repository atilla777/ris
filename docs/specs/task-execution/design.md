## 1. Архитектура и владельцы

Поставляется **один сценарный скил `ris-execute-task` без новой переносимой базы**.
Он управляет одной задачей: выбирает цель, передаёт входы исполнителям,
проверяет переходы и отвечает за итог.

| Операция | Владелец |
|---|---|
| Выбор задачи, готовность, переходы, возобновление, итог | `ris-execute-task` |
| Подготовка настроек и путей | `ris-context` |
| Чтение задач, claim, защищённые записи, закрытие и публикация трекера | Выбранный адаптер |
| Подготовка или повторное использование копии | `ris-prepare-task-worktree` |
| Технический план | `ris-plan-task` |
| Кодовая реализация и исправления | `ris-tdd-implement-task` |
| Текстовая реализация | Маршрут из раздела 5 |
| Независимое ревью | `ris-review` |
| Интеграция и Git-публикация | `ris-publish-main` |
| Полная приёмка и закрытие выбранной однозадачной фичи | `ris-complete-container` |

**Границы состояния:**
- трекер владеет статусом, назначением, составом и зависимостями;
- Git владеет версиями содержания, решениями и опубликованным результатом;
- локальные отчёты содержат свидетельства операций, но не образуют вторую очередь.

Сценарий не копирует алгоритмы TDD, ревью, worktree или Dolt. Исполнители
загружают свои скилы и зависимости; ведущий получает короткие проверяемые результаты.

## 2. Роли исполнения

Предлагаются три явно настроенные роли в существующем `execution.roles`:

| Роль | Операции |
|---|---|
| `task-execution` | Исследование очереди и готовности, подготовка копии, планирование, публикация, завершение и tracker publication |
| `task-implementation` | Реализация кода или текста, исправления |
| `task-review` | Независимое ревью, включая изменённую интегрированную версию |

Схема `ris.yaml` v2 не меняется: она уже разрешает такие имена ролей.
Для этого репозитория предлагается привязать все три к доступному `general`;
независимость обеспечивает **разный фактически запущенный контекст**, а не
разное имя агента.

Перед первой мутацией проверяются необходимые для оставшегося маршрута роли,
доступность исполнителей и разрешения. Каждая самостоятельная неинтерактивная
операция запускается в субагенте. Ревью — свежий вызов, независимый от авторов
реализации и исправлений.

Ведущий сохраняет диалог, принимает решения о переходах и задаёт необходимые
вопросы. Отсутствующая роль блокирует зависимую операцию.

## 3. Выбор и принадлежность работы

Используется полная выборка задач всех состояний. Точная задача дополнительно
перечитывается перед действием.

**«Собственная работа» подтверждается совокупностью сведений:**
1. установлен actor текущего исполнения из явного входа или проверенного
   свидетельства предыдущего запуска;
2. назначение в трекере соответствует actor;
3. свидетельства связывают задачу с этим исполнением и фактической рабочей копией;
4. свежая проверка не обнаруживает чужого активного исполнения или противоречия.

Имя пользователя ОС, `owner` записи и ветка `task/<ID>` по отдельности
принадлежность не доказывают. Неоднозначное продолжение требует одного
необходимого решения пользователя.

Без аргументов:
- сначала рассматривается подтверждённая собственная незавершённая работа;
- несколько таких работ сортируются по приоритету, времени создания и ID;
- препятствие выбранной собственной работы останавливает запуск;
- при отсутствии собственной работы выбирается готовая задача с тем же порядком.

Для Beads меньшее числовое значение приоритета выше. Время сравнивается как
временная метка; ID — стабильным лексикографическим сравнением. Другой адаптер
должен предоставить однозначную семантику приоритета; неполные данные не
заменяются догадкой.

**Закрытая задача с незавершённой публикацией трекера** может представлять
собственное незавершённое исполнение только при подтверждённой связи и
фактическом остатке операции. Возобновляется проверка или публикация;
задача не переоткрывается.

Явный ID фиксирует единственную цель. Закрытый ID проверяется и получает
отчёт о состоянии; новый цикл реализации не начинается.

## 4. Готовность и последовательность

До начала реализации проверяются:
- согласованный результат, границы и критерии;
- принятый применимый дизайн либо достаточные принятые технические ограничения
  самостоятельной задачи;
- существенные входы и текущие контракты;
- статус, claim, направленные блокеры и обязательный состав;
- разрешения, исполнители и доступность маршрута публикации.

Для feature-linked работы проверяются опубликованные требования, дизайн и
отдельные решения через контракт адаптера. Исторический неподдерживаемый
feature record сохраняется и блокирует зависимое действие.

Связь с родителем и блокирующая зависимость рассматриваются раздельно.
Ограничения родителя оцениваются по проектным правилам; сценарий не создаёт
отсутствующую связь автоматически.

Последовательность проверяемых результатов:

```text
Выбранная готовая задача
→ подтверждённый claim и пригодная копия
→ актуальный план
→ проверенная реализация
→ независимое ревью и необходимые исправления
→ проверенная Git-публикация
→ проверка критериев, итог и закрытие
→ отдельно проверенная публикация трекера
→ отчёт и следующая рекомендация
```

Перед новыми пакетами изменений повторно проверяются владение и блокеры.
Claim не заменяет защиту конкурентной записи.

Результат исполнителя содержит: операцию, ID, область, версии входов,
адрес результата и evidence, фактические эффекты, ограничения и необходимое
решение. Непроверенное «готово» не открывает следующий переход.

## 5. Кодовые и текстовые задачи

**Код:** `ris-tdd-implement-task`; наблюдаемые ожидаемые RED и GREEN,
затронутые проверки и разрешённая синхронизация документации.

**Текст:** исполнитель `task-implementation` выбирает содержательного владельца:
- исходники скилов — `ris-author-skills` либо автономный `ris-author-skills-base`
  по границе задачи;
- синхронизация документации с реализацией — `ris-update-documentation`;
- разрешённая форматная операция над явно выбранным OKF-бандлом — проектный `ris-okf`;
- обычная ограниченная Markdown-правка без специализированного владельца —
  непосредственное редактирование по принятой задаче, плану и правилам проекта.

Последняя ветка проверяет содержание, критерии, ссылки, сохранность соседних
решений и итоговый diff. Она не формулирует новые требования или дизайн.
Все текстовые ветки сохраняют claim/current-copy guards, точную версию
результата и независимое ревью, **без искусственного RED**.

Классификация определяется воздействием изменения. Изменение поведения
исполняемого кода в смешанной задаче сохраняет обязательный TDD.

## 6. Ревью, исправления и прогресс

Каждый раунд сохраняет версию проверенного снимка, происхождение reviewer,
устойчивые ID замечаний и решения по ним.

- Высокие и средние замечания передаются на исправление, затронутые проверки
  и новое независимое ревью.
- Низкие получают зафиксированное решение; сами по себе новый раунд не запускают.
- Изменённый снимок требует применимого ревью.

Прогресс оценивается по устранённым причинам, новым проверенным фактам и
уменьшению обязательных нерешённых замечаний. Повтор той же проблемы без нового
обоснованного подхода вызывает диагностику причины; если продолжение невозможно —
частичный отчёт или вопрос. Фиксированного лимита раундов нет.

## 7. Свидетельства и возобновление

Используются существующие `worktree.md`, `plan.md`, `implementation.md`,
`review.md` и разрешённый локальный отчёт сценария — по умолчанию
`workspace.tasks/<ID>/execution.md`.

`execution.md` хранит идентифицированные наблюдения с сохранением истории:
- project/current/primary roots, actor и связь задачи с копией;
- версии требований, дизайна, правил и пакета;
- адреса результатов этапов и provenance исполнителей;
- снимок реализации, checks и применимость review;
- Git remote/ref/commit и проверку удалённой видимости;
- отдельные факты закрытия и публикации трекера;
- частичные эффекты и остаток операций.

Это журнал evidence, не авторитетный флаг «этап завершён».

При повторном запуске факты перечитываются и сравниваются со свидетельствами.
Продолжение начинается с первой незавершённой или утратившей применимость операции:
- изменённые существенные входы требуют проверки плана и затронутой реализации;
- изменённый снимок — checks/review;
- подтверждённый опубликованный Git-результат сохраняется при сбое закрытия или Dolt;
- неоднозначный push сначала проверяется удалённым чтением.

Отсутствие локальных заметок допускает восстановление из трекера, Git и
доступных отчётов. Недоказанный результат не считается выполненным;
прежний чат не обязателен.

## 8. Публикация и завершение

`ris-publish-main` получает полный проверенный снимок и независимое ревью.
Изменение интегрированного дерева требует затронутых checks и независимого
reassessment до push. Запрет прямой публикации останавливает этот путь.

После Git:
- **leaf task:** сценарий проверяет критерии и обязательный состав, затем
  поручает адаптеру отдельную запись итога и закрытие точного ID;
- **однозадачная фича:** `ris-complete-container` проверяет все AC на опубликованной
  интегрированной ревизии, сохраняет verification и отдельно закрывает выбранную фичу;
- **контейнер с незавершёнными детьми:** не исполняется целиком; выдаётся
  рекомендация подходящего ребёнка.

Для leaf-маршрута не требуется будущий `ris-complete-task`: достаточность
завершения принадлежит сценарию, инструментальная операция — адаптеру.
Родители не закрываются.

Защищённые записи требуют реально установленного короткого окна над изменяемой
записью, составом, блокерами и evidence. Публикация Dolt требует отдельного окна
финальной проверки исходящей истории и push. При отсутствии гарантии зависимый
эффект блокируется.

Адаптер проверяет весь разрешённый исходящий состав и независимо читает
отправленный snapshot из выбранного remote. Общий успех требует раздельных
доказательств Git, закрытия и tracker publication.

## 9. Покрытие критериев и проверочные границы

| AC | Проверка и наблюдаемый результат |
|---|---|
| 001–002 | Очередь с равными приоритетами, несколькими собственными работами, чужим claim и закрытым ID; ожидаемый ID и отсутствие подмены |
| 003–004 | Поочерёдное отсутствие принятого входа, наличие блокера/ребёнка; конкретная диагностика без начала реализации |
| 005 | Журнал фактических запусков; отсутствие роли блокирует мутации, reviewer независим |
| 006 | Реальная копия с чужими staged/unstaged/untracked изменениями; сохранность и подтверждённая связь с задачей |
| 007 | Реальные кодовая и текстовая задачи; RED/GREEN для кода, содержательные проверки текста |
| 008–009 | Существенное исправление, low-only и повтор без прогресса; правильные переходы и сохранный частичный результат |
| 010 | Прерывания после этапов и изменение входов; повторяются только необходимые операции |
| 011 | Изменение интегрированного дерева, отказ push и запрет direct push; evidence относится к фактической версии |
| 012 | Сбой закрытия или tracker publication, отсутствие окна записи; раздельные факты и безопасный retry |
| 013 | Однозадачная фича и контейнер с детьми; полная приёмка, неизменные родители |
| 014 | Успешный и частичный отчёты; свежая рекомендация без claim или запуска следующей задачи |
| 015 | Два изолированных RIS-проекта с разными путями, правилами и настроенным адаптером |
| 016 | Source/install parity, ресурсы и ссылки; реальные запросы полного выполнения и соседних операций |

Сбои проверяются на контролируемых границах; успешные пути — фактическими
действиями. Отчёт поставки различает реальные проходы, изолированные сценарии
и непроверенные гарантии. Структурная проверка текста не доказывает поведение агента.

## 10. Совместимость и состав поставки

Предлагаемый исходник — `skills/ris-execute-task/SKILL.md`. Подробности
возобновления и текстового маршрута могут находиться в owned resources,
загружаемых по соответствующему условию. Полные методики дочерних операций
в ведущий контекст заранее не загружаются.

При реализации синхронизируются установленная копия, README, точные роли в
`ris.yaml` и затронутые нормативные утверждения, пока откладывающие task executor:
прежде всего `01-architecture.md`, `05-adoption-and-validation.md`,
`ris-sdlc-mvp-skills.md` и `overview.md`.

Это ограниченная поправка для явно запускаемого сценария одной задачи.
Контракты самостоятельных операций сохраняются. По полной выборке других
открытых задач с активными принятыми дизайнами не обнаружено; будущие решения
не выдаются за текущую архитектуру.

Отдельный ADR не предлагается: решения помещаются в дизайн фичи, новый
глобальный state owner или workflow engine не вводится. Независимое ревью
поставки проверит границы композиции и совместимость.
