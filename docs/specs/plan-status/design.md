# Дизайн D1 — компактный обзор плана Beads

## 1. Основание и границы

- Требования v1: `docs/specs/plan-status/spec.md` на опубликованной ревизии `71bb5b225137754643f76bb0d37091c53a61d235`.
- Отдельное принятие требований: `acceptance.md#требования-v1` на той же ревизии.
- Работа: обычная самостоятельная задача `ris-oqv`, без feature-record. Сейчас `open`, детей и зависимостей нет.
- Контекст проекта: корневой `ris.yaml`, версия 2; адаптер — `ris-proj-adapter-beads-tasks`.

Дизайн описывает будущую поставку инструкций и команды. Обзор выполняется read-only, без сохранения отчёта, запуска рекомендации или изменения трекера.

## 2. Компоненты и ответственность

| Компонент | Ответственность |
|---|---|
| Новый `ris-proj-op-show-plan` | Область обзора, полное дерево, компактные строки, выбор кандидата, достаточность итогового ответа |
| Новая `/risp-status` | Тонкий вызов нового скила с `$ARGUMENTS` |
| `ris-proj-lib-common` | Общие правила с условным применением ресурсов |
| `ris-proj-op-resolve-context` | Выбранный проект, конфигурация и необходимые настройки |
| Выбранный адаптер задач | Проверенные чтения записей, родительства, статусов и направленных блокировок |
| `ris-proj-op-suggest-continuation` | Доказательная рекомендация для переданного точного кандидата и проверка установленной команды |

**Один проектный скил достаточен:** самостоятельная переносимая методика здесь не выделяется. Прямой запуск работает в текущем агенте; обязательные execution-роли и субагенты для обзора не нужны.

## 3. Чтение данных

В Beads-адаптер добавляется **инструментальный read-only контракт обзора плана**, отдельно от task-only и feature-record операций. Он покрывает:

- полный набор рабочих записей всех типов;
- точное чтение записи неизвестного заранее типа;
- полное чтение детей любого рабочего контейнера;
- родительство и направленные `blocks`;
- необходимые поля строки и данные для распознавания фичи.

Нативная основа — `bd list --all --limit 0 --brief --json` без фильтра task/epic/bug. Адаптер явно учитывает штатно скрываемые категории Beads, чтобы рабочие записи не исчезали из обзора; служебные записи и шаблоны не объявляются работой по одному факту существования.

Компактная выборка — первый проход. Если она не раскрывает нужное поле, адаптер делает адресное чтение `show --brief-deps` или типизированных связей. Пропущенное поле означает «неизвестно», а не «пусто».

- **Без ID:** полный набор проекта, включая закрытые записи для расчётов и контекста.
- **С ID:** выбранная запись и рекурсивно её дети, включая закрытых для расчётов; необходимые предки и внешние блокеры. Полная очередь проекта для этого не требуется.

Все ответы проверяются на ошибку, полноту и понятную структуру. Усечённый вывод дочитывается средствами среды; его нельзя принять за полную выборку.

## 4. Построение дерева

Дерево собирается во временном представлении по ID:

- принадлежность определяется фактическим `parent`/`parent-child`, не формой ID;
- блокировки хранятся отдельно: **заблокированная запись → prerequisite**;
- каждая незакрытая запись области появляется ровно одной основной строкой;
- закрытые предки открытых записей показываются с пометкой «закрыт, контекст»;
- standalone-ветки находятся в отдельной группе;
- внешние блокеры выбранной ветки показываются отдельными короткими строками без раскрытия их независимых деревьев.

Цикл, отсутствующий родитель или противоречивые связи диагностируются. Такие записи сохраняются в явной группе с нарушенной/неподтверждённой иерархией, вместо пропуска или искусственного переподчинения.

Роль «фича» определяется по действительному контракту RIS и содержимому записи. Обычная task под эпиком и нативный тип `feature` автоматически ею не становятся. Исторические и malformed-данные видны с диагностикой.

## 5. Строка и глубина подтверждения

Форма строки:

```text
<ID> <название> [тип/роль; статус; Pn; исполнитель; ждёт ID; срок; прогресс; этап]
```

Обязательны ID, название, тип/роль, исходный статус и приоритет. Дополнения выводятся при наличии; неизвестное обязательное поле явно помечается.

**Прогресс контейнера:** `закрыто/всего прямых детей`. Область подсчёта обозначается в легенде. Это счётчик статусов, включая административно закрытые записи, а не процент выполнения критериев. При неполном составе счётчик не выдаётся за точный.

**Требования и дизайн фичи:** различаются:

- ссылка указана, принятие не проверено;
- принятие подтверждено по конкретной версии и решению;
- отсутствует по проверенным данным;
- данные неизвестны или некорректны.

**Понятный этап:** выводится только из достаточных фактов. Например, `in_progress` позволяет сказать «в работе по Beads», но не доказывает запуск конкретного flow. «Нужен дизайн» требует проверки соответствующих входов; отсутствие ссылки в компактной строке недостаточно.

Для обычного дерева не читаются все документы. Углублённая проверка ограничивается фактами, необходимыми для итоговой рекомендации.

## 6. Выбор одного следующего действия

Порядок выбора:

1. В пределах запрошенной области сначала рассматривается начатая незавершённая работа. `in_progress` — сигнал для проверки, а не доказательство действующего сценария.
2. Если начатого несколько — учитываются приоритет, затем более раннее начало; стабильный ID используется как последний способ разрешить равенство.
3. Если начатого нет — учитываются приоритет и направленные зависимости. При равном приоритете prerequisite рассматривается раньше заблокированной им работы.
4. Контейнер не считается лишним кандидатом только потому, что у него есть дети: необходимым действием может быть уточнение или проверка самого контейнера.
5. Для выбранного точного ID применяется `ris-proj-op-suggest-continuation`.

Навигатор получает проект, ID, область и уже проверенные факты с ограничениями. Он читает необходимые источники, решения и контракты; новый скил проверяет соответствие его результата выбранному кандидату и запросу.

Если выбранная начатая работа требует решения или имеет пробел, итогом становится именно это решение/пробел. Скил не перебирает очередь до получения удобной команды.

Чужой исполнитель виден явно. Рекомендация может предложить согласовать продолжение с ним, но не перехватить работу.

В конце — **одно действие**, причина и проверенная slash-команда. При отсутствии команды, совместимого владельца или существенного входа — точный пробел. Пустой план обозначается прямо.

## 7. Ошибки и конкурентные изменения

Обзор — наблюдение текущего состояния, не транзакционный снимок всего проекта.

Перед окончательной рекомендацией перечитываются выбранная запись и существенные для вывода связи. При изменениях пересматривается затронутый вывод; постоянная конкуренция обозначается ограничением.

При ошибке отдельного чтения сохраняется доступная часть дерева с указанием неполноты. Нельзя утверждать, что найден глобально лучший кандидат, если неизвестная часть могла повлиять на выбор.

Нет блокировок писателей, автоматического pull/push, исправления записей или установки пакета.

## 8. Поставка и совместимость

Предполагаемые изменения:

- `skills/ris-proj-op-show-plan/SKILL.md`;
- `commands/opencode/risp-status.md`;
- адресное расширение чтений Beads-адаптера;
- `docs/skills.md`, относящиеся примеры README и переходная справка;
- адресная поправка действующей нормы о составе меню команд.

Исторический перечень 18 команд сохраняется как принятая версия. Актуальное меню расширяется `/risp-status`; фиксированное новое число заранее не задаётся, поскольку параллельно принят дизайн `/risp-run-simple-task`.

С `ris-1wa.1` нет необходимой blocks-зависимости: общий стык — меню и справка. Будущий fast-flow может рекомендоваться только после проверки его фактической доступности и установленной команды.

Новые скрипты, реестр состояний и изменение схемы Beads не требуются. Отдельный ADR не нужен: решения локальны для навигации и чтений адаптера.

## 9. Покрытие критериев и проверки

| Критерии | Проверяемая граница |
|---|---|
| AC-001–003 | Области project/ID, все рабочие типы, полные выборки и одна строка на запись |
| AC-004 | Родительство отдельно от `blocks`, закрытые предки и внешние блокеры |
| AC-005–006 | Поля строки, прямой прогресс, ссылки отдельно от принятия, доказательные этапы |
| AC-007 | Лёгкое дерево; адресное углубление только для рекомендации |
| AC-008–009 | Приоритет начатого, зависимости, применение навигатора, проверка command target |
| AC-010–011 | Ошибки и неизвестность явны; пустой план; отсутствие постоянных эффектов |
| AC-012 | Различимость соседних операций, зависимости, команда, справка и пакет |

Проверки поставки: содержательное чтение, затронутая статика, ссылки/имена/ресурсы, согласованность команд и source/install при разрешённой установке; независимое ревью без нерешённых высоких/средних замечаний. Существующие файловые проверки пакета применяются по затронутому составу. Тесты поведения агентов не добавляются.
