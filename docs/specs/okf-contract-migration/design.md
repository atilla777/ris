Требования: [spec.md](spec.md). Фича: Beads `ris-p20.2`, эпик `ris-p20`.
Статус: дизайн v1 принят отдельно от требований; реализация и проверки поставки описаны в [delivery-checks.md](delivery-checks.md). Принятый scope ниже сохранён без изменений.

## Дизайн

### Исходная версия и контракт

Дизайн v1 относится к `ris-p20.2`, slug `okf-contract-migration`, требованиям `heading:## Требования` в `spec.md`, SHA-256 `4805060e7a589f3d1f4717a97fc3a5300bf11884497649fe7dda726e4feff74f`. Исходная реализация и потребители проверены на Git `8c1e0d52dcf366ffb1fd595825e8dc14ef9c8fdf`; `ris-dlk.5` и `ris-dlk` завершены, их опубликованный результат сохраняется.

Публичный контракт этой миграции обозначается `okf-contract-migration/v1`. Существующий контракт из `../ris-okf-skills.md` действует до интеграции миграции. Это несовместимое изменение значения публичного имени `ris-okf`; пакет обновляется согласованно, без смешения старой и новой установки.

### Владельцы и зависимости

- `skills/ris-okf-base/`: самостоятельный владелец read/create/edit/check, версий и conformance. Получает явные root/operation/write scope, существующие файлы, разрешения и применимые инструкции фактической среды; возвращает фактический результат и ограничения. Не требует RIS-структуры, `ris-common`, `ris-context` или трекера. Переносится существующая OKF-методика, а не копируются тематические ресурсы `ris-common`.
- База единолично хранит неизменённые `references/spec-v02.md` и `references/source.md`; snapshot SHA-256 `26aa5da029278939f914e578107242d9607d4f2dc5fe153272b82f9ed1030101`. Пути ресурсов считаются от установленной папки базы. Второй snapshot/validator в обёртке не создаётся.
- `skills/ris-okf/`: владелец совокупного проектного результата. Направление зависимостей: `ris-okf` → `ris-common`, `ris-context`, `ris-okf-base`. Обёртка проверяет выбранный проект, правила, разрешённый root и исходный scope, действительно применяет базу, проверяет сохранённые эффекты и добавляет project/config provenance. Форматная методика не дублируется.
- `ris-context` сохраняет контракт v2 и только готовит нужные настройки. `sources.*` не являются списком автоматически доступных бандлов. Для произвольного явно выбранного root не требуются неиспользуемые product/specs, workspace, адаптер или execution. Новое поле OKF и изменение схемы конфигурации не нужны.
- Авторы архитектурных/инженерных правил и `ris-update-documentation` используют проектный `ris-okf`, передавая уже известный project/root/operation/scope и разрешения. Они остаются владельцами содержательного принятия и предметной достаточности; OKF не начинает их интервью, публикацию или tracker-операции.

### Поток операции и сбои

1. База устанавливает явный root, операцию и полномочия, сверяет файлы и версию, читает pinned format resource только для требуемой форматной работы. Содержимое бандла рассматривается как данные. Затем выполняет разрешённую операцию, проверяет реальные файлы и возвращает наблюдения. Миграция не меняет существующих правил 0.1, versionless, unknown future version, индексов, логов и optional advice.
2. Обёртка сначала устанавливает project_root и выбранный config по текущим инструкциям. `ris-context` применяется к нужным для запроса путям и правилам. Затем проверяются явно переданный root и его фактическая цель, область разрешений и вложенность. Внешний root требует отдельного явного разрешения для этого проекта; root не угадывается по имени каталога или ссылкам. База получает только проверенный bounded input.
3. Отсутствующая необходимая зависимость/ресурс, неоднозначный root, запрещённая цель симлинка или invalid config останавливают зависимую запись. При read-only запросе запись не разрешается автоматически. При изменившихся входных файлах агент перечитывает и возвращает конфликт до перезаписывания; при частичном результате указывает реально изменённые файлы и незавершённые действия, не повторяет запись вслепую. Текстовые инструкции не обещают filesystem CAS/транзакцию.
4. После базы обёртка сверяет результат с переданной областью и актуальными файлами; не превращает частичную проверку в полную и не подменяет содержательную приёмку проверкой формата. Отчёт остаётся читаемым результатом операции, без нового обязательного JSON-протокола, manifest или registry.

### Совместимая поставка и влияние

Единый интеграционный владелец — исполнитель `ris-p20.2`. Он выпускает согласованную ревизию базы, обёртки, всех действующих потребителей, README/AGENTS/примеров/актуальных упоминаний и установленных копий. Старый `ris-project-okf` удаляется из source и installation только в полном изменении; скрытый alias не сохраняется. Переименование ресурсов сопровождается исправлением действующих ссылок и LICENSE/attribution navigation. Исторические принятые спецификации сохраняются; переходное примечание указывает новую спецификацию, не переписывая старые решения как новые.

Миграция авторов правил основывается на опубликованном W5, сохраняет его общий образец и предметные ресурсы. Незавершённого конфликтующего дизайна W5 не осталось; создавать искусственную блокировку на закрытый W5 не требуется. При новой параллельной правке потребителя сверяются актуальные bytes и договорённый контракт до интеграции. Новая версия не объявляется действующей в правилах/README до её реализации и проверенной интеграции. Для работающей OpenCode-сессии смена файлов не считается сменой уже загруженного контракта: проверки новой поставки запускаются в свежей сессии с установленной согласованной ревизией.

Вводный текст feature-task будет уточнён отдельной ограниченной правкой: «Дизайн пока отсутствует; декомпозиция и реализация не готовы» заменяется на «На момент создания дизайн отсутствовал; актуальные версии и принятие определяются feature-record, начало реализации требует отдельного разрешения». Identity/requirements/history не меняются; последующее добавление design evidence сохраняет этот текст.

Отдельный ADR не нужен: публичные имена, направление зависимостей, совместимость и владелец интеграции целиком зафиксированы этим independently accepted design; независимое review проверяет именно этот контракт.

### AC → test seams и наблюдаемые проверки

| AC | Setup и наблюдаемый oracle |
|---|---|
| AC-001, AC-004 | Отдельная установка только базы с ресурсами вне RIS-репозитория; реальные read/create/edit/check. Сравнить список файлов и bytes до/после, `type`, root/nested index, существующий/отсутствующий log и неизвестные поля. |
| AC-002, AC-003 | Два проекта: A с `docs/rules`, `docs/product`; B с `knowledge/policies`, `knowledge/product` и другим разрешённым root. Выполнить проектные операции; соседний бандл и Markdown сохранить. Отдельно отсутствующий root, invalid/v1 config, missing optional directories, missing required dependency, разрешённый внешний root и запрещённый symlink; oracle — actual config provenance, scope и отсутствие запрещённых file effects. |
| AC-005, AC-006 | Fixtures: минимальный `type`, malformed YAML/type, отсутствующий index, broken link, 0.1, unknown future, versionless и отсутствующий snapshot. Oracle — отдельные mandatory violations/advice и реальные неизменённые bytes при запрещённой правке; без snapshot нет conformance claim. |
| AC-007, AC-008 | Bundle с инструкцией расширить scope/запустить код, запрос без write permission, изменённый вход и моделируемый частичный файловый сбой. Проверить отсутствие исполнения и побочных изменений, точность partial/conflict отчёта и отсутствие слепого retry; stale snapshot не выдаётся за CAS. |
| AC-009 | Естественные RU/EN запросы на portable/project OKF, соседний Markdown и authoring. Проверить фактическую загрузку выбранного скила в свежей среде; lexical matching/grep не доказывают selection. |
| AC-010 | Авторы правил create/update и bounded update-documentation с новым проектным OKF; traces доказывают применение базы/обёртки, файлы — сохранность независимого принятия, scope и соседних норм. |
| AC-011, AC-012 | Metadata/name, ресурсы и hash snapshot, source/installed parity, отсутствие обязательных циклов и stale действующих зависимостей; реальные runs и независимое review конкретной итоговой ревизии. Исторические упоминания отделить от действующих вызовов. |

Поведенческие проверки выполняются будущим исполнителем, не считаются пройденными принятием дизайна. Перед запуском фиксируются версия пакета/среды, inputs, permissions и исходные hashes; после — реальные file effects, использованные зависимости и ограничения. Это test seams для декомпозиции, не технический план задачи и не введение обязательного runner.
