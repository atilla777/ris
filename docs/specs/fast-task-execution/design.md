## 1. Новый вход

- Скилл: **`ris-proj-flow-execute-simple-task`**.
- Команда: **`/risp-fast-task`**.
- Вход: поручение пользователя, выбранный проект, необязательный существующий ID
  и доступные решения/свидетельства для продолжения.
- Результат: проверенное изменение, независимое ревью, подтверждённая
  Git-публикация; при использовании трекера — отдельно проверенные итог,
  закрытие выбранной задачи и публикация трекера.

Команда явно загружает этот flow и передаёт `$ARGUMENTS`. Без содержательного
поручения flow запрашивает его, а не выбирает работу из очереди.

Описание скилла допускает естественные просьбы «сделай по-быстрому» и
самостоятельный выбор маршрута агентом для **уже порученной** простой задачи.
Формального классификатора, лимита diff и нового диспетчера не вводим.

Это адресное расширение компактного меню на одну команду. Историческое принятие
набора из 18 команд сохраняется в истории; действующая документация фиксирует
дополнение.

## 2. Разделение ответственности

| Часть результата | Владелец и изменение |
|---|---|
| Достаточность входов, переходы, общий результат | Новый flow |
| Настройки и пути проекта | `ris-proj-op-resolve-context`, только необходимые поля |
| Реализация и исправления | `ris-port-op-implement-change` в основном агенте |
| Затронутая документация | `ris-proj-op-update-documentation`, когда нужна |
| Независимое ревью | `ris-proj-op-review-task`, расширенный для no-ID change |
| Git-публикация | `ris-proj-op-publish-task`, расширенный для no-ID change и подходящей текущей копии |
| Изоляция при необходимости | `ris-port-op-prepare-worktree` и выбранный адаптер |
| Учёт, claim, результат, закрытие, Dolt | Выбранный адаптер задач |

**Новой переносимой базы и проектной обёртки реализации не требуется.** Flow
подготавливает проектные входы и непосредственно применяет существующую
переносимую реализацию. Она уже поддерживает `standard|tdd`, достаточные
технические ограничения для самостоятельного изменения и возврат результата
без файла отчёта.

`ris-proj-op-implement-task-tdd` сохраняет обязательный TDD-контракт. Fast не
вызывает его с просьбой пропустить RED.

## 3. Маршрут

### Подготовка

Основной агент устанавливает результат, границы, способ проверки, применимые
правила и состояние рабочей копии.

- Понятное поручение служит принятым описанием самостоятельного изменения.
- Существенно недостающие решения уточняются адресно.
- Наличие настроенного адаптера само по себе не включает обязательный учёт.
- При переданном ID читаются его собственные ограничения, тип, владение,
  состав и блокеры.
- Feature record с отсутствующим обязательным дизайном, чужой claim или
  незавершённый контейнер не обходятся выбором fast.

Если правила требуют записи задачи, адаптер создаёт короткую **обычную задачу**
с целью, границами, критериями и основанием поручения. Проверяется существующая
идентичность; искусственные epic, feature payload и документы не создаются.

Для используемой задачи выполняется необходимый claim. Без трекера не нужны
actor, каталог по ID и доступ к очереди.

### Рабочая копия

По умолчанию используется текущая подходящая копия. Проверяются HEAD, индекс,
staged/unstaged/untracked изменения, незавершённые Git-операции и принадлежность
изменений.

При необходимости изоляции применяется существующий владелец подготовки
worktree. Идентичность работы может задаваться поручением без Beads ID;
привязка repository/path/branch остаётся явной.

Чужие изменения не сбрасываются, не присваиваются и не включаются в коммит.
Неоднозначный состав будущей публикации требует изоляции либо разрешения
конкретного конфликта.

### Реализация и проверки

Основной агент применяет `ris-port-op-implement-change`:

- `standard` — если TDD не требуется;
- `tdd` — если требуется правилами или выбран для содержательно полезного
  test-first исполнения;
- для обратимой текстовой правки достаточно проверки результата и diff;
- для конфигурации используется применимая валидация;
- для логики — затронутые проверки и содержательно необходимые тесты.

Затронутые документы синхронизируются до финального ревью. Проверки связываются
с конкретной версией полного кандидата, включая новые файлы и режимы.

### Ревью и исправления

Flow запускает отдельного независимого субагента через настроенную роль
`task-review`. Роли `task-execution` и `task-implementation` для fast не требуются.

Ревьюер получает поручение и уточнения, правила, полный кандидат, результаты
проверок и предыдущие замечания. Файлы spec/design/plan не обязательны сами по себе.

- High/medium → исправления основным агентом, затронутые проверки, новое
  независимое ревью.
- Low → необязательные рекомендации с кратким решением по ним.
- Недоступный ревьюер → блокировка публикации с сохранением результата.

### Публикация и завершение

Основной агент применяет Git-публикатор к одобренному кандидату. После
интеграционных изменений повторно оцениваются затронутые проверки и независимо
пересматривается новый полный snapshot.

PR-only политика, запрет direct push или недостающие права дают блокировку.
Подтверждённый push проверяется свежим удалённым чтением.

При трекере затем отдельно выполняются сохранение достаточного итога, проверка
завершения и exact close выбранной задачи, публикация трекера и её подтверждение.
Родители не закрываются.

## 4. Точные поправки существующих контрактов

### `ris-proj-op-review-task`

Добавить самостоятельный вход **«ограниченное изменение без ID»**:

- основание — поручение, критерии и технические ограничения;
- без обязательного адаптера, task directory и поиска файлов отчётности;
- отчёт возвращается в ответе, сохранение — по необходимости или правилам;
- ID-ветка сохраняет актуальные task/feature/bug-проверки.

Методика остаётся у `ris-port-op-review-change`.

### `ris-proj-op-publish-task`

Расширить ветку Task/change: ID необязателен для явно заданного самостоятельного
изменения. Поручение, критерии, проверки и независимое ревью заменяют
искусственные tracker/spec-входы.

Добавить ограниченный путь публикации **из подходящей текущей копии**. Сейчас
контракт требует собственной ветки/копии и запрещает использование общей
локальной `main`; без поправки он противоречит принятому fast-поведению.

Новый путь допустим, когда правила разрешают его, копия не используется
параллельно, состав изменения однозначен и нет мешающих чужих изменений.
Если безопасная интеграция требует изоляции, используется собственная
ветка/копия. Полный маршрут сохраняет прежнюю политику.

Проверки всей исходящей Git-истории, точного одобренного snapshot, normal
non-force push и удалённого результата остаются общими.

### Beads-адаптер

Уточнить ordinary-task контракт: для простой задачи допустимо самодостаточное
принятое поручение с атрибуцией и критериями в записи. Обязательная ссылка на
опубликованную спецификацию не требуется.

Это не ослабляет feature-record и bug-execution контракты. Существующая задача
сохраняет собственные принятые ограничения; fast не превращает зарегистрированный
баг в обычную задачу для обхода его обязательных входов.

### Правила самого RIS

Ввести ограниченное исключение для явно выбранного fast-маршрута:

- новая запись Beads, `plan.md`, журналы и файл ревью не обязательны;
- подходящая текущая копия разрешена, изоляция включается по необходимости;
- основной агент реализует и публикует, отдельный субагент ревьюит;
- при существующем ID сохраняются tracker-проверки и отдельное завершение.

Остальной SDLC и багфикс-сценарий сохраняют свои контракты.

## 5. Продолжение и сбои

Flow не хранит отдельную машину состояний. Состояние восстанавливается по Git,
доступным решениям и свидетельствам, при ID — также по трекеру.

Возобновляется первая недостающая операция:

- подтверждённый push не повторяется;
- выполненный close не повторяется;
- потерянное или неприменимое ревью проводится заново;
- неизвестные критерии и согласования не восстанавливаются догадкой;
- существенное усложнение останавливает зависимые действия и выносится на
  адресное согласование.

Итог различает Git-публикацию, локальные tracker-эффекты и публикацию трекера.
Отсутствие обязательных файлов отчётности не означает обещания автоматического
восстановления недоступной истории чата.

## 6. Проверяемость и состав поставки

| Критерии | Проверяемая граница |
|---|---|
| AC-001–002 | Команда, описание выбора flow, минимальные входы |
| AC-003–004 | No-ID/ID/обязательный учёт; текущая копия/изоляция |
| AC-005–008 | Владельцы операций, независимость, условный TDD, отсутствие обязательных отчётов |
| AC-009–011 | Публикатор, отдельные tracker-эффекты, точные блокировки |
| AC-012–013 | Адресное расширение и восстановление фактических эффектов |
| AC-014–015 | Границы компонентов, правила RIS, документация, доставка и проверки |

Поставка затрагивает новый flow и команду, указанные атомарные контракты, правила
RIS, каталог/README/карту команд и установленный комплект. Редкие ветки worktree,
tracker и recovery загружаются по условию.

Проверки инструкций — чтение и независимое ревью. Дополнительно проверяются
имена, зависимости, ссылки, состав команд и source/install parity. Изменения
доставки проверяются применимыми существующими файловыми/CLI-тестами. Тесты
поведения агентов не вводятся; измеренное ускорение не заявляется.

Отдельный ADR не нужен: архитектурная модель владельцев сохраняется, а новые
контракты и совместимость фиксируются в дизайне.
