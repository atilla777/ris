# Ускоренное выполнение простой задачи — дизайн D1

**Статус:** дизайн D1 отдельно принят пользователем для `ris-1wa.1`.
Основа — требования v1 на опубликованном
`e4829930e857263659f1f5c36abc70d5dc01e778`.
Отдельное [решение принятия](acceptance.md#дизайн-d1).
Документ описывает будущую поставку, не её реализацию или приёмку.

## 1. Новый вход и граница сценария

- Скилл: **`ris-proj-flow-execute-simple-task`**.
- Команда: **`/risp-run-simple-task`**.
- Вход: порученный результат, выбранный проект, необязательный существующий ID и доступные уточнения.
- Выход: проверенное изменение и подтверждённая Git-публикация; при использовании трекера — отдельно проверенные итог, закрытие выбранной задачи и публикация трекера.

Пустая команда запрашивает поручение. Автоматический выбор задачи из очереди не предусмотрен.

Один проектный flow отвечает за переходы и совокупный результат. Переносимая копия сценария и дополнительная обёртка реализации не нужны.

## 2. Владельцы операций

| Ответственность | Решение |
|---|---|
| Достаточность запроса, применимость fast, переходы и продолжение | Новый flow |
| Правила, настройки и необходимые пути | Common/context |
| Реализация и устранение замечаний | `ris-port-op-implement-change` в основном агенте |
| Затронутая документация | `ris-proj-op-update-documentation`, по необходимости |
| Проектное ревью | Расширенный `ris-proj-op-review-task`, в независимом субагенте |
| Методика ревью | Существующий `ris-port-op-review-change` |
| Git-интеграция и публикация | Расширенный `ris-proj-op-publish-task`, в основном агенте |
| Учёт и завершение | Выбранный адаптер задач |
| Отдельный worktree | Существующие владельцы подготовки копии |

`ris-proj-op-review-task` расширяется до ревью ограниченного проектного изменения **с ID или без него**. Его имя сохраняется, описание уточняется. Файлы spec/design/plan не становятся обязательными входами: достаточны поручение, принятые ограничения, точная версия изменения и результаты проверок.

`ris-proj-op-implement-task-tdd` сохраняет обязательный TDD. Fast применяет переносимую реализацию в `standard` или `tdd` по условиям задачи и правилам проекта.

## 3. Минимальный контракт передачи

Между операциями передаётся достаточный набор сведений, без нового файлового формата или реестра:

- проект, поручение, границы и критерии;
- принятые ограничения и существенные решения;
- рабочая копия, ветка, базовая ревизия;
- точный состав итогового изменения, включая новые и удалённые файлы;
- проверки, результаты и ограничения их применимости;
- вывод ревью, его версия и независимый исполнитель;
- фактические результаты Git и, при наличии, трекера.

По умолчанию эти сведения находятся в сессии. Обязательный файл отчёта появляется только по правилам проекта или конкретной необходимости.

## 4. Рабочая копия и ветка

До изменений flow проверяет состояние Git, незавершённые операции и пригодность копии.

- Подтверждённая собственная ветка используется повторно.
- В свободной подходящей копии создаётся собственная ветка от проверенного текущего `HEAD`: например, `task/<ID>` либо `fast/<краткое-имя>-<суффикс>`. Имя без ID не изображает запись трекера.
- Создание и переключение ветки — небольшой подготовительный шаг flow через Git, с проверкой результата. Нового скилла для него не требуется.
- Чужие изменения не переносятся между ветками автоматически. При неясной принадлежности, занятой общей копии или необходимости изоляции применяется подготовка worktree.
- Для worktree с ID используется проектный владелец подготовки; без ID — переносимый владелец с явными repository/path/branch/base и разрешениями. Путь не выводится из выдуманного ID.

Публикатор продолжает работать из собственной ветки. Общая локальная `main` не используется для интеграции и коммитов результата.

## 5. Последовательность выполнения

1. **Проверить достаточность.** Понятный запрос с ограниченными последствиями и доступным способом проверки допускается без отдельной подготовки документов.
2. **Применить учёт проекта.** Использовать переданный ID; при обязательном учёте создать короткую обычную задачу после проверки идентичности. Без такого требования запись не создавать.
3. **Подготовить копию и ветку.** При наличии ID проверить состояние, блокеры и необходимый claim.
4. **Реализовать и проверить.** Основной агент применяет владельца реализации и, при необходимости, документации.
5. **Запустить независимое ревью.** Используется существующая роль `task-review`; фактическая доступность и запуск проверяются. Отдельные роли реализации и публикации fast не требует.
6. **Исправить high/medium.** Повторить затронутые проверки и независимое ревью. Low достаточно рассмотреть и зафиксировать решение.
7. **Опубликовать через владельца Git.** Передать точный проверенный снимок и свидетельства ревью. Изменение интегрированного дерева требует применимой независимой переоценки до push.
8. **Завершить учёт отдельно.** При наличии ID сохранить итог с опубликованным коммитом, проверить возможность закрытия и отдельно опубликовать трекер. Предков не закрывать.

Требование PR, запрет direct push, недоступное ревью или обязательная непройденная проверка останавливают зависимую публикацию с сохранением доступного результата.

## 6. Адресные изменения существующих контрактов

- **Ревью:** no-ID change, входы непосредственно из сессии, необязательное сохранение отчёта.
- **Публикатор:** ветка `Task/change` принимает ограниченное изменение без ID; проверки трекера условны. Алгоритм интеграции, проверки полного снимка и удалённого подтверждения остаётся один.
- **Адаптер задач:** короткая ordinary-задача может сохранять достаточные поручение, ограничения и критерии без искусственных spec/design-ссылок. Feature-record и требования к существующим feature/bug-записям не ослабляются.
- **Правила самого RIS:** для явно выбранного fast отменяется обязательность файлов плана, журнала и отчётов; разрешается выполнение основных операций ведущим агентом. Обязательный учёт Beads в RIS сохраняется, запись становится краткой.
- **Архитектурная методика:** добавляется адресное исключение из обязательного делегирования операций сценария для fast; независимое ревью остаётся отдельным.

Переданный ID сохраняет свой действительный тип и контракт. Fast не превращает feature в ordinary-задачу, не обходит незавершённых детей и не заменяет подготовку зарегистрированного бага.

## 7. Усложнение и восстановление

Небольшое уточнение остаётся внутри fast. Существенный выбор поведения, публичного контракта или архитектуры возвращается пользователю с конкретным вопросом. Подключается только необходимая подготовительная операция; пригодные результаты сохраняются.

При продолжении сверяются текущие Git/трекер и доступные свидетельства. Подтверждённые эффекты не повторяются. Утраченное или неприменимое ревью проводится заново. Отсутствие истории сессии не заменяется предположениями о прежних решениях.

## 8. Проверка дизайна и поставки

| Критерии | Проверяемая граница и ожидаемый результат |
|---|---|
| AC-001–002 | Команда явно вызывает flow; ясный запрос проходит без обязательных подготовительных документов |
| AC-003–004 | Ветки no-ID/ID и current-copy/worktree определены; чужая работа сохраняется |
| AC-005–008 | Основной агент применяет владельцев; ревью независимо; TDD условен; отчётные файлы необязательны |
| AC-009–011 | Публикатор принимает точный reviewed snapshot; проверяет remote; Git и tracker-эффекты разделены |
| AC-012–013 | Усложнение расширяет только нужную часть; продолжение сверяет эффекты до повторения |
| AC-014–015 | Владельцы, документы, команда и source/install согласованы; выполнены затронутые проверки |

Инструкции проверяются чтением и независимым ревью. Имена, ссылки, зависимости и source/install parity — статически. Доставка нового скилла и команды — существующими файловыми/CLI-проверками пакета. Agent behavior tests не добавляются; ускорение не объявляется измеренным.

## 9. Документы и совместимость

Дизайн сохраняется отдельно в `docs/specs/fast-task-execution/design.md`, решение — новым разделом `acceptance.md`. Принятая ссылка требований остаётся неизменной.

Добавление команды адресно расширяет компактный каталог на один вход; историческая спецификация 18 команд сохраняется. Обновляются актуальные каталог, README, переходная справка и затронутые нормы. Полный task flow и багфикс-сценарий сохраняют свои режимы.

Отдельный ADR не нужен: решения локальны для маршрута и его входных контрактов. После принятия требуются независимое ревью документов, Git-публикация и сверенное обновление `design` в Beads с отдельной Dolt-публикацией.
