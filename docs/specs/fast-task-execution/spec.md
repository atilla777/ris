# Ускоренное выполнение простой задачи

**Статус:** требования v1 приняты пользователем в текущем интервью;
разрешены сохранение, независимое ревью, публикация и создание записи фичи
под эпиком `ris-1wa`. Дизайн, декомпозиция и реализация этим не запускаются.
Постоянный slug: `fast-task-execution`.
Отдельное [решение принятия](acceptance.md#требования-v1).

## 1. Цель и граница

Дать пользователю RIS короткий путь от понятного ограниченного запроса до
проверенного опубликованного изменения в целевом проекте, включая сам RIS.
Примеры — точная замена слова в шапке сайта, простая правка конфигурации,
небольшое понятное изменение кода. Размер diff сам по себе не определяет простоту.

Основной результат:

**Запрос → изучение контекста → реализация → достаточные проверки → независимое
ревью → необходимые исправления и перепроверка → подтверждённая публикация.**

Запрос может быть достаточным описанием результата. Отдельные этапы подготовки
требований, дизайна, декомпозиции и технического плана, а также их документы
не обязательны. Это не отменяет понимания результата, границ и способа проверки.
Агент полагается на предметную оценку достаточности, а не на формальный
классификатор, лимит строк или обязательный опросник.

## 2. Запуск и полномочия

- Предоставляется отдельный составной проектный скилл и команда его запуска.
  Команда явно указывает этот скилл; точные техническое и пользовательское
  имена определяются при дизайне с учётом актуальной схемы команд RIS.
- Можно запустить тот же маршрут обычной просьбой: «сделай простую задачу»,
  «сделай по-быстрому». Агент также может выбрать его сам для порученной
  пользователем задачи, если оценивает её как простую. Это не разрешает
  самостоятельно выбирать и начинать непорученную работу.
- Агент оценивает ясность результата, ограниченность последствий и возможность
  соразмерной проверки. Закрытого списка допустимых типов правок нет.
- Запуск разрешает согласованный цикл: реализацию, проверки, независимое ревью,
  исправления, коммит и push в установленную основную ветку проекта без
  повторного подтверждения. Когда используется Beads, сюда входят отдельные
  завершение выбранной задачи и публикация изменений трекера при выполнении
  применимых условий. Родители автоматически не закрываются.
- Права среды и обязательные правила проекта сохраняются. Наличие команды
  не разрешает обход запретов публикации, проверок или учёта.

## 3. Минимальные входы и соразмерная подготовка

Агент устанавливает выбранный проект, запрошенный результат и границы, изучает
относящиеся к изменению инструкции и текущую реализацию. Понятного запроса
достаточно для начала; материально недостающие решения уточняются адресно.
Повторное формальное утверждение уже ясного поручения не требуется.

| Элемент | Поведение fast-маршрута |
|---|---|
| Beads | По умолчанию новая запись не создаётся. Переданный существующий ID используется. Если проект требует учёта, короткая запись создаётся автоматически; перед записью проверяется существующая идентичность. |
| План | Нет обязательного отдельного этапа и файла `plan.md`. Агент при необходимости кратко сообщает подход в сессии. Необходимость серьёзного планирования вызывает пересмотр применимости fast. |
| Рабочая копия | По умолчанию текущая подходящая копия с проверкой её состояния и сохранением чужой работы. Отдельный worktree — при необходимости изоляции, например пересечении параллельных изменений, или по правилам проекта. |
| Исполнители | Основной агент реализует, исправляет и публикует в текущей сессии, применяя владельцев атомарных операций. Отдельный субагент проводит независимое ревью. Отдельный вызов исполнителя на каждый этап не обязателен. |
| Отчётность | Нет обязательных файлов журнала, реализации и ревью. Подход, проверки, выводы ревью и итог публикации отражаются в сессии; при Beads сохраняется краткий итог. Дополнительные записи — по конкретной необходимости или правилам проекта. |

Для работы без ID не требуется искусственная запись, каталог по выдуманному ID
или второе хранилище статусов. Существующая запись не отменяет её актуальные
ограничения, принадлежность работы и необходимые проверки состояния.

## 4. Реализация, проверки и независимое ревью

Агент выбирает минимальный достаточный набор проверок по последствиям:
для простой обратимой текстовой правки — результат и diff, для конфигурации —
применимая валидация, для логики — затронутые тесты и новые тесты при
содержательной необходимости. Формальные тесты только ради этапа не добавляются.
TDD не обязателен для всего маршрута: используется, когда полезен либо требуется
правилами проекта. Обязательные проектные проверки соблюдаются.

Ревью обязательно и проводится отдельным субагентом, независимым от авторов
реализации и исправлений. Он получает запрос/уточнения, правила, конкретную
версию изменения и свидетельства проверок; наличие файлов spec/design/plan
или записи трекера не требуется само по себе. Основной агент проверяет
достаточность возвращённого результата; самопроверка не заменяет независимость.

Замечания высокого и среднего уровня устраняются с применимыми проверками
и последующим независимым ревью. Низкие рекомендации не требуют
автоматического исправления, новой задачи или нового раунда. Непроверенный
либо изменившийся результат не выдаётся за одобренный. При отсутствии
необходимого ревью публикация остаётся заблокированной.

## 5. Публикация и завершение

Первая версия использует существующий путь прямого push в установленную
основную ветку выбранного remote. Коммит содержит только согласованные
изменения; чужая работа сохраняется. После интеграционных изменений
пересматривается применимость проверок и независимого ревью к публикуемой
версии. Успех подтверждается свежим чтением удалённого состояния, не только
кодом выхода push.

Если правила требуют PR, прямой push запрещён либо отсутствуют необходимые
права, агент сохраняет проверенный результат и сообщает точную блокировку
публикации. Создание PR, ожидание слияния и обход проектных правил в первую
версию не входят. Частичный результат не объявляется завершённым циклом.

При использовании Beads краткий итог и опубликованный Git-коммит сохраняются
в выбранной задаче; её выполнение и отдельное закрытие проверяются по
применимым правилам. Git push, локальное закрытие и отдельная публикация
трекера — разные факты. Без Beads остаётся подтверждённый Git-результат
и итог в сессии; служебная запись для имитации завершения не создаётся.

## 6. Уточнение, усложнение и продолжение

Небольшую неясность агент уточняет и продолжает fast. Если обнаруживается
существенное решение, например изменение публичного контракта или потребность
в проектировании, агент останавливает зависимые действия, объясняет причину
и предлагает согласовать подходящий маршрут. Расширяется только необходимая
часть; пригодные решения и результаты сохраняются, весь SDLC не запускается
заново автоматически. Полный маршрут возможен после согласования.

После прерывания агент сверяет фактическое состояние Git, доступные решения
и свидетельства, а при использовании трекера — его состояние. Подтверждённые
публикации и записи не повторяются вслепую. Если прежнее обязательное ревью
недоступно или неприменимо к текущей версии, оно проводится заново. История
чата не предполагается доступной новой сессии; отсутствие обязательного
журнала не позволяет выдумывать недостающие входы или подтверждения.

## 7. Граница поставки и совместимость

Принят один новый проектный flow: он отвечает за переходы и общий результат.
Самостоятельная переносимая база для этого flow не нужна: переносимые
методики этапов уже существуют. Реализация, ревью, публикация, подготовка
копии и операции трекера сохраняют существующих владельцев; flow не копирует
их алгоритмы и не становится общим диспетчером всех запросов RIS.

В объём входят необходимые доработки атомарных владельцев для режима без ID,
без обязательных файлов отчётности и с соразмерными проверками, команда,
документация и согласованный установленный комплект. Изменения должны
сохранить явные обязательные режимы соседних операций, в частности TDD-скилла,
а не молча отменить их контракт из вызывающего flow. Точный состав компонентов
и интерфейсы — предмет отдельного дизайна, ещё не принятого этой спецификацией.

Для применения в самом RIS в поставку включены адресные изменения его правил,
сейчас требующих учёта Beads, плана и файлов отчётности, а также согласование
обязательного делегирования с fast. Это не автоматическое ослабление правил
любого целевого проекта. До принятия/внедрения поправок действующие правила
соблюдаются. Общий полный workflow, багфикс-сценарий, релизы, deploy и PR-маршрут
не переустраиваются этой фичей.

## 8. Критерии приёмки поставки

Ссылки имеют вид `fast-task-execution#AC-nnn`. Проверки инструкций ниже —
чтение и независимое ревью контрактов, не живой запуск агентов.

- **AC-001:** команда явно вызывает новый проектный flow; инструкции допускают
  естественную просьбу и выбор агентом для уже порученной простой задачи.
- **AC-002:** достаточность определяется ясностью, последствиями и проверяемостью;
  понятный запрос не требует обязательных интервью, spec/design, декомпозиции
  или сохранённого плана. Контракты покрывают замену слова и простую правку конфига.
- **AC-003:** без требования учёта нет новой Beads-записи; существующий ID
  используется, а обязательный учёт проекта вызывает автоматическую короткую
  запись с проверкой идентичности. Отсутствие ID не блокирует доступный цикл.
- **AC-004:** подходящая текущая копия используется по умолчанию; необходимость
  изоляции или правила проекта включают подготовку отдельной копии;
  чужие изменения не присваиваются и не уничтожаются.
- **AC-005:** основной агент применяет атомарные операции непосредственно;
  независимое ревью фактически должно запускаться отдельным субагентом.
  Нет обязательного делегирования каждой операции и подмены ревью самопроверкой.
- **AC-006:** выбор проверок соразмерен последствиям, обязательные проектные
  проверки сохранены; новые тесты содержательны, TDD условен для fast,
  явный TDD-контракт соседней операции не обходится.
- **AC-007:** высокие/средние замечания требуют исправлений, проверок
  и независимого ревью; низкие не запускают обязательный ремонт/задачи/раунды.
  Недоступное ревью не заменяется заявлением об одобрении.
- **AC-008:** нет обязательных файлов отчётности или искусственного ID;
  свидетельства и ограничения отражаются в сессии, при Beads — краткий итог.
- **AC-009:** согласованный запуск разрешает полный цикл без отдельного
  подтверждения публикации; публикуется проверенная версия с применимым ревью,
  удалённый Git-результат подтверждается чтением.
- **AC-010:** при Beads отдельно проверяются итог/закрытие выбранной задачи
  и публикация трекера; push Git не подменяет эти действия и не закрывает предков.
- **AC-011:** требование PR, запрет push, недостающие права или обязательные
  проверки дают точную блокировку и сохранённый частичный результат;
  правила проекта не обходятся, полный успех не заявляется.
- **AC-012:** небольшое уточнение сохраняет fast; существенное усложнение
  вызывает адресное согласование и расширение только нужной части с сохранением
  пригодных результатов, без автоматического перезапуска полного процесса.
- **AC-013:** продолжение сверяет фактическое состояние и доступные свидетельства,
  не повторяет подтверждённые эффекты вслепую; утраченное/неприменимое ревью
  проводится заново, неизвестные решения не выдумываются.
- **AC-014:** один проектный flow композирует существующих владельцев;
  необходимые изменения их контрактов, правил самого RIS, документации,
  команды и source/install согласованы; новые обязательные слои и переносимая
  копия оркестрации не вводятся.
- **AC-015:** выполнены затронутые статические проверки и независимое ревью
  без высоких/средних замечаний; исполняемый код проверен необходимыми обычными
  тестами. Тесты поведения агентов не пишутся и не запускаются; чтение
  инструкций не объявляется доказательством runtime-надёжности или ускорения.

## 9. Источники, статусы и достаточность

Поведение §§1–6 и граница §7 подтверждены ответами пользователя в интервью:
последовательно выбраны варианты без Beads по умолчанию, без плана,
с основным исполнителем и отдельным ревью, с текущей копией, соразмерными
проверками, автоматической публикацией, адресным расширением и без файлов
отчётности; затем выбран direct-push-only и утверждена общая сводка.
AC-001–015 формализуют эти решения и применимые правила без новых этапов.
