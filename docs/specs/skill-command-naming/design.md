## 1. Контракт имён и владельцы

Канонический идентификатор:

```text
ris-<port|proj>-<op|flow|lib|adapter>-<verb-object|purpose>
```

- Только lowercase ASCII и одиночные дефисы; не более 64 символов по формату
  Agent Skills. Префикс и маркеры обязательны, отсутствующий маркер не имеет default.
- Один идентификатор у source-каталога, поля `name`, installed-каталога,
  command basename и slash-команды. Расширение `.md` не является частью имени.
- Для op/flow действие — глагол, затем различающий объект; окончание `-tdd`
  сохраняет обязательный режим проектной реализации. Опциональный TDD базы
  остаётся параметром её прежнего контракта, не вторым именем.
- Для lib/adapter указывается назначение/контракт, а не искусственный глагол.
- `-base` и `-tech` больше не отдельные типы нового пространства имён.
  Их семантика заменяется явными маркерами среды и ответственности.
- Пакетные скилы следуют схеме. Автор не навязывает префикс `ris-` чужим
  проектным скилам: их принадлежность и соглашения не меняются этой миграцией.

`skills/` — единственный редактируемый источник скилов с ресурсами;
`commands/opencode/` — источник команд. `.opencode/` — установленная копия.
Карта этого дизайна задаёт переход имён, но не создаёт runtime registry,
маршрутизатор, формат метаданных или новый граф зависимостей.

## 3. Обоснование неоднозначных классификаций

- Два flow владеют переходами между самостоятельно вызываемыми предметными
  стадиями: select/specify/design/publication и prepare/plan/implement/review/
  publication/completion. Их диапазон не расширяется: подготовка фичи по-прежнему
  заканчивается опубликованным ID без декомпозиции, выполнение — одной задачей.
- Авторы правил, roadmap/specify/design/decompose — op. Применение предметной
  базы, получение принятия, сохранение и read-back — необходимые части одного
  результата обёртки, не отдельный сквозной SDLC-маршрут.
- `complete-container` — op одной проверенной операции завершения контейнера.
  Проверка критериев, запись evidence и отдельное закрытие — её внутренний
  протокол. Она не запускает реализацию, публикацию Git или завершение предков.
  Применение portable verify и adapter не превращает её в workflow.
- `prepare-task-worktree` и portable `prepare-worktree` — op готовой копии/
  environment handoff; технические действия/claim не начинают следующую стадию.
- Ретроспектива — op отчёта; сбор истории и необязательное делегирование
  не превращаются в orchestration всего SDLC. Это не запуск расследуемой сессии.
- `proj` означает RIS-интеграцию контракта, не обязательное наличие ris.yaml,
  Beads или execution роли у каждого скила. `author-skill` использует общие
  RIS-правила, но контекст проекта загружает только при прежнем условии.
- Общая библиотека — proj-lib, так как это общий процесс RIS, а не универсальная
  методика с отдельным предметным результатом. `resolve-context` — proj-op:
  есть собственный проверяемый read-only результат и прямой вызов.
- Git/Worktrunk адаптеры не требуют common/context/config/tracker по своим
  SKILL.md и потому port-adapter. Beads адаптер требует ris-common и условно
  context, поэтому proj-adapter. CLI-инструменты сами по себе не определяют среду.
- `manage-okf-bundle` сохраняет read/create/edit/check и прежние явные root/
  operation/scope. Это один форматный контракт, не новый универсальный диспетчер.
- `publish-task` не означает tracker completion/push, deploy или PR: предмет
  остаётся прежним — интеграция в установленную primary branch и Git push.
  Слово main убрано из имени, поскольку literal main не требуется контрактом.

Новых скилов, пар base/wrapper и обязательных зависимостей не добавляется.
Методики остаются у своих владельцев; меняются идентификаторы и их употребление.

## 4. Командный интерфейс

Каждый из 37 command-файлов имеет обычный OpenCode description и `$ARGUMENTS`,
загружает один явно выбранный по имени скил и следует его текущему контракту.
Обработка пустого запроса остаётся предметной: вопрос о недостающем входе,
read-only выбор или recovery допускаются только там, где уже предусмотрены.
Нельзя добавлять общий запрет пустых аргументов поверх существующего autoselect.
Прямые операции не требуют исполнения в субагенте только из-за наличия команды;
workflow сохраняют свои действующие правила фактического запуска исполнителей.

Полная карта восьми прежних команд:

| Старая команда | Новая команда |
|---|---|
| `/ris-author` | `/ris-port-op-author-skill` для автономного результата; `/ris-proj-op-author-skill` для RIS-интегрированного |
| `/ris-plan-roadmap` | `/ris-proj-op-plan-roadmap` |
| `/ris-next` | `/ris-proj-op-select-feature` |
| `/ris-interview` | `/ris-port-op-interview` |
| `/ris-interview-feature` | `/ris-proj-op-interview-feature` |
| `/ris-prepare-feature-work` | `/ris-proj-flow-prepare-feature` |
| `/ris-execute-task` | `/ris-proj-flow-execute-task` |
| `/ris-retrospect-session` | `/ris-proj-op-retrospect-session` |

Прежний author-маршрутизатор заменяется двумя явными входами без старой команды.
Текущая защита RIS-автора от ошибочно выбранного автономного предмета сохраняется;
шаблон команды сам не определяет среду по присутствию ris.yaml и не переключает
вызванный скил. Новая команда не снимает прежние gates скила и не даёт новых прав.
Адаптерные операции остаются доступны через скилы/их вызовы, без прямых команд
и без новой команды tasks, скрывающей библиотечный или адаптерный контракт.

## 5. Области миграции и сохранение истории

Один интеграционный владелец выпускает согласованную ревизию. До файловой правки
исполнитель сверяет actual HEAD, карту, dirty paths и принадлежность изменений.
Параллельная файловая работа требует отдельной рабочей копии по правилам проекта.

Порядок подготовки единого изменения:

1. Перенести каталоги source с ресурсами, обновить name и текущие зависимости,
   текстовые/файловые ссылки, примеры и инструкционные скрипты, где имя операционно.
   Относительные ресурсы остаются внутри владельца; содержимое форматов/данных
   и атрибуция pinned OKF не изменяются из-за переименования.
2. Заменить восемь старых command-файлов новым полным набором 37. У lib/adapter
   не создаются командные фасады. Обновить README-команды/примеры.
3. Обновить действующие AGENTS.md, ris.yaml (`adapters.tasks.skill`), нормативные
   правила именования/ссылки и фактическую карту архитектуры. Execution role IDs,
   имена general и формат конфигурации v2 не меняются: это не имена скилов.
4. Для норм в docs/product и docs/rules применить проектный OKF-владелец
   к конкретным выбранным бандлам и затронутым индексам; docs/specs остаётся
   обычным Markdown. Не переписывать весь корпус ради удаления строки старого имени.
5. Старые принятые specs/design/acceptance, immutable refs, отчёты и закрытые
   Beads-записи сохранять как историю. Действующая нормативная секция именования
   получает новую норму; переходные указатели и таблица объясняют старые имена.
   Не менять содержащий старое имя принятый snapshot и не переиздавать прежнее
   `containing-commit` решение как принятие обновлённого текста.
6. Проверить активные планы/задачи на связанные старые адреса. Предложить адресный
   impact их владельцам; менять их записи только с нужными правами и защитой
   конкурентной записи через выбранный adapter. Массовое обновление трекера
   или локальных заметок других задач не часть механической замены.
7. Синхронизировать локальную установку пакетных скилов и команд с source.
   Удалить именно выбывшие элементы карты, сохранить сторонние grilling/grillme,
   конфигурацию клиента и проектные материалы. Проверить состав/байты/ресурсы.
8. Проверить общее дерево, независимое ревью и разрешённую публикацию по правилам.
   Это один совместимый комплект; промежуточное смешение имён не публикуется.

Инструкция для целевого проекта использует ту же карту: выбрать одну ревизию
пакета, проверить старую установку/потребителей, заменить пакетные элементы,
обновить явные ссылки и ris.yaml, удалить прежние имена, сопоставить состав и
ресурсы, перезапустить OpenCode. При частичной файловой ошибке сообщить точный
остаток и завершить согласованную замену либо восстановить прежний комплект;
смешанное состояние не объявлять пригодным. Новый recovery-установщик здесь
не создаётся; отдельный installer можно применять лишь после его реализации.
Внешние проекты не изменяются самим сохранением этой инструкции.

## 6. Адресный impact на package-installation

Это отдельная принятая будущая поставка с Git-базой
`51da1068b2124c0cb6de8a87912e0375be7524f4`, контейнером `ris-lr1`,
задачами W1 `ris-lr1.1` и W2 `ris-lr1.2`. Исходников установщика пока нет.
Новая карта 41 не включает несуществующий management-скил.

**Предлагаемая поправка интерфейса**, требующая явного согласования:

```text
Будущий скил:    ris-manage-installation → ris-port-op-manage-installation
Будущая команда: /ris-manage             → /ris-port-op-manage-installation
Будущий script:  skills/ris-port-op-manage-installation/scripts/ris-install.sh
```

Среда port: установка не требует инициализированного RIS-проекта. Тип op:
каждый вызов выполняет выбранную install/update/uninstall, а не SDLC-workflow.
Поправка затрагивает package-installation#AC-013, интерфейс §6, D1 §2,
W1 script/bootstrap path и W2 skill/command paths/интеграционную проверку.
Один CLI, shell/dependencies, алгоритм journal/rollback и остальные требования
не меняются. Будущий итог, если этот скил будет реализован и включён в общую
ревизию, станет 42 скила/38 команд; это отдельный delta, не текущая инвентаризация.

До зависимой реализации владелец должен сохранить отдельно принятую scoped
поправку к требованиям и дизайну package-installation, обновить task inputs
с нужными гарантиями и опубликовать фактические refs. Старые принятия сохраняются.
Само принятие D1 именования не выдаётся за это отдельное решение соседней фичи.
В этой подготовке соседние файлы/записи и блокирующие связи не изменяются.
Применимая последовательность работ определяется при отдельной декомпозиции
по фактической готовности обеих инициатив; технически неоднозначный блокер
не добавляется предположением. Независимая часть унификации может готовиться.

discovery клиентом или прохождение agent workflow. Поведенческие агентские
тесты запрещены правилами проекта и не планируются. Не создаётся постоянный
тестовый harness ради проверки текстовых инструкций.

## 8. Принятие и передача

Пользователю предъявляются полная карта, классификация complete-container как op,
37 одинаково именованных команд и конкретный impact установщика. Требуется
отдельное решение D1; требования v1 не перепринимаются из-за выбора имён.
После принятия сохранить design.md и отдельное решение с точной областью/
версией; до публикации refs pending. Декомпозиция и запуск реализации —
следующие отдельно разрешаемые операции. Кандидат не создаёт ADR, feature-record
или свидетельство реализации. Собственная локальная заметка не является
обязательным удалённым входом для будущей задачи.
