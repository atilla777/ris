## 2. Достаточность и актуальность каталога

Карта D1 полностью совпадает с 41 фактическим `skills/*/SKILL.md`.
Каталоги совпадают с текущими `name`; все новые имена уникальны, допустимы
и не длиннее 64 символов. 35 op + 2 flow дают 37 команд; 1 lib + 3 adapter
не получают команд. Все восемь нынешних command basenames представлены в §4 D1,
включая два явных преемника `/ris-author`.

`skills/`, `commands/opencode/`, `.opencode/`, AGENTS.md, ris.yaml,
docs/concepts и docs/rules не имеют tracked delta к проверенной базе.
92 пакетных source-файла вместе с ресурсами совпадают с installed-копиями
по составу, байтам, типам и modes; восемь команд также совпадают.
Сторонние `grilling` и `grillme.md` присутствуют и сохраняются.

Уточнение файловой инвентаризации: в обоих skill roots остаются пустые деревья
`ris-beads-tech/` (с пустым references/), `ris-implement-task/`, `ris-project-okf/`.
В них нет SKILL.md, файлов или symlinks; это не ещё три скила и не delta к карте.
При будущей миграции проверить принадлежность этих остатков и убрать именно
подтверждённые пустые выбывшие деревья, чтобы проверка отсутствия старых имён
охватывала физическую установку. В этой подготовке каталоги не удаляются.

Дизайн определяет владельцев, классификацию неоднозначных операций, контракт
тонких команд, области миграции, исторические исключения и статические oracle
всех AC. §§1–8 сохранённого D1 совпадают с принятым кандидатом; его прежнее
независимое ревью применимо к неизменённому содержанию. Наблюдаемого изменения
каталога или нового конфликта ответственности нет. Дополнительное исследование,
новый ADR, workflow, registry или технический redesign для разбиения не нужны.
Будущий management-скил установщика отсутствует и не включён в эти 41/37.

## 4. Минимальное разбиение: одна задача U

**U — локальная метка предложения, не Beads ID.**
Будущий тип: самостоятельный обычный `task`, без parent и feature-record.
Устойчивый ключ: `ris:skill-command-naming:delivery:v1`.
Предлагаемый title: **«Поставить единые имена скилов и команд RIS без алиасов»**.

**Результат:** одна согласованная интегрированная ревизия пакета, собственной
локальной установки, действующих потребителей и инструкции целевого перехода
по v1/D1; все AC-001–AC-011 проверены на одном итоговом дереве.

**Границы содержания будущей записи:**

- Полная карта D1: перенести все 41 source skills с ресурсами, обновить `name`,
  зависимости и операционные ссылки; сохранить алгоритмы, предметные права,
  условия загрузки ресурсов, входов и остановки.
- Поставить 37 тонких одноимённых команд op/flow взамен восьми старых;
  `$ARGUMENTS`, один явный target, прежний empty-input/recovery contract,
  без выбора port/proj за пользователя и без команд lib/adapter.
- Согласовать активные указатели, AGENTS.md, ris.yaml adapter selection,
  README/примеры, действующие нормы и карту архитектуры; role IDs, `general`
  и configuration v2 остаются прежними. Для реальных OKF-бандлов concepts/rules
  применять проектного OKF-владельца с явными root/operation/scope.
- Синхронизировать полный пакет с `.opencode/skills/` и `.opencode/command/`,
  удалить выбывшие имена/алиасы и проверенные пустые остатки; сохранить сторонние
  элементы и клиентскую конфигурацию. Редактируемые источники — skills/commands.
- Дать целевым проектам комплект одной ревизии, полную таблицу 41 скила/8 старых
  команд и инструкцию: независимый target root, смена потребителей/config,
  удаление старого набора, сверка состава/ресурсов, действия при частичной
  ошибке и restart OpenCode. Автоматического установщика здесь нет.
- Разделить активные ссылки и историю: принятые snapshots, immutable refs,
  старые decisions/отчёты/закрытые задачи не переписывать механически;
  оставшиеся старые имена объяснить переходным указателем/историческим смыслом.
  Новые найденные impacts активных задач согласовывать адресно через адаптер.

**Исключения:** installer и его W1/W2, новые workflow, новые предметные функции,
рефакторинг методик/разрешений, alias layer, массовая правка истории/трекера,
автоматическое изменение внешних проектов. Поведенческие агентские тесты
не писать и не запускать; статическое review не объявлять runtime-наблюдением.

**Проверяемое завершение U:** матрица ниже пройдена на общей интегрированной
ревизии; source/install parity включает ресурсы и удаление выбывших элементов;
классификация/команды/сохранность контрактов и истории прошли независимое ревью
без высоких/средних замечаний. Проверки и применимость evidence привязаны к
точному итоговому дереву и фактически опубликованному Git commit; закрытие U
в Beads — отдельная проверенная операция, публикация Dolt также отдельная.
Одно закрытие ris-bsy, наличие новых файлов или промежуточный commit не являются
завершением U. Реализация U требует отдельного поручения.

**Почему одна задача достаточна:** это координированная смена публичного
namespace без смены алгоритмов. Отдельно опубликованные source-only,
commands-only, docs-only или install-only результаты оставили бы смешанный
несовместимый комплект. Они не самостоятельные пригодные поставки.
Число файлов само по себе не оправдывает разбиение. Один интеграционный
владелец сохраняет целостность; docs, проверки и review — критерии этой же
задачи, не формальные дети/отдельная приёмочная задача. Контейнер-копия над
единственным ребёнком также не нужен. Между частями U графовых blockers нет.

## 6. Установщик: минимальный направленный граф

Существующая связь сохраняется: **`ris-lr1.2 → ris-lr1.1` (`blocks`)**.
После подтверждения реального ID U необходимо добавить ровно одну новую
связь: **`ris-lr1.1 → U` (`blocks`, blocked → prerequisite)**.
Она запрещает продолжение W1 до завершения полного согласованного комплекта;
W2 блокируется транзитивно через W1. Прямое W2 → U дублировало бы тот же путь.
Контейнер ris-lr1 сохраняет обязательный состав W1/W2 и не закрывается по
одному статусу детей: дополнительный container → U не нужен для этого порядка.
`parent-child` остаётся принадлежностью, не blocker. Цикла в предложенном графе нет.

Нельзя заменить U на ris-bsy или задачу публикации документов. Продолжение
installer также требует фактически опубликованной N1 с решениями, свежей
сверки каталога и проверенного завершения U; open/ready не отменяет gates.
Новые 42-й скил/38-я команда принадлежат будущему installer, не задаче U.

Сейчас новый edge **не записан**: подтверждённого endpoint U нет. Его
межинициативный характер требует явной tool-specific blocking операции
выбранного адаптера; это не common tasks.dependencies.add внутри feature scope.
Перед записью перечитать endpoints, обязательный состав и typed blockers,
проверить направление/цикл и требуемую защиту структуры. `bd --sandbox`, claim
или read/write/read сами по себе не являются такой защитой. Если необходимый
предикат не покрыт нативной операцией/реальной координацией, остановить именно
эту запись с точной диагностикой, не устанавливая координатор скрытно.

## 7. Запись, ограничения и безопасное продолжение

Применён `ris-decompose-spec-base`: выведен один результат, проверены AC,
исключения, seams, совместная проверка и необходимая зависимость.
Контракт `ris-decompose-feature` проверен, но его полный feature-record маршрут
неприменим: ris-bsy — подготовка без feature-record/эпика и опубликованных refs.
Он не даёт права объявить такую запись принятой опубликованной фичей.

Адаптер предоставляет полные tasks v1 reads; ordinary tool-specific task create
позволяет самостоятельные работы без искусственного parent. Create — best-effort
с all-state collision search/read-back, не строгая уникальность external-ref.
Нативный append-notes объединяет дополнение с актуальной строкой; общая
revision CAS содержания и структуры в bd 1.3.1 не предоставляется.
Для этой поставки сохраняются требования проектной процедуры к реальным
опубликованным входам реализации: обычный task не используется как обход.

Заблокированная запись: создание/переиспользование **реализационной** U с
достаточными опубликованными spec/design/decision refs. Таких refs нет;
создание placeholder с pending evidence не выдаётся за исполненную декомпозицию.
Следствие — заблокирован новый installer edge. Требуемые гарантии будущей
структурной записи ещё предстоит установить; отсутствие полного CAS не мешает
независимому анализу, документу и нативному дополнению notes подготовки.

Для продолжения после отдельно разрешённой публикации:

1. Сверить фактические неизменённые v1/D1/N1/решения и published Git refs.
   Не перепринимать и не перепривязывать старые решения ради свежего SHA;
   `containing-commit` разрешать только по реальной совместной публикации.
2. Через выбранный адаптер повторить all-state поиск по ключу U, spec и
   содержанию; переиспользовать только совпадающую самостоятельную task,
   иначе создать одну по §4 с реальными опубликованными ссылками. Проверить
   фактические ID/type/parent/content/status/key и отсутствие дублей best-effort.
3. Проверить граф/гарантии и добавить только отсутствующий ris-lr1.1 → U;
   перечитать обе стороны, W1/W2 membership и W2 → W1. Не менять историю installer.
4. Отдельно проверять разрешённую Dolt-публикацию всего исходящего состава
   и независимый remote read-back. Реализацию не начинать без её поручения.

Это handoff из документа, а не второй файловый реестр состояний: актуальные
ID/состояния/связи всегда заново читаются в Beads.
