# RIS — руководство по разработке

RIS — набор готовых скиллов для AI-агентов, помогающих решать задачи на этапах жизненного цикла разработки ПО. Перед работой ознакомься с [README.md](../../README.md) и относящимися к поручению материалами проекта. Не считай планы или идеи уже реализованными возможностями.

Доводи согласованную задачу до результата без пауз ради формального подтверждения: если нет вопросов к пользователю или препятствий, продолжай работу, проверки и завершение задачи. После реализации, необходимых проверок и ревью **публикуй подлежащие публикации изменения: сделай коммит и отправь его в настроенный удалённый репозиторий без отдельного запроса разрешения**. После подтверждения публикации в рамках той же работы отдельно заверши согласованную задачу в Beads по пункту 8, не ожидая дополнительного запроса пользователя. Проверь успешность отправки до сообщения о завершении; если публикация не удалась, сообщи об этом и не называй результат опубликованным или задачу завершённой. Локальную папку `tasks/` в Git не добавляй. Это не отменяет согласования объёма и критериев до реализации.

## Задачи разработки

Адресная [поправка ris-y8z, S1/D1](../specs/ris-y8z/spec.md) заменяет прежние
primary-sync/полнота-поставки нормы: проверенный remote Git-результат завершён
независимо от локального обновления. Занятая/небезопасная основная копия остаётся
нетронутой и не блокирует отдельные exact close/Dolt. Явно порученное локальное
обновление остаётся отдельной невыполненной частью именно этого поручения.
Полное поручение включает штатные действия выбранной операции и переходы между
существующими владельцами без повторного разрешения; узкие ограничения сохраняются.
Технические факты исследуются самостоятельно, вопросы — только о существенном
решении, конфликте или недостающих полномочиях; техническая ошибка — точный блокер.
Своя ветка и выделенный worktree для всех versioned Git-project edits, claim/blockers,
принятие, проверки, независимое ревью точного снимка и non-force не ослабляются.

Адресная принятая [поправка ris-wcv](../specs/ris-wcv/spec.md) заменяет прежние
feature-record/same-record refs и обязательное saved verification: новые документы
фичи находятся в `sources.specs/<full feature ID>/spec.md`, читаемый H1, затем
column-zero Feature-ID/Summary/optional Keywords; дизайн inline либо design.md.
Реальные отдельные принятия scope/version и исходная provenance сохраняются,
Beads не дублирует accepted refs/готовность. Старые ссылки/readable payload hints
ведут к фактическим документам/решениям без schema gate, миграции или переноса;
missing/old/malformed JSON сам по себе не блокер. Ordinary/document-only/bug не
получают искусственный feature ID/каталог. Versioned bug basis и независимый review YAML
сохраняются. При verify-and-close фичи достаточно успешной содержательной текущей
проверки и native exact close: обязательная предварительная запись verification/
результата не нужна; краткий ordinary итог допустим. Остальные quality/Git/close/
Dolt gates не ослабляются. Исторические спецификации/данные не переписываются;
противоположные нормы ниже заменены только в этой области.

Адресная поправка подготовки фичи по принятым [S1 §3 / D1 §§2–4](../specs/sdlc-feature-lifecycle/acceptance.md): `ris-proj-flow-prepare-feature` рано регистрирует выбранную фичу, использует одну ID-associated safe copy до документов и один requirements/design dialogue. Один явный акт может точно принять две полные различимые области/версии; каждый owner проверяет своё принятие, неизменённое не перепринимается. Достаточный inline design не требует design.md/ADR. После independent review и подтверждённой remote Git-публикации обновляется та же запись и применяется полная existing decomposition, в своей сессии либо исполнителе, до one-task или verified children/необходимых directed blocks и отдельной tracker publication. Для внутренних действий этого flow не обязателен отдельный executor; reviewer фактически независим от всех авторов/исправителей. Direct specify/design/decompose сохраняют scoped контракты, не запускают друг друга. Исторические спецификации подготовки сохраняются, их противоположные нормы заменены только в этой области; prepare не запускает реализацию.

Поправка исполнения по тем же принятым **S1 §4 / D1 §5**: full task/bug/direct
implementation начинается из достаточных принятых входов и актуального кода без
planner, сохранённого плана, его approval/readiness или omission-decision.
Исполнитель выбирает жизнеспособный подход в принятой архитектуре, соблюдает TDD
и текущие quality gates. Обязательные implementation/progress отчёты удалены без
заменяющего файла/журнала и без распределения их полей в review/Beads. Старые планы
и заметки — необязательный контекст. История RED/GREEN не требуется для допуска
review/recovery/publication и не восстанавливается задним числом; неизвестное не
выдаётся за доказанный TDD, известное нарушение не скрывается. Reviewer оценивает
итоговый результат и применимые текущие проверки. Full flow может непосредственно
применять владельцев и переиспользовать пригодный implementation/repair context;
независимый reviewer фактически запускается отдельно от всех авторов/исправителей.
Bugfix использует воспроизводимый исторический basis по [единой норме product §4.1](../product/06-artifacts-and-handoff.md#41-воспроизводимое-основание-bugfix):
точная версия трекера и immutable Git sources/decisions вместо обязательного полного
snapshot в notes или нового файла. Полноту чтения/locator append/retry проверяет
адаптер; старые snapshots/история сохраняются. Claim/blockers/copy, full YAML, non-force Git и отдельные
result/exact close/Dolt gates сохранены. Исторические противоположные нормы заменены
только в этой области.

Выбирай наименее затратную проверку, достаточную для конкретного утверждения; различай обязательные проверки, условные проверки с явными условиями запуска и исследовательские эксперименты. Не превращай перечень возможных сценариев в обязательную матрицу: переиспользуй применимые свидетельства и повторяй затронутые проверки. **Не пиши и не запускай тесты для проверки поведения агентов, включая живые прогоны и сценарные тестовые сессии: такие проверки чрезмерно увеличивают длительность работы. Проверяй инструкции агентов чтением и ревью; не выдавай это за подтверждение поведения в живом запуске.** При подтверждённом конфликте принятого контракта с платформой или существенном росте стоимости проверки своевременно верни вопрос пользователю до продолжения зависимых экспериментов; независимую полезную работу можно продолжать. Ограничивай поручения субагентам проверяемым промежуточным результатом и условиями раннего возврата, передавай относящиеся к делу входы и версии вместо всей накопленной истории. Обязательные проверки не сокращай молча: согласуй изменение объёма, явно укажи невыполненные проверки и границы выводов, не объявляй их пройденными. Это не отменяет TDD, независимое ревью и проверки публикации там, где они обязательны.

Обычная доработка инструкций завершается после предусмотренных статических проверок и независимого ревью: отсутствие live run не создаёт блокера и не требует повторного вопроса о запуске. Имена, ресурсы, зависимости и source/install parity проверяются статически; исполняемые программы — необходимыми обычными тестами. Выводы о надёжности, стоимости и повторяемости поведения агента допустимы только в пределах применимых имеющихся наблюдений. Старые поведенческие обязательства и непроверенные результаты не становятся pass; специальная работа с явно принятой поведенческой целью требует отдельного согласования объёма и не разрешает обходить запрет выше. Подробное разделение доказательств — в [05](../product/05-adoption-and-validation.md#4-три-уровня-проверки) и [07](../product/07-quality-and-verification.md#2-критерий-и-подтверждение).

Источник истины для очереди, состояния и зависимостей задач разработки **этого проекта** — Beads (Dolt), выбранный в корневом `ris.yaml` через `adapters.tasks.skill: ris-proj-adapter-beads-tasks`. Перед изменениями подтвердить проект командой `bd where`/`bd context`; для полной выборки задач (включая закрытые) использовать `bd list --all --limit 0 --type task --json`, для эпиков — такую же выборку с `--type epic`, для конкретного ID — `bd show <id> --json`. Не считать порядок выдачи приоритетом или наличие эпика разрешением начать задачу. Историческая игнорируемая Git папка `tasks/` содержит завершённые `PLAN-001`–`PLAN-054`, не является действующей очередью и не является настроенным `workspace.tasks`:

- [`tasks/RIS.md`](../../tasks/RIS.md) и [`tasks/RIS - roadmap.md`](../../tasks/RIS%20-%20roadmap.md) — исторические указатели;
- [`tasks/RIS - backlog.md`](../../tasks/RIS%20-%20backlog.md) и [`tasks/RIS - archive.md`](../../tasks/RIS%20-%20archive.md) — снимок очереди и архив периода `PLAN-*`, не изменяемые списки состояний Beads;
- [`tasks/RIS - inbox.md`](../../tasks/RIS%20-%20inbox.md) — исторические идеи периода `PLAN-*`;
- `tasks/PLAN-NNN - <название>.md` — сохранённая история прежних задач. Новые номера `PLAN-*` не назначать, закрытые задачи задним числом в Beads не создавать.

Локальный отчёт ревью **новой** задачи находится в `workspace.tasks/<подтверждённый Beads ID>/review.yaml` исходной папки, для RIS это `.sdlc/tasks/<ID>/` по корневому `ris.yaml`. План/implementation-журнал не требуется. Каталог игнорируется Git: автоматическая удалённая доступность не обещается. В Beads сохранять достаточные цель, границы, критерии, ссылки на опубликованные спецификации и краткий проверяемый итог с опубликованным Git-коммитом; не ссылаться на локальный журнал как на обязательный удалённый вход. Принятые спецификации публиковать в `docs/specs/`. Context вычисляет обычную source folder из фактического общего `.git` в схеме один repo — один project, с проверкой physical path/registration/current-copy association, без saved-primary discovery, сканирования или другого worktree fallback. Bare/missing source/nonordinary layout блокирует зависимую shared-path операцию. Относительные workspace paths — от source folder: отсутствующие leaves получают `.sdlc/tasks/` и `.sdlc/worktrees/` даже в выбранном валидном config, явные leaf overrides их заменяют; sources/adapters/roles не дополняются. Отсутствие выходной папки не выбирает другой путь: её создаёт разрешённая операция. Sources — из текущей worktree-копии. Найденный root не разрешает менять source checkout.

Все версионируемые Git-изменения, включая simple-task, общие документы, `AGENTS.md`
и `ris.yaml`, выполняются в выделенном worktree своей работы. Подготовкой/reuse
владеет `ris-proj-op-prepare-task-worktree`, portable method и выбранный adapter;
для действительно no-ID документов допустима явно подтверждённая отдельная копия
через portable preparer без искусственного ID. Одна пригодная копия переиспользуется
между стадиями/сессиями; исходная папка не площадка разработки. Установка/обновление
пишет в явный target без Git; согласованный первоначальный bootstrap без Git
допускает local writes. После появления пригодного Git-репозитория versioned edits требуют
worktree, без автоматического переноса чужих/грязных bootstrap-файлов. Общие
Beads/Dolt и локальные evidence остаются ресурсами своих владельцев, не изолированы worktree.

Подготовка копии и полный task flow по умолчанию не создают и не требуют
`worktree.md`, `execution.md` или равноценного журнала переходов в файле/Beads.
Независимый отчёт ревью и достаточный итог Beads сохраняются, без плана/журнала
реализации или записи каждого перехода. Переход сверяет
живые Git/Beads-факты, опубликованные версии и доступный точный результат владельца.
Старые журналы — подсказки, не обязательный или авторитетный вход. Неизвестные
association, снимок проверки или независимость ревью блокируют зависимый шаг с
точной причиной, но не из-за отсутствия журнала как такового. Для нестандартной
association, неидемпотентного setup, оставшегося процесса или неоднозначного эффекта
до зависимого необратимого действия нужен компактный адресуемый результат в уже
разрешённом канале; если его нельзя сохранить/восстановить, действие блокируется.
Обычный create без hooks/setup проверяет регистрации, target/ref, pinned base и
новую копию, без обхода/хеширования всех файлов primary и соседних worktree и без
заявления об их байтовой неизменности. Reuse и hooks/setup проверяют соответственно
выбранную копию и конкретные защищаемые ресурсы/выходы по последствиям.

### Узкое исключение: явно выбранный fast

Для явно выбранного `ris-proj-flow-execute-simple-task` (`/risp-run-simple-task`)
применяется принятое [D2, §§4–6](../specs/fast-task-execution/design.md):

- Понятное поручение с границами, критериями и достаточным способом проверки
  допускается без обязательных этапов интервью/spec/design/декомпозиции/плана.
  Файлы `plan.md`, журнала выполнения/реализации и отчёта ревью не обязательны;
  достаточные входы, проверки, независимый вывод ревью, решения по замечаниям и
  факты публикации сохраняются в сессии. Дополнительные файлы — по конкретной
  необходимости или явно согласованному требованию, не для имитации этапов.
- **Краткий учёт Beads в RIS обязателен.** Переданный ID используется с его
  действительным типом, принятыми входами и ограничениями. Без ID сначала сверяется
  идентичность во всей относящейся all-status выборке; затем создаётся/сверяется
  короткая ordinary-задача с атрибутированным поручением, границами, критериями и
  принятыми ограничениями, без искусственных spec/design-ссылок. Свежие claim,
  ownership, children и направленные blocker gates сохраняются.
- Основной агент непосредственно применяет существующих владельцев реализации,
  документации, подготовки копии, Git-публикации и трекера. Только ревью обязательно
  фактически запускается отдельно в независимом от всех авторов/исправителей
  субагенте `task-review`; настроенное имя не доказывает запуск. High/medium требуют
  исправлений, затронутых проверок и свежего независимого ревью. Low достаточно
  рассмотреть и зафиксировать решение в сессии, без обязательной задачи/раунда.
- Собственная ветка в выделенном worktree обязательна через того же preparer,
  что full/feature/bug. Подтверждённая пригодная копия переиспользуется, а не создаётся
  для каждого этапа. Flow не создаёт/переключает ветку в исходной папке; чужая работа
  сохраняется, source checkout не площадка разработки/интеграции или branch return.
- Проверки соразмерны последствиям: текст — результат/diff, конфигурация —
  применимая валидация, логика — содержательные затронутые тесты. Обязательные
  проверки и требуемый проектом TDD сохраняются; тесты поведения агентов запрещены.
- После verified Git publication в Beads сохраняется краткий удалённо достаточный
  итог, проверки/ревью и ограничения с Git SHA; затем отдельно проверяются exact
  close и разрешённая Dolt-публикация по действующим правилам ниже. Локальный
  журнал не обязательный удалённый вход. Предки автоматически не закрываются.

Это исключение к обязательному review-файлу пункта 6 только выбранного fast,
не к worktree-first. Полный task flow,
bugfix/feature-контракты и
`ris-proj-op-implement-task-tdd` с обязательным TDD сохраняют свои требования.
Переданный feature/bug не понижается до ordinary ради обхода подготовки/приёмки.
Недоступное ревью/обязательная проверка, PR-only или запрет direct push блокируют
зависимую публикацию; существенное новое решение возвращается адресно человеку.
При продолжении сверяются реальные эффекты и применимость evidence; отсутствие
журнала не позволяет выдумывать прежнее принятие или pass.

Порядок работы (с указанным fast-only исключением):

1. Перед планированием или началом задачи прочитай актуальные Beads-задачи и эпики, их связи и относящиеся к делу проектные документы. Сырые идеи обсуди до оформления задачи; не веди параллельный изменяемый inbox или backlog в файле. Сверь все состояния перед созданием записи: если задача уже существует (например, `ris-p20.1`), используй её подтверждённый ID, не создавай дубль. Задачи, относящиеся к фиче, связывай с её подтверждённым родителем; самостоятельные работы не прикрепляй к эпику искусственно.
2. После прояснения проблемы, результата, границ и критериев и разрешения на запись создавай задачу в Beads через выбранный адаптер с устойчивым ключом для повторной сверки. Проверяй фактический ID, содержание, состояние и связи после записи; отсутствие дублей при конкурентном создании не гарантируется. Перед новой записью или повтором сверяй полную выборку, включая закрытые задачи. Не веди одновременно изменяемый файловый список задач.
3. Согласуй с пользователем объём и критерии задачи до реализации. Каждый агент одновременно выполняет не более одной задачи разработки RIS; разные агенты могут выполнять разные согласованные задачи по правилам параллельной работы ниже. Состояние Beads не является само по себе разрешением приступить к реализации.
   После обсуждения и явного утверждения требований к новому результату или изменению предложи сохранить их как спецификацию в `docs/specs/` и запланировать исполнение в Beads. Если пользователь согласен, зафиксируй принятые решения и проверяемые критерии так, чтобы реализацию можно было начать в новой сессии без истории чата, независимо от локальных заметок. Не создавай повторную спецификацию, если подходящая уже сохранена; утверждение требований само по себе не разрешает запуск отдельной задачи реализации.
   Для спецификации нового скила RIS оцени, уместна ли самостоятельная переносимая методика и отдельный проектный скил по [архитектуре](../product/01-architecture.md). Зафиксируй принятое разделение ответственности или причину выбора одного скила; не требуй пары формально.
    При подготовке и ревью спецификации скила проверь владельца каждого дополнительного действия, различимость соседних операций, типичный объём загружаемых инструкций и условия редких веток по [критериям проверки](../product/05-adoption-and-validation.md). Не переносить чужую ответственность в скил или ресурс только ради удобства; не дробить необходимый шаг ради уменьшения числа строк.
    Для скила RIS также различай самостоятельную методику, операционную обёртку и сквозной сценарий: отдельная обёртка не назначает следующий скил, сценарий отвечает за переходы и совокупный результат. Оценка роли исполнителя и проектной конфигурации обязательна только там, где это требуется конкретному вызывающему; поддержка `execution` в `ris-proj-op-resolve-context` готовит имена агентов, но не доказывает их доступность или запуск.
4. Для согласованной задачи проверь достаточность принятых входов и актуальный код, выбери подход внутри принятой архитектуры и выполни реализацию/проверки. Не создавай отдельный план, implementation-report или заменяющий журнал. После реализации проверь относящиеся к изменению результаты и итоговый diff.
5. После реализации запусти ревью сделанных изменений в субагенте. Передай ему требования задачи, правила проекта и итоговый diff. Ревью должно проверить, что требования выполнены, правила проекта соблюдены, а в коде и бизнес-логике решения нет ошибок. Для изменений без кода проверяй применимые к ним требования и корректность результата. При разработке или изменении скила RIS ревью отдельно проверяет принятое решение о декомпозиции, переносимость базового скила (если он выделен), границы RIS-интеграции, ответственность за общий результат, отсутствие чужих операций и ненужной обязательной загрузки по [критериям](../product/05-adoption-and-validation.md).
6. Оформи обычное проектное ревью одним компактным локальным `workspace.tasks/<ID>/review.yaml` по [единственному владельцу формата](../../skills/ris-proj-op-review-task/references/report-format.md), без Markdown-дубля. Новый файл — `ris.review/2`; существующий `/1` читается и продолжается по условному прежнему контракту без переписывания/миграции. Без ID нужен явный разрешённый локальный путь. Для замечания — стабильный ID, место, описание причины и необходимой правки, ровно одна критичность **high/medium/low** (в представлении: **высокий/средний/низкий**). Сохраняй append-only раунды, точные Git tree/base/exclusions, версионированные входы, содержательную assessment/checks, ограничения и actual independent provenance. В `/2` нет шести фиксированных coverage mappings, per-check tree, previous или повторения прошлых findings; dispositions адресуют прежние IDs по owner. Области оценки не исчезают. Форматная корректность отдельно от допуска: approved не заменяет snapshot/evidence/реальную независимость, поздний adverse/blocked/invalid/unknown не обходится старым approval. Машинный verdict: применимый независимый approved завершает цикл; changes_required требует исправления и нового ревью; blocked/missing/invalid/unsupported останавливает зависимое продвижение для недостающего факта, а не бесконечного repair loop. В Beads — только адрес/раунд, не копия verdict/findings. Отчёт локален и не публикуется автоматически. Fast сохраняет no-file исключение; optional save — тот же выбор схемы. Утраченное ревью восстанавливается точно либо проводится новое с честными временем/версией, без выдумывания старого approval или повторного push/close. Предмет — итоговые код/тесты/документы, требования, архитектура и правила, не история авторских RED/GREEN/implementation-report; TDD остаётся обязанностью исполнителя. Основание — принятые [ris-ppw S1/D1 §5](../specs/ris-ppw/spec.md#5-компактный-review-и-машинный-итог); исторические решения не переписываются.
7. Замечания высокого и среднего уровня устрани на этапе реализации, затем повторно проверь результаты и запусти новое ревью изменений в субагенте. Повторяй цикл до тех пор, пока таких замечаний не останется. Решения по low можно рассмотреть коллективно в сессии; отдельная заметка/задача/раунд только ради low не требуется.
8. В Beads запиши краткий проверяемый итог, существенные проверки, адрес/раунд review, ограничения и опубликованный Git-коммит, не промежуточный implementation-журнал. Согласование выполнения конкретной задачи RIS разрешает после подтверждённого Git push **отдельной операцией** закрыть именно эту задачу в Beads без повторного вопроса: проверь её ID, выполнение критериев, обязательный состав, отсутствие незавершённых детей и активных блокировок, вызови штатное закрытие без force и проверь сохранённый статус и относящиеся факты. Успешный Git push сам по себе не закрывает задачу и не доказывает выполнения критериев. При неуспешной публикации, невыполненных критериях или конфликте не закрывай её молча: сообщи причину и фактическое состояние; вопросы задавай только для необходимого содержательного решения. Закрытие родительского контейнера остаётся отдельной операцией с явным разрешением и проверкой полного обязательного состава, не следует из закрытия ребёнка. Обновляй только порученные поля после свежей сверки, сохраняй чужое содержание и закреплённые принятые ссылки, используй нативные операции и повторное чтение по правилам ниже. Перед Dolt push проверь remote и разрешённую область общей проектной истории `main`: она публикуется целиком, не по одному ID. Подтверждай достижимость требуемой ревизии свежим чтением выбранного remote по правилам ниже; Git push не заменяет Dolt push. Историческую `tasks/` и локальную `.sdlc/tasks/` в Git не добавляй.

### Отдельные намерения для контейнера

Поправка ris-oub по согласованному поручению пользователя от 2026-10-21:
обычное закрытие родительской фичи/эпика/ordinary task-контейнера не повторяет
приёмку закрытых детей. Она заменяет прежние требования полной приёмки/состава
**только для обычного закрытия родителя**, включая противоположные формулировки
пункта 8 и старых продуктовых описаний. Содержательная проверка остаётся отдельным
явным намерением; исторические спецификации не переписываются.

Различай запросы:

- **Обычно закрыть родителя / проверить возможность закрытия:** прочитать exact
  ID/type/status, полный all-status список прямых детей и направленные блокеры
  родителя. Для открытого родителя список непустой, все дети строго `closed`,
  активных блокировок родителя нет — этого достаточно. Доверять закрытию детей:
  не обходить потомков, не проверять child evidence/блокеры, спецификации, Git,
  ревью или полноту декомпозиции заново. Неполные/неизвестные данные не считаются
  пустым списком или успехом. При разрешении закрыть — native exact close без
  force и read-back статуса, прямых детей/блокеров; публикация Dolt отдельно.
  Вопрос «можно ли закрыть?» остаётся read-only с теми же короткими проверками.
  Слово «административно» не требуется. Такой статус означает завершение учтённых
  прямых детей, не новую независимую приёмку всего результата.
- **Без детей:** фича, реализуемая одной задачей, сохраняет проверку собственного
  результата, независимое ревью и Git-гейты execution. Ноль детей не означает
  успех короткой проверки. Для пустого эпика/ordinary контейнера нужны отдельная
  содержательная проверка либо явно административное решение; автоматического
  перехода к административному закрытию нет.

- **Административно закрыть по решению пользователя:** точные project/ID/type/kind,
  явное полномочие/причина, свежие прямые дети и направленные блокеры, штатный
  exact close без force и read-back. Не требуются новая приёмка, рекурсивное
  восстановление поставок, Git evidence или запись результата/verification.
  Административный `closed` **не является независимой приёмкой**; весь feature
  description/block/refs/verification, включая null/failed/historical/malformed,
  остаётся неизменным. Нативный отказ по детям/блокерам не обходится.
- **Проверить выполнение:** по умолчанию read-only, критерий → наблюдение/evidence
  → выполнено / не выполнено / не хватает данных; без закрытия, публикации или
  обязательной записи отчёта. Применимые свидетельства переиспользуются.
- **Проверить и при успехе закрыть:** содержательная проверка полного обязательного
  состава и актуальных свидетельств, затем close только при успехе; для фичи нет
  обязательного сохранения verification/готовности. Отдельно запрошенная запись
  остаётся отдельным эффектом. Обычное завершение leaf-результата и однозадачной
  фичи в execution flow сохраняет проверки, независимое ревью и Git-гейты;
  административная ветка не является их обходом.

Ни один запрос не закрывает детей/предков автоматически. Уже закрытый ID не
закрывается повторно; неоднозначный эффект сначала сверяется. При подтверждённом
close и pending publication продолжается только недостающая публикация/read-back.
Политика отдельной Dolt-публикации ниже сохраняется и не превращается в новую
содержательную приёмку для административного пути.

## Параллельная работа и совместная публикация Dolt

Разделяй **защиту записи конкретной задачи** и **разрешение публикации общей истории**. Изменения другой согласованной задачи сами по себе не блокируют работу и не требуют нового вопроса пользователю.

1. Перед реализацией агент захватывает свою подтверждённую незаблокированную задачу через адаптер и проверяет результат. Чужой активный захват не перезаписывать. Для параллельных файловых изменений используй отдельный Git worktree; он разделяет рабочие деревья Git, но **не изолирует общую базу Beads**. Область записи и общие файлы согласовываются отдельно.
2. Для обычной своей задачи и явно порученных общих записей используй свежие проверки, нативные атомарные/условные операции и точечные поля с независимым чтением результата. Ручное окно, обязательная глобальная блокировка/очередь и общая транзакция над задачей, графом и внешними документами не требуются. Штатное закрытие транзакционно проверяет прямых детей и блокеров; полноту принятого состава, потомков и применимость внешнего evidence проверь непосредственно перед ним и после записи. Это не гарантирует неизменность всего графа или отсутствие всех потерянных обновлений. CAS строки, claim, lease, worktree, `--sandbox` и read/write/read не являются общим CAS содержимого и структуры. Если явно запрошенное сложное действие или строгую уникальность нельзя корректно обеспечить доступной операцией, сообщи точное ограничение до зависимой записи, не проси остановить участников.
   Проверка принятого состава/потомков/evidence относится к verified-work completion,
   не к обычному child-based или административному закрытию контейнера выше.
3. В Beads выполняй записи с `bd --sandbox`, чтобы подавить Dolt auto-push. Используй атомарное добавление заметок и правки отдельных metadata-ключей вместо замены прочитанного целого поля. Для необходимой замены description/acceptance свежо сравни ожидаемое содержание, сохрани нецелевую прозу и принятия, передай только разрешённое поле и проверь результат; не отправляй всю старую запись. При конфликте сначала перечитай факты, не убирай защитные условия и не используй force. Проверяй реальную область нативных guards: наличие `revision` в ответе не доказывает поддержки `--if-revision`. Не устанавливай координатор и не обновляй Beads скрытым побочным действием. Независимые удалённые копии согласуются при публикации; локальную атомарность не выдавай за распределённую защиту. Git-публикация и отдельный Dolt push сохраняют свои проверки.
4. **В самом RIS действует постоянное разрешение на штатную публикацию всей накопленной общей истории Dolt `main` в установленный remote**, включая соседние задачи и записи других агентов, без нового согласования каждого ID/commit. Это разрешение публикации истории, не принятие содержания и не право редактировать или закрывать чужие записи/контейнеры. Явные более узкие ограничения пользователя сохраняются. Политика применяется только к этому проекту; соседние проекты автоматически не перенастраиваются, их адаптер использует собственную принятую политику либо явные полномочия.
5. Перед новым push проверяй установленный remote/адрес, общую проектную ветку `main`, применимость постоянной политики или более узких ограничений и направление локальной/удалённой истории. Используй обычный non-force push общей `main` в выбранную remote `main`, без private snapshot ref. Не требуются аудит каждого исторического commit/parent, реконструкция всех строк или обязательный all-row net diff. Соседние ID/commits сами по себе не создают вопроса при действующей общей политике. Неожиданный remote, явный выход за полномочия, конфликт политики или расхождение историй блокируют зависимую публикацию; технический сбой сообщается точно, человеку возвращается только содержательное решение. Не удаляй чужую историю, не выполняй скрытый merge, force или автоматическую смену remote. Других писателей не останавливают: новые claim/heartbeat/комментарии не требуют принятия каждого commit. Общая ветка может сдвинуться между наблюдением и push; точный неизменяемый snapshot отправки и CAS не обещаются.
6. Сначала свежо fetch выбранного remote и проверь достижимость точной требуемой/восстановленной ревизии S из remote R, до incoming-only/divergence и new-write gates. Уже достижимая S подтверждается без push, повторной записи результата или закрытия, даже при более новых local/remote изменениях. Не подменяй известную S новым local HEAD. После push, отказа или неоднозначного ответа снова свежо fetch/read remote независимо от ответа push и проверь S; неизвестная S или неудачное чтение не разрешают replay и не означают успех. Новая копия, SQL AS OF и полная семантическая сверка строк не обязательны. Гарантия — remote revision/reachability, не независимое доказательство прав каждого исторического действия и не точное равенство всех полей snapshot. Более новый R не отменяет публикацию S и не означает принятия новых действий. При частичном результате укажи отдельные факты Git, локальных записей/закрытия и Dolt, ограничения и только недостающее восстановление.

Git-публикатор собирает и коммитит результат в собственной ветке/копии задачи, туда же merge-интегрирует свежую основную ветку выбранного remote и разрешает конфликты. Локальная `main` не является площадкой интеграции: в ней не коммитят и не merge-интегрируют результат, не переключают на неё копию ради интеграции. Из собственной ветки отправляется проверенный commit в разрешённый основной remote ref обычным non-force push. Продвижение remote или отказ push вызывает свежую сверку и повтор только затронутых шагов интеграции, проверок и независимой переоценки полного нового snapshot; применимые свидетельства сохраняются. Неизменённые документы не перепринимаются, весь SDLC не перезапускается. Неоднозначный push сначала проверяется независимым чтением remote.

Git-публикатор по умолчанию завершает remote-only результат и не обновляет/переключает исходную папку. Только явно порученное обслуживание после remote confirmation включает rare `primary-sync.md`: безопасный FF уже находящейся на установленной primary branch исходной копии, без branch switching/return, reset/stash/pull/autostash/force или перезаписи protected tracked/untracked/ignored файлов. Идентичность/полномочия/безопасность — гейты только этой мутации, не push/completion/Dolt. Занятая, изменённая, расходящаяся, detached/на другой ветке или неоднозначная копия остаётся нетронутой; явно запрошенное обновление сообщается отдельным skipped/failed/unknown долгом, remote Git успешен независимо. Повтор сначала сверяет факты и выполняет только недостающий FF/read-back, не push. Локальный успех требует read-back на последний наблюдавшийся remote tip, не обещает будущей неизменности. Детальные guards и bounded retry принадлежат ресурсу публикатора. Исторические решения не переписываются.
