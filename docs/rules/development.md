# RIS — руководство по разработке

RIS — набор готовых скиллов для AI-агентов, помогающих решать задачи на этапах жизненного цикла разработки ПО. Перед работой ознакомься с [README.md](../../README.md) и относящимися к поручению материалами проекта. Не считай планы или идеи уже реализованными возможностями.

Доводи согласованную задачу до результата без пауз ради формального подтверждения: если нет вопросов к пользователю или препятствий, продолжай работу, проверки и завершение задачи. После реализации, необходимых проверок и ревью **публикуй подлежащие публикации изменения: сделай коммит и отправь его в настроенный удалённый репозиторий без отдельного запроса разрешения**. После подтверждения публикации в рамках той же работы отдельно заверши согласованную задачу в Beads по пункту 8, не ожидая дополнительного запроса пользователя. Проверь успешность отправки до сообщения о завершении; если публикация не удалась, сообщи об этом и не называй результат опубликованным или задачу завершённой. Локальную папку `tasks/` в Git не добавляй. Это не отменяет согласования объёма и критериев до реализации.

## Задачи разработки

Выбирай наименее затратную проверку, достаточную для конкретного утверждения; различай обязательные проверки, условные проверки с явными условиями запуска и исследовательские эксперименты. Не превращай перечень возможных сценариев в обязательную матрицу: переиспользуй применимые свидетельства и повторяй затронутые проверки. **Не пиши и не запускай тесты для проверки поведения агентов, включая живые прогоны и сценарные тестовые сессии: такие проверки чрезмерно увеличивают длительность работы. Проверяй инструкции агентов чтением и ревью; не выдавай это за подтверждение поведения в живом запуске.** При подтверждённом конфликте принятого контракта с платформой или существенном росте стоимости проверки своевременно верни вопрос пользователю до продолжения зависимых экспериментов; независимую полезную работу можно продолжать. Ограничивай поручения субагентам проверяемым промежуточным результатом и условиями раннего возврата, передавай относящиеся к делу входы и версии вместо всей накопленной истории. Обязательные проверки не сокращай молча: согласуй изменение объёма, явно укажи невыполненные проверки и границы выводов, не объявляй их пройденными. Это не отменяет TDD, независимое ревью и проверки публикации там, где они обязательны.

Обычная доработка инструкций завершается после предусмотренных статических проверок и независимого ревью: отсутствие live run не создаёт блокера и не требует повторного вопроса о запуске. Имена, ресурсы, зависимости и source/install parity проверяются статически; исполняемые программы — необходимыми обычными тестами. Выводы о надёжности, стоимости и повторяемости поведения агента допустимы только в пределах применимых имеющихся наблюдений. Старые поведенческие обязательства и непроверенные результаты не становятся pass; специальная работа с явно принятой поведенческой целью требует отдельного согласования объёма и не разрешает обходить запрет выше. Подробное разделение доказательств — в [05](../concepts/05-adoption-and-validation.md#4-три-уровня-проверки) и [07](../concepts/07-quality-and-verification.md#2-критерий-и-подтверждение).

Источник истины для очереди, состояния и зависимостей задач разработки **этого проекта** — Beads (Dolt), выбранный в корневом `ris.yaml` через `adapters.tasks.skill: ris-proj-adapter-beads-tasks`. Перед изменениями подтвердить проект командой `bd where`/`bd context`; для полной выборки задач (включая закрытые) использовать `bd list --all --limit 0 --type task --json`, для эпиков — такую же выборку с `--type epic`, для конкретного ID — `bd show <id> --json`. Не считать порядок выдачи приоритетом или наличие эпика разрешением начать задачу. Историческая игнорируемая Git папка `tasks/` содержит завершённые `PLAN-001`–`PLAN-054`, не является действующей очередью и не является настроенным `workspace.tasks`:

- [`tasks/RIS.md`](../../tasks/RIS.md) и [`tasks/RIS - roadmap.md`](../../tasks/RIS%20-%20roadmap.md) — исторические указатели;
- [`tasks/RIS - backlog.md`](../../tasks/RIS%20-%20backlog.md) и [`tasks/RIS - archive.md`](../../tasks/RIS%20-%20archive.md) — снимок очереди и архив периода `PLAN-*`, не изменяемые списки состояний Beads;
- [`tasks/RIS - inbox.md`](../../tasks/RIS%20-%20inbox.md) — исторические идеи периода `PLAN-*`;
- `tasks/PLAN-NNN - <название>.md` — сохранённая история прежних задач. Новые номера `PLAN-*` не назначать, закрытые задачи задним числом в Beads не создавать.

Рабочие заметки, планы, проверки и отчёты ревью **новой** задачи находятся локально в `workspace.tasks/<подтверждённый Beads ID>/` основной рабочей копии, для RIS это `.sdlc/tasks/<ID>/` по корневому `ris.yaml`. По умолчанию технический план — `plan.md`; другие имена файлов указывать явно. Этот каталог игнорируется Git: из другой копии заметки недоступны. В Beads сохранять достаточные цель, границы, критерии, ссылки на опубликованные спецификации и краткий проверяемый итог со ссылкой на опубликованный Git-коммит при завершении; не ссылаться на локальный журнал как на обязательный удалённый вход. Принятые спецификации публиковать в `docs/specs/` по правилам проекта. При работе из worktree использовать проверенный context корень основной копии для `workspace.tasks`: valid explicit либо уже доступное saved indication с проверенными provenance/project/repository/current-copy association; не угадывать по Git или `.sdlc`. Неразрешённая association блокирует только зависимые shared-path действия.

Порядок работы:

1. Перед планированием или началом задачи прочитай актуальные Beads-задачи и эпики, их связи и относящиеся к делу проектные документы. Сырые идеи обсуди до оформления задачи; не веди параллельный изменяемый inbox или backlog в файле. Сверь все состояния перед созданием записи: если задача уже существует (например, `ris-p20.1`), используй её подтверждённый ID, не создавай дубль. Задачи, относящиеся к фиче, связывай с её подтверждённым родителем; самостоятельные работы не прикрепляй к эпику искусственно.
2. После прояснения проблемы, результата, границ и критериев и разрешения на запись создавай задачу в Beads через выбранный адаптер с устойчивым ключом для повторной сверки. Проверяй фактический ID, содержание, состояние и связи после записи; отсутствие дублей при конкурентном создании не гарантируется. Перед новой записью или повтором сверяй полную выборку, включая закрытые задачи. Не веди одновременно изменяемый файловый список задач.
3. Согласуй с пользователем объём и критерии задачи до реализации. Каждый агент одновременно выполняет не более одной задачи разработки RIS; разные агенты могут выполнять разные согласованные задачи по правилам параллельной работы ниже. Состояние Beads не является само по себе разрешением приступить к реализации.
   После обсуждения и явного утверждения требований к новому результату или изменению предложи сохранить их как спецификацию в `docs/specs/` и запланировать исполнение в Beads. Если пользователь согласен, зафиксируй принятые решения и проверяемые критерии так, чтобы реализацию можно было начать в новой сессии без истории чата, независимо от локальных заметок. Не создавай повторную спецификацию, если подходящая уже сохранена; утверждение требований само по себе не разрешает запуск отдельной задачи реализации.
   Для спецификации нового скила RIS оцени, уместна ли самостоятельная переносимая методика и отдельный проектный скил по [архитектуре](../concepts/01-architecture.md). Зафиксируй принятое разделение ответственности или причину выбора одного скила; не требуй пары формально.
    При подготовке и ревью спецификации скила проверь владельца каждого дополнительного действия, различимость соседних операций, типичный объём загружаемых инструкций и условия редких веток по [критериям проверки](../concepts/05-adoption-and-validation.md). Не переносить чужую ответственность в скил или ресурс только ради удобства; не дробить необходимый шаг ради уменьшения числа строк.
    Для скила RIS также различай самостоятельную методику, операционную обёртку и сквозной сценарий: отдельная обёртка не назначает следующий скил, сценарий отвечает за переходы и совокупный результат. Оценка роли исполнителя и проектной конфигурации обязательна только там, где это требуется конкретному вызывающему; поддержка `execution` в `ris-proj-op-resolve-context` готовит имена агентов, но не доказывает их доступность или запуск.
4. Для согласованной задачи зафиксируй план и ход реализации в локальной заметке по подтверждённому ID. После реализации проверь относящиеся к изменению результаты и итоговый diff.
5. После реализации запусти ревью сделанных изменений в субагенте. Передай ему требования задачи, правила проекта и итоговый diff. Ревью должно проверить, что требования выполнены, правила проекта соблюдены, а в коде и бизнес-логике решения нет ошибок. Для изменений без кода проверяй применимые к ним требования и корректность результата. При разработке или изменении скила RIS ревью отдельно проверяет принятое решение о декомпозиции, переносимость базового скила (если он выделен), границы RIS-интеграции, ответственность за общий результат, отсутствие чужих операций и ненужной обязательной загрузки по [критериям](../concepts/05-adoption-and-validation.md).
6. Оформи результат ревью отчётом: для каждого замечания укажи место, суть и ровно один уровень критичности — **высокий**, **средний** или **низкий**. При отсутствии замечаний явно укажи это. Сохрани отчёт в локальной заметке задачи и представь результаты пользователю.
7. Замечания высокого и среднего уровня устрани на этапе реализации, затем повторно проверь результаты и запусти новое ревью изменений в субагенте. Повторяй цикл до тех пор, пока таких замечаний не останется. Замечания низкого уровня и решения по ним зафиксируй в заметке задачи.
8. Зафиксируй итог и проверки в локальной заметке; в Beads запиши краткий проверяемый итог и опубликованный Git-коммит. Согласование выполнения конкретной задачи RIS разрешает после подтверждённого Git push **отдельной операцией** закрыть именно эту задачу в Beads без повторного вопроса: проверь её ID, выполнение критериев, обязательный состав, отсутствие незавершённых детей и активных блокировок, вызови штатное закрытие без force и проверь сохранённый статус и относящиеся факты. Успешный Git push сам по себе не закрывает задачу и не доказывает выполнения критериев. При неуспешной публикации, невыполненных критериях или конфликте не закрывай её молча: сообщи причину и фактическое состояние; вопросы задавай только для необходимого содержательного решения. Закрытие родительского контейнера остаётся отдельной операцией с явным разрешением и проверкой полного обязательного состава, не следует из закрытия ребёнка. Обновляй только порученные поля после свежей сверки, сохраняй чужое содержание и закреплённые принятые ссылки, используй нативные операции и повторное чтение по правилам ниже. Перед Dolt push проверь remote и весь исходящий состав: он публикуется целиком, не по одному ID. Отправляй лишь разрешённые записи, подтверждай синхронизацию отдельным чтением из другой копии; Git push не заменяет Dolt push. Историческую `tasks/` и локальную `.sdlc/tasks/` в Git не добавляй.

## Параллельная работа и совместная публикация Dolt

Разделяй **защиту записи конкретной задачи** и **разрешение публикации общей истории**. Изменения другой согласованной задачи сами по себе не блокируют работу и не требуют нового вопроса пользователю.

1. Перед реализацией агент захватывает свою подтверждённую незаблокированную задачу через адаптер и проверяет результат. Чужой активный захват не перезаписывать. Для параллельных файловых изменений используй отдельный Git worktree; он разделяет рабочие деревья Git, но **не изолирует общую базу Beads**. Область записи и общие файлы согласовываются отдельно.
2. Для обычной своей задачи и явно порученных общих записей используй свежие проверки, нативные атомарные/условные операции и точечные поля с независимым чтением результата. Ручное окно, обязательная глобальная блокировка/очередь и общая транзакция над задачей, графом и внешними документами не требуются. Штатное закрытие транзакционно проверяет прямых детей и блокеров; полноту принятого состава, потомков и применимость внешнего evidence проверь непосредственно перед ним и после записи. Это не гарантирует неизменность всего графа или отсутствие всех потерянных обновлений. CAS строки, claim, lease, worktree, `--sandbox` и read/write/read не являются общим CAS содержимого и структуры. Если явно запрошенное сложное действие или строгую уникальность нельзя корректно обеспечить доступной операцией, сообщи точное ограничение до зависимой записи, не проси остановить участников.
3. В Beads выполняй записи с `bd --sandbox`, чтобы подавить Dolt auto-push. Используй атомарное добавление заметок и правки отдельных metadata-ключей вместо замены прочитанного целого поля. Для необходимой замены description/acceptance свежо сравни ожидаемое содержание, сохрани нецелевую прозу и принятия, передай только разрешённое поле и проверь результат; не отправляй всю старую запись. При конфликте сначала перечитай факты, не убирай защитные условия и не используй force. Проверяй реальную область нативных guards: наличие `revision` в ответе не доказывает поддержки `--if-revision`. Не устанавливай координатор и не обновляй Beads скрытым побочным действием. Независимые удалённые копии согласуются при публикации; локальную атомарность не выдавай за распределённую защиту. Git-публикация и отдельный Dolt push сохраняют свои проверки.
4. **Разрешается совместно публиковать исходящую историю Dolt по явно согласованным задачам и инициативам**, включая разрешённые изменения других агентов в этой области. Область устанавливается подтверждёнными задачами/инициативами и доступным основанием согласования, а не неизменным списком commits. Наличие записи, статус `ready`/`in_progress` или принадлежность эпику сами по себе не доказывают согласования. При явно более узком разрешении пользователя соблюдай его. Публикация чужих записей не даёт права менять их содержание, принимать результат за владельца, закрывать чужие задачи или автоматически закрывать контейнеры.
5. Перед каждым push проверяй настроенный remote, **всю исходящую историю выбранного snapshot и полный фактический состав изменений**, включая содержание записей и направленные связи. Убедись, что они принадлежат разрешённой области и выполнены в пределах прав записи. Отправляй проверенный Dolt snapshot через отдельный уникальный локальный ref владельца публикации: остальные агенты не изменяют этот ref; он не переключает рабочую ветку и не включает позднейшие коммиты. Разрешение Dolt-публикации включает создание такого локального ref, если явно не ограничено. Если корректный snapshot-bound путь недоступен, сообщи точное ограничение, не заменяй его ручной паузой или обязательным глобальным lock. Других писателей для push не останавливают: обычный push без force может отказать, после чего нужна свежая сверка. Новый захват, heartbeat, комментарий или иное разрешённое изменение внутри согласованной области не требует повторного согласования каждого commit. При новой несогласованной инициативе внутри отправляемого snapshot, выходе за разрешённые действия, конфликте затронутой задачи или расхождении истории останови зависимую публикацию/запись; перечитай факты и задай только необходимый содержательный вопрос. Не удаляй чужую историю и не используй force-push для обхода конфликта.
6. После push проверь отправленную ревизию и ожидаемые записи отдельным чтением из независимой копии выбранного remote. Более поздние разрешённые изменения другой задачи не делают уже подтверждённую публикацию неуспешной: различай проверенный отправленный snapshot и новые локальные изменения. При частичном результате укажи фактическое состояние Git и Dolt и конкретное восстановление, без повторного выполнения уже проверенных действий.

Git-публикатор собирает и коммитит результат в собственной ветке/копии задачи, туда же merge-интегрирует свежую основную ветку выбранного remote и разрешает конфликты. Общая локальная `main` не является площадкой публикаторов: её не переключают и не изменяют ради публикации. Из собственной ветки отправляется проверенный commit в разрешённый основной remote ref обычным non-force push. Продвижение remote или отказ push вызывает свежую сверку и повтор только затронутых шагов интеграции, проверок и независимой переоценки полного нового snapshot; применимые свидетельства сохраняются. Неизменённые документы не перепринимаются, весь SDLC не перезапускается. Неоднозначный push сначала проверяется независимым чтением remote.
