# 04. Контракты скилов, адаптеры и инструменты

[Оглавление](index.md)

## 1. Контракт каждого скила

| Часть | Содержание |
|---|---|
| Назначение | Основной результат и его владелец |
| Применение | Когда использовать и где нужен другой скил |
| Входы | Источники, параметры, статус принятия и допустимые пробелы |
| Зависимости | Роль, условие загрузки и форма применения |
| Роль исполнения (если нужна вызывающему) | Смысловая роль работы без модели, имени субагента и обязательного режима запуска при прямом вызове |
| Предусловия | Что нужно до действия; не только существование файлов |
| Методика | Содержательная процедура или её явная композиция |
| Результат | Артефакт или ответ, содержание, адрес и критерии |
| Изменения | Разрешённые побочные эффекты и границы записи |
| Проверка | Наблюдаемые подтверждения именно заявленного результата |
| Ошибки | Отсутствие входов, конфликты, частичное выполнение и восстановление |
| Завершение | Граница ответственности и данные передачи |

Для критичных рисков дополнительно описываются типичные обходы требований и признаки нарушения с реакциями. Необязателен отдельный заголовок для каждой части; обязательна ясность контракта. Пустые разделы не заменяют спецификацию.

Контракт записывается в теле `SKILL.md` и связанных ресурсах. ris не вводит исполняемые `imports`, `depends_on` или автоматические параметры в YAML-заголовке. Дополнительные сведения могут быть соглашением инструментов лишь после реализации их обработки.

В спецификации нового скила зафиксируй, имеет ли предметная методика самостоятельный переносимый контракт или остаётся в одном RIS-скиле. Если выделена пара, базовый скил определяет свою методику, входы и проверяемый самостоятельный результат без RIS-зависимостей; проектный RIS-скил определяет условия применения базового, проектные входы, работу с `ris-proj-op-resolve-context` при необходимости, совокупный результат и остановку. Области ответственности и условия выбора должны быть различимы в обоих `description`; детали методики не дублируются. Критерии решения — в [01](01-architecture.md), правила применения — в [03](03-composition.md).

При проектировании или пересмотре контракта проверь каждый значимый шаг: нужен ли он для заявленного результата, не принадлежит ли существующему владельцу и будет ли его инструкция востребована при обычном запросе. Если шаг требует отдельного результата, решения или разрешений, специфицируй его как отдельную операцию/скил либо вынеси координацию в составной скил. Если шаг нужен только условно, определи точное условие подключения и место хранения деталей. Не дублируй в обёртке базовую методику; сохранение проверяемого общего результата не требует копии её алгоритма. Не дроби на скилы шаги без самостоятельной ответственности.

Прикладная обёртка не объявляет следующего скила как часть собственного выхода и не запускает следующий этап. Её вызов других скилов для **своего** результата остаётся допустимой необходимой зависимостью. Сквозной скил владеет маршрутами и допусками, но не копирует содержание методик и адаптеров. Роль объявляется в контракте операции, когда она нужна реальному вызывающему; не вводить обязательную роль каждому действующему скилу ради единообразия. Инструкция может описать следующий возможный шаг содержательно, без привязки к публичному имени следующего скила.

Самостоятельная read-only навигация вправе рекомендовать фактического владельца
как свой полезный результат по текущим фактам, его установленному контракту и
проверенной команде. Это узкое исключение, не разрешение обычной обёртке назначать
next skill. Навигация различает unfinished operation/scenario, следующий результат,
возврат caller, человеческое решение и exact gap; не исполняет рекомендацию,
не пишет состояние и не выдаёт её за полномочия или полную readiness.

## 2. Метаданные и description

Устанавливаемый скил имеет обязательные `name` и `description`; имя соответствует каталогу. Остальные поля добавляются только при реальной потребности и поддержке выбранной среды. Базовый формат основан на Agent Skills. [S1](sources.md).

`description` объясняет результат, условия применения и отличие от соседних скилов. Оно не пересказывает процесс, не подменяет `SKILL.md` и не содержит обещаний, которые не покрывает контракт. Само указание «для агентов разработки» не позволяет выбрать скил.

Пример для каталога ris:

```yaml
---
name: ris-proj-op-plan-roadmap
description: >-
  Формирует или актуализирует roadmap проекта по концепции и целям:
  крупные результаты, границы MVP и зависимости эпиков.
  Используй для планирования проекта, а не для декомпозиции одной фичи.
---
```

Ограничения формата проверяются валидатором выбранной версии стандарта. Практическую различимость описаний проверяют сценарии из [05](05-adoption-and-validation.md), а не только корректность YAML.

## 3. Передача ограниченной операции

Операция получает:

```text
Имя нужной операции
+ актуальный контекст проекта
+ конкретные входные данные
+ разрешённые изменения
+ ожидаемый результат
```

В одной сессии это может быть явный блок контекста; в существующем оркестраторе — его объект задания. Текст «вызови адаптер» не создаёт программную функцию с возвращаемым значением.

Исполнитель обязан получить фактический результат, проверить его и только затем использовать. Нельзя продолжить работу с предполагаемым идентификатором задачи или непроверенной записью.

## 4. Адаптеры

Git-публикация принадлежит `ris-proj-op-publish-task`, не tasks adapter:
task/change получает подтверждённый ID/scope и применимые accepted inputs/checks;
pre-ID documents — exact paths/subject, отдельные решения применимых принятых
результатов, substantive checks и independent full-snapshot review. Для
requirements-only не требуются ID, implementation evidence или будущий дизайн.
Обе ветки используют один алгоритм с authority/target/full outgoing scope,
preservation/reassessment/remote read-back. Публикация proposed не делает accepted;
publisher не создаёт/закрывает записи и не публикует Dolt. Receipt содержит
subject/version/decision locators, commit/tree/ref/remote, applicability и actual
effects/limits/remainder; common задаёт достаточность recoverable output без
универсальной схемы. Эти границы не расширяют `tasks` v1.

Разные реализации одной роли должны соблюдать одинаковую семантику. Иначе смена имени адаптера в конфигурации не обеспечивает заменяемость.

### Контракт роли `tasks`, версия 1 (roadmap и задачи фичи)

Это **нормативный владелец** общей семантики; условные имена ниже не являются командами RIS CLI или машинным API. Версия 1 первоначально охватывала только roadmap; теперь она совместимо дополнена **необязательным набором операций задач фичи** ниже. Существующие операции эпиков и их связей не меняют смысла. Адаптер заявляет версию, поддерживаемые операции и гарантии **по каждой** операции; частичная поддержка допустима. Потребитель проверяет выбранный установленный адаптер, совместимую версию и все нужные операции и гарантии до зависимого действия. Дополнение необязательной операции совместимо с версией 1; изменение семантики существующей требует новой версии и проверки потребителей. Одно лишь заявление «v1», без нужных операций и гарантий, недостаточно. Отсутствующее требование не заменяется похожим вызовом трекера или другим адаптером.

Общие входы каждой операции: явно выбранный проект/workspace, разрешённая область чтения или записи, подтверждённая цель и идентичность записей; для записи — точное изменение и ожидаемое состояние. Чтение не даёт права записи. **Для операций roadmap ниже** тип записи — `epic`, состояния передаются как фактическое состояние трекера и признак открытости/закрытости, без навязанной таблицы статусов другого трекера. Содержание эпика включает идентичность цели и самого эпика, результат, границу/исключения, критерий завершения и покрытые сценарии либо подтверждённую ссылку на эти сведения. Идентичность проверяется по ID и устойчивому признаку принадлежности цели; одно название или предполагаемая уникальность внешней ссылки недостаточны.

| Операция | Вход и необходимая семантика | Результат и гарантии |
|---|---|---|
| `tasks.epics.list` | Область проекта, тип `epic`, все состояния, включая закрытые; фильтр цели применяется только при сохранении полноты | Полная выборка применимых записей с ID, типом, состоянием и содержанием либо явная неполнота и способ продолжения пагинации; усечённая выборка не подтверждает отсутствие |
| `tasks.epics.read` | Подтверждённый ID | Ровно одна запись с совпавшим ID, типом, состоянием, содержанием и доступными связями либо отсутствие/неоднозначность |
| `tasks.epics.create` | Разрешённые описание и устойчивый признак принадлежности цели, ожидание отсутствия | Фактический ID и прочитанные после записи поля; best-effort с проверкой коллизий; явно требуемая строгая уникальность нуждается в реальной поддержке инструмента, иначе точное ограничение до записи |
| `tasks.epics.update` | Подтверждённый ID, свежо проверенное ожидаемое состояние, явно названные поля | Точечная нативная запись с применимыми guards, сохранённые поля и нецелевое содержание по повторному чтению; ограничения защиты от same-field конкуренции названы явно, без ручного окна или отдельного вопроса о риске для обычной записи |
| `tasks.blocks.list` | ID эпика и область требуемых связей | Типизированные направленные связи: блокируемый эпик → блокирующий эпик; пустая полная выборка отличается от ошибки |
| `tasks.blocks.add` | Подтверждённые ID блокируемого и блокирующего эпиков, тип `blocks`, ожидаемое отсутствие | Проверенная связь в нужном направлении без цикла; если состояние изменилось, сначала сверить факты |
| `tasks.blocks.remove` | Те же ID и тип, свежо проверенная существующая **точная** связь, разрешение удалить её | Нативное удаление и подтверждённое отсутствие именно этой связи после записи; не обещает защиты от необнаруженной конкурентной замены, явно требуемая более сильная неподдерживаемая гарантия блокирует только зависимое действие |

Для `create`, `update`, `add` и `remove` адаптер свежо читает затронутые записи и связи, использует точечную нативную операцию и независимо проверяет результат; возвращает фактические ID, состояние, содержание, связи и ограничения атомарности. Нулевой код команды сам по себе не подтверждает результат. При неоднозначном ответе сначала сверяет фактическое состояние, не повторяет вслепую создание или удаление. Если запись частична, сообщает подтверждённую часть и прекращает следующие изменения; причины `blocked|conflict|error` и форма отчёта — в разделе 6. Чтение до/после не является универсальным CAS; обычная разрешённая запись не требует ручного окна, глобального lock или транзакции над всем графом. Отсутствие права, операции, совместимой версии или явно необходимой более сильной гарантии — `blocked` либо `conflict` без зависимой записи с точным ограничением, не запрос остановки писателей. Захват и завершение остаются инструментальными операциями, не входят в общий контракт v1.

### Дополнительные операции `tasks` v1: задачи фичи

Ниже — необязательные task-операции v1. Early feature create использует ordinary
content и optional epic, без JSON capability/accepted-ref registry. Фактические
принятые документы нужны зависимому результату, не ранней регистрации. Child inputs,
decomposition, execution, native protection и publication gates сохраняются.

Запись фичи и её прямых детей имеет native type `task`; epic optional и проверяется
при наличии. Маленькая фича может исполняться собственной задачей без детей.
Tracker status возвращается фактически, не как результат RIS. Kind устанавливается
из явной области, реального content/source association и релевантных native связей,
не title/JSON/parent-child alone. Exact ID, approved scope и scoped stable retry key
обеспечивают bounded reconciliation; new full-ID documents либо existing explicit
links позволяют найти actual content и независимые решения. Адаптер не принимает
спецификацию за пользователя. Детям нужны own outcome/criteria, parent-scoped key
и sufficient accepted inputs/contracts/seams; отсутствие дублей проверяется во всей
релевантной all-status области без обещания строгой конкурентной уникальности.

| Операция | Вход и необходимая семантика | Результат и гарантии |
|---|---|---|
| `tasks.items.list` | Проект, тип `task`, все состояния, в том числе закрытые; область/ключ идентичности с проверкой полноты | Полная выборка задач с ID, типом, состоянием, родителем, содержанием и доступными ссылками либо явная неполнота и способ продолжения; усечённая выборка не подтверждает отсутствие |
| `tasks.items.read` | Подтверждённый ID задачи | Ровно одна задача с совпавшим ID, типом, состоянием, родителем, содержанием, ссылками и доступными связями либо отсутствие/неоднозначность; эпик с тем же ID по смыслу не подходит |
| `tasks.items.create` | Разрешённые ordinary content/goal и scoped stable key, optional подтверждённый open epic для фичи; ребёнку — confirmed open feature parent и достаточные accepted inputs/own criteria; expected absence | Exact reuse при совпадении identity/optional parent/content/source association либо created ID с read-back и проверенной membership; conflict при расхождении, без скрытого update. Нет JSON/refs/ready registry; best-effort не strict uniqueness |
| `tasks.children.list` | Подтверждённый ID задачи фичи, только **прямые** дети всех состояний | Полный состав прямых детей с ID, типом, состоянием, родителем и содержанием либо явная неполнота; пустой полный состав отличается от ошибки. Потребитель решает, достаточен ли состав |
| `tasks.dependencies.list` | Подтверждённые ID задач и нужное направление | Полные типизированные направленные связи `blocks`: блокируемая задача → блокирующая задача; не смешивать со связью состава `parent-child` |
| `tasks.dependencies.add` | Подтверждённые ID задач в разрешённой области, ожидаемое отсутствие точной связи `blocks` | Подтверждённая связь в правильном направлении без цикла; повтор уже существующей точной связи возвращает фактическое состояние без фиктивного изменения |

Перед зависимой записью потребитель проверяет версию, **каждую** нужную операцию и гарантию: полные выборки для проверки отсутствия и детей, идентичность с родителем и ссылкой, проверку направления и цикла, прочтение после записи и реальные пределы нативной защиты. Область записи и ожидаемое состояние задаются явно; адаптер проверяет тип и принадлежность обоих концов. Создание по умолчанию best-effort с поиском и сверкой всех состояний до и после записи; параллельное создание может породить дубли, и при их обнаружении результат `conflict` с фактическими ID. Явно требуемое отсутствие дублей нуждается в реальной гарантии инструмента; без неё возвращается точное ограничение, не запрос ручного окна. Добавление связи проверяет концы и отсутствие цикла, перечитывает результат; при несовпадении останавливается. Изменение содержания, перенос детей и удаление связей **не** включены в эти новые общие операции; инструментальные способы их выполнить не считаются взаимозаменяемым контрактом. При неоднозначной команде сначала перечитать факты; после частичного успеха вернуть подтверждённые ID и изменения и остановить следующую запись. Отсутствие операции, права, полноты, совместимой версии либо явно требуемой более сильной гарантии останавливает зависимую запись без обхода через конкретный трекер.

### Tool-specific standalone операции

Адресное совместимое расширение по [ris-a17 S1/D1](../specs/ris-a17/spec.md):
адаптер может отдельно объявить `tasks.items.update` для bounded ordinary feature
content и `tasks.feature-dependencies.add|remove` для графа предварительных фич.
Последнее требует approved graph delta, exact endpoints с подтверждённым feature
kind и epic membership; оба эпика при cross-epic связи явно входят в scope.
Результат — точная направленная implementation `blocks` связь либо проверенное
удаление именно её, с cycle checks, fresh reads/native guards/read-back и честными
concurrent replacement limits. `tasks.dependencies.add` остаётся intra-feature,
не получает скрытого cross-feature смысла. Нужны объявленные capabilities до записи.
Requirements prerequisites хранятся читаемыми exact-ID + required accepted decision/
contract scope ссылками, информационные связи не блокируют. Принятое/начатое/чужое/
завершённое сохраняется; непонятный create effect сверяется, не дублируется. Это не
универсальный CAS графа и не новая readiness-схема. Иные операции и ограничения
таблицы выше не расширяются.

Обычные standalone task/task-контейнеры и их дети — отдельная явно выбранная
ветка, не расширение смысла `tasks.items.create`.
Выбранный адаптер отдельно объявляет tool-specific create/reconcile, source
update, child/link, result persistence и exact close с гарантиями каждого действия.
Содержание хранит own outcome/scope/criteria, устойчивый key и точные принятые
sources/decisions; обязательного JSON/registry нет. Simple task достаточно
accepted constraints; material design принимается отдельно. Ребёнок имеет
собственные refs/contracts/seams, не копию всех global AC. Нет искусственного
эпика или ребёнка для one-task результата. Отсутствие/ошибка payload не доказывает
standalone kind; historical/malformed данные сохраняются без миграции.
Native append/key merge защищает только свою row operation; expected graph и
external evidence требуют свежей содержательной проверки, не заморозки. Native close direct-child/
blocker guards не доказывают полноты mandatory composition или принятия outcomes.
Отсутствие нужной гарантии блокирует зависимую запись, не read-only assessment.

Административное закрытие явно выбранного контейнера — отдельно объявляемая
tool-specific status-only операция: точные project/ID/type/kind, полномочие,
свежие прямые дети/направленные блокеры, native close без force и read-back.
Она не требует новой приёмки, рекурсивной реконструкции поставок, Git evidence
или result/verification persistence. `closed` не независимая приёмка. Verify
по умолчанию read-only и различает выполнено / не выполнено / не хватает данных;
verify-and-close допускает close только после успешной содержательной проверки.
Обычная leaf completion в execution flow сохраняет собственные result/Git gates.

### Документы и принятие фичи

Фича использует ordinary
native task с optional подтверждённым epic. Early create требует выбранную цель,
title и устойчивый scoped retry key, не spec/design/acceptance; документы и actual
acceptance обязательны только зависимому результату. Children
требуют sufficient accepted scope/criteria и подтверждённого родителя.
Create/retry сверяют релевантную all-status identity, destination/source association
и conflicts; unknown не absence, best-effort не CAS или strict uniqueness.

Новые документы: `sources.specs/<full feature ID>/spec.md`, без title suffix и
переезда при rename. H1 readable name, column-zero Feature-ID/Summary/optional
Keywords; требования в spec.md, достаточный дизайн — отдельная различимая область
там либо соседний design.md. Реальные независимые scope/version принятия, original
`containing-commit` provenance и publication сохраняются; duplicate accepted refs
в Beads не нужны. Exact project+ID обнаруживает документы по этому соглашению или
существующим explicit links/readable legacy hints; проверяются actual content и
decisions, не schema. Missing/old/malformed JSON сам по себе не блокирует маршрут.
Document-only/ordinary/bug сохраняют собственные пути и contracts.

Нет JSON writer/readiness, slug/spec pin,
duplicate accepted refs, mandatory record-verification/read-back перед feature close
или заменяющего registry. Verify по умолчанию read-only; verify-and-close проверяет
полные AC/composition/blockers и evidence на общей integrated revision, затем native
exact close при успехе. Краткий ordinary outcome допустим без mandatory saved
verification. Старые JSON/проза/история не изменяются; нет новой `/3`, schema parser,
bulk migration или product functionality index. Substantive acceptance, independent
review, claim/copy и Git/close/Dolt остаются отдельными gates. Исторические контракты
и решения доступны в [спецификации lifecycle](../specs/sdlc-feature-lifecycle/acceptance.md)
и [основании document route](../specs/ris-wcv/spec.md), не являются альтернативным
операционным алгоритмом и не переоценивают старые evidence.

Обычное закрытие родителя доверяет полному непустому all-status набору закрытых
прямых детей и проверяет блокеры родителя, без рекурсивной приёмки/аудита Git и
ревью. Проверка возможности закрытия — те же чтения без записи. Native exact close
без force и с read-back, затем отдельная tracker publication остаются у адаптера. Ноль детей
не даёт short-close success: one-task feature проходит собственные execution gates,
пустой epic/ordinary container требует явного substantive либо administrative intent.
Явные verify/verify-and-close проверяют полный mandatory scope и актуальное evidence;
подробные границы намерений — в [08](08-sdlc-methodology.md#4-переходы-и-владельцы).

Принятие и исходная provenance принадлежат [06 §4](06-artifacts-and-handoff.md#4-сохранение-согласованных-решений)
и common published-inputs, не tracker payload. Подготовка фичи и decomposition —
у их предметных owners по [08 §4](08-sdlc-methodology.md#4-переходы-и-владельцы).
Версионированный bug basis — [06 §4.1](06-artifacts-and-handoff.md#41-воспроизводимое-основание-bugfix):
адаптер владеет полным историческим чтением/locator/retry, не копией отчёта.

### Общая публикация — действующий контракт

Публикацией общей проектной Dolt-ветки `main` владеет адаптер, не ведущий. Полномочия задаются принятой standing shared-history policy выбранного проекта либо явным разрешением согласованных задач/инициатив и действий; статус, claim и эпик сами по себе не authority. В RIS правила постоянно разрешают штатную публикацию всей накопленной общей истории в установленный remote, включая соседние задачи, без согласования каждого ID/commit. Другие проекты сохраняют собственную политику; пакет её автоматически не меняет. Co-publication не разрешает менять, принимать или закрывать чужие записи; более узкие ограничения сохраняются. Перед новым обычным non-force push `main` проверяются destination, актуальная политика/область и направление истории. Не требуются per-commit/parent audit, реконструкция всех строк, private snapshot ref, новый clone или SQL AS OF/full-row comparison; не вводится эквивалентный обязательный all-row net diff. Непокрытая полномочиями область, неожиданный remote, конфликт политики, расхождение или недоступный required CLI останавливают зависимое действие без force, скрытого merge, смены remote, ручного окна и глобального lock.

Точная требуемая/восстановленная S проверяется свежим fetch выбранного remote и ancestry относительно R прежде incoming-only/divergence и new-write gates. Достижимая S даёт confirmation-only без push/повторных write/close даже при более новом R/L; известная S не подменяется новым HEAD. После push, отказа или неоднозначности снова проверяются remote и S независимо от ответа push. Неизвестная S или failed remote/ancestry read остаются unverified, не разрешают replay. Receipt различает S, наблюдаемую local L и свежую remote R: общая moving branch не гарантирует точный snapshot отправки, независимое доказательство разрешения каждого исторического действия или равенство всех полей. Более новые действия этим receipt не принимаются. При частичной Git/трекер-публикации эффекты сохраняются; повтор проверяет лишь недостающее, без повторного принятия, создания ID или закрытия.

## 5. Владение интерфейсом

Общая семантика `tasks` версии 1 находится в разделе 4 этого документа, без второй нормативной копии в `ris-proj-lib-common`. Прикладной скил знает требуемую операцию и её контракт, адаптер — отображение на реальный инструмент. Установленные скилы содержат достаточные рабочие требования без обращения к этому репозиторию.

В адаптере остаются ссылка на контракт, поддерживаемая версия, настройки и особенности реализации. Не нужно повторять весь интерфейс или создавать скил лишь ради хранения короткой таблицы. Несовместимое изменение требует обновить потребителей и проверки.

## 6. Результат выполнения

Для операций ris используется небольшой набор состояний:

| Состояние | Значение |
|---|---|
| `ok` | Заявленный контракт выполнен и проверен |
| `blocked` | Не хватает обязательного входа, зависимости, разрешения, решения или проверки |
| `conflict` | Конкурентное изменение либо существенное противоречие состояния |
| `error` | Выполнение завершилось технической ошибкой |

Это не статусы задач трекера и не характеристики покрытия или готовности артефакта. Самостоятельного статуса `partial` нет. Для незавершённой заявленной операции выбирается состояние фактической причины остановки; отдельно указываются сохранённые эффекты с подтверждениями, причина и точный остаток. Полный `ok` такой операции не возвращается.

`ok` относится к явно запрошенной границе: успешно проверенное предложение или явно ограниченное локальное сохранение может быть `ok`, но не означает принятия, публикации или готовности следующего этапа. Остаток за этой границей называется отдельно; нельзя задним числом сузить полный запрос ради `ok`. При восстановлении сначала проверяются реальные файлы, ID, commits, закрытие и состояние каждого удалённого канала; уже совершённые эффекты не повторяются по одному лишь статусу или старому маркеру.

Результат содержит полезные данные, фактические изменения, достаточные подтверждения, ограничения и данные следующего действия. Если операция не меняет состояние, отсутствие изменений указывается явно.

```yaml
status: blocked
operation: tasks.epics.update
value:
  id: E-003
changes: []
evidence:
  - Текущая запись прочитана перед изменением
limitations:
  - У используемого доступа нет права записи
next_action: Получить разрешённый доступ либо передать изменение владельцу
```

Это иллюстрация формы. В реальном отчёте подтверждение ссылается на действительный результат чтения или команды, а не копирует шаблон. Эквивалентные Markdown-разделы допустимы; JSON/YAML обязателен только при программном потребителе.

`ok` для подготовки предложения не означает сохранение или принятие. `ok` для записи не означает содержательное одобрение документа. Границы этих состояний раскрываются в [06](06-artifacts-and-handoff.md).

## 7. CLI и скрипты

Адаптер использует действительно доступный инструмент и проверенный контракт. Команды не сочиняются по условным именам операций. Проверяются необходимые разрешения, совместимость и параметры; не требуется механически повторять `--help` перед каждым вызовом.

Аргументы и данные отделяются от исполняемого кода. Пути, заголовки и тексты не вставляются в небезопасную shell-строку. Конфигурация не исполняется через `eval`; секреты не включаются в отчёт.

После вызова проверяются статус завершения, ответ и достаточные свидетельства изменения. При неоднозначном результате сначала устанавливается фактическое состояние, а не повторяется потенциально дублирующее создание.

Ресурсы инструментов разрешаются от каталога адаптера. Язык скрипта и конкретные детали запуска относятся к реализации; универсальное требование использовать Bash, Go или Python не вводится. При наличии программного потребителя машинные данные и диагностика должны быть различимы, а временные ресурсы — безопасно очищаться.

## 8. Конкурентная запись

До изменения устанавливаются актуальная цель, ownership где нужен claim и разрешённая область. Обычная своя задача и явно порученные общие записи изменяются штатными атомарными/условными операциями и точечными полями после свежей сверки, с независимым read-back. Не требуется ручная пауза, обязательный глобальный lock/координатор/очередь или общая транзакция над задачей, графом и внешним evidence. Гарантии каждого нативного действия ограничены его реальными предикатами.

Атомарная замена файла защищает от частичной записи, но не сама по себе от потери параллельного изменения. Гарантия отсутствия потерянных обновлений требует дополнительного протокола; инструкция агенту не является таким протоколом.

Блокировка не удерживается во время диалога или длительного анализа. При конфликте выполняются перечитывание и согласование либо возвращается `conflict`. Молчаливая перезапись чужой работы запрещена.

Перед повтором создания исключается уже состоявшаяся операция. Ключ идемпотентности применяется, если его поддерживает инструмент; отсутствие этой возможности не скрывается.

Для адаптера Beads разрешённое создание задач и эпиков без специального требования строгой уникальности работает как best-effort без отдельного согласования конкурентного риска на каждый вызов. Проверка существующей записи и результата остаётся обязательной, но не выдаётся за гарантию отсутствия дублей при параллельном создании: `bd` не обеспечивает уникальность внешней ссылки. Если явно требуемую строгую гарантию или сложное действие нельзя корректно обеспечить доступной операцией, возвращается точное ограничение до зависимой записи, не запрос остановки писателей. При обновлении сохраняются нецелевые поля, чужая проза и закреплённое acceptance evidence; неожиданные изменения требуют сверки, а не молчаливой перезаписи.

Прямая запись обычного Markdown допустима при соблюдении правил проекта и конкурентного изменения. Если обязательный CLI обеспечивает согласованность, отсутствие доступа к нему не разрешает обход через файлы. Отдельный универсальный адаптер документов не требуется ради симметрии.

## 9. Готовность входов и выходов

Наличие файла, доступность его чтения и содержательная готовность — отдельные вопросы. Скил проверяет принадлежность выбранной работе, актуальность, статус принятия и достаточность нужных разделов.

Служебная операция может проверить формат, но не должна сама объявлять спецификацию достаточной для реализации. Общий стандарт готовности проекта дополняет критерии конкретного задания и контракт скила; правила подтверждения приведены в [07](07-quality-and-verification.md).

## 10. Завершение

Прикладной скил останавливается после своего проверенного результата либо явного неполного завершения. Он может подготовить передачу, но не запускает следующий этап без основания.

Служебная операция завершает только порученное действие; методика действует в переданной области; общий документ не начинает новый процесс. Эти границы позволяют сочетать компоненты без скрытой рекурсивной оркестрации.
