# Пример содержания спецификации фичи для RIS

[Каталог SDLC MVP](../ris-sdlc-mvp-skills.md)

Это **пример смыслового профиля**, а не готовая нормативная спецификация фичи, обязательный набор Markdown-заголовков или шаблон OKF-бандла. По [целевой методике](../08-sdlc-methodology.md) новые документы фичи находятся в `sources.specs/<full feature ID>/spec.md` — обычном Markdown без OKF-индекса; корень `sources.specs` задаётся конфигурацией проекта (default `docs/specs/`). Путь использует полный подтверждённый ID без title/slug-суффикса и не меняется при переименовании заголовка. Существующие документы читаются по проверенным явным ссылкам без перемещения или миграции. Автор указывает источник и статус существенных решений; непринятое предложение не становится требованием от записи в файл.

| Сведения | Что должен понять следующий исполнитель |
|---|---|
| Цель и область | Какой результат должна дать фича, какие сценарии и пользователи охвачены, с какой верхнеуровневой концепцией она связана. |
| За пределами области | Что явно не входит сейчас, какие будущие возможности остаются открытыми. |
| Поведение | Основные и альтернативные сценарии, ошибки и исключения, важные состояния и условия переходов. |
| Ограничения и контракты | Численные пределы, отрицательные требования, публичные интерфейсы и совместимость, если они существенны; условия их применимости. |
| Проверяемость | Критерии приёмки с практическим how-to-check: условия/вход, наблюдаемый результат и доступный oracle/способ проверки, достаточные для декомпозиции и последующей проверки. |
| Решения и вопросы | Какие решения приняты, какие предложены, что известно как факт, какие вопросы остаются открытыми и что именно они блокируют. |
| Прослеживаемость | Полный подтверждённый ID фичи, локально устойчивые `AC-001`, `AC-002` (новые ссылки `<full feature ID>#AC-nnn`), точные пути и применимые версии источников product без глобальных ID; существующие legacy AC-ссылки сохраняются, ID удалённого AC не используют повторно для другого смысла. |
| Дизайн | Достаточный технический подход, существующие контракты, владельцы состояния и test seams — в отдельно проверяемом непересекающемся разделе `spec.md` или, при необходимости, в `design.md`. Требования и дизайн имеют независимо достаточное прямое/унаследованное/смешанное основание по [06 §4](../06-artifacts-and-handoff.md#4-сохранение-согласованных-решений): точные источники/исходные решения и объяснение следования, фактическое принятие только нового существенного в контексте полного кандидата. Один акт может охватить новое в обеих областях; наличие файла не подтверждает основание. |

Не нужно создавать пустые разделы ради шаблона. Информация может быть распределена по связанным документам, если ссылки доступны, статус понятен, а следующий исполнитель не должен восстанавливать решения из прежнего чата. Проверка формата документа, в том числе OKF, не заменяет содержательную сверку этих сведений.

Короткая достаточная spec/design допустима без минимальной длины и квоты разделов.
Допустимое policy-принятие полного prepare проверяется по [06 §4](../06-artifacts-and-handoff.md#4-сохранение-согласованных-решений)
отдельно от human approval и inheritance; оно не убирает содержательных вопросов
и не включается от config при прямом вызове.
Spec не ведёт task backlog, статусы исполнения или checklist. Дизайн заполняет
материальные пробелы, ссылаясь на применимые архитектуру/контракты вместо пересказа;
design.md и ADR нужны только по существу. Доменные подсказки (например, balance,
frame/audio/softlock для игр) и отложенные параметры применимы только там, где
они действительно существенны, не как анкета для любого проекта.
