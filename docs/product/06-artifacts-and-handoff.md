# 06. Артефакты, решения и передача работы

[Оглавление](index.md) · [Product, Architecture и Delivery](08-sdlc-methodology.md)

## 1. Назначение

Следующий исполнитель должен получать не только название этапа и факт предыдущего обсуждения, но и достаточные исходные данные. Существенные согласованные решения не должны зависеть от сохранности всей истории чата.

Этот документ определяет требования ris к рабочим артефактам. При реализации общая процедура размещается в `ris-proj-lib-common/references/artifacts.md`; содержательное наполнение конкретного документа остаётся у прикладного скила.

## 2. Уровни документов

По принятому [ris-wcv](../specs/ris-wcv/spec.md) новые feature-документы используют
`sources.specs/<full feature ID>/spec.md`, H1 readable name и column-zero
Feature-ID/Summary/optional Keywords; sufficient design inline либо design.md.
Обычная independent scope/version acceptance notation сохраняется с исходной
provenance, без duplicate refs/readiness/verification registry в Beads. Legacy
explicit links/readable payload hints ведут к actual documents/decisions без schema
gate/миграции; old data/history не переписываются. Missing/old/malformed JSON сам
по себе не блокер. Feature close требует substantive current assessment, не её
обязательного сохранения. Ordinary/document-only/bug не получают искусственный ID
или feature-каталог; versioned bug basis (§4.1) и review YAML остаются отдельными входами.

| Артефакт | Что содержит | Что не заменяет |
|---|---|---|
| Концепция / проектная спецификация | Назначение продукта, основные сценарии, общие правила и границы | Подробный план каждой фичи |
| Roadmap как эпики в трекере | Крупные результаты, MVP, эпики, зависимости и приоритеты | Второй независимый трекер или автоматический файл roadmap |
| Описание эпика | Ограниченный результат и состав выбранного направления | Все технические решения будущей реализации |
| Спецификация фичи | Поведение, исключения, ограничения и критерии принятия | Проектную концепцию или универсальные правила разработки |
| Задачи / зависимости | Проверяемые единицы реализации и необходимые блокировки | Новую независимую версию требований или технический план |
| Глоссарий | Точные значения доменных терминов | Спецификацию, журнал ответов или технические заметки |
| ADR | Значимый выбор, альтернативы и причины | Запись каждого локального решения |
| Ревью / диагностика | Наблюдения, подтверждения и выводы в заданной области | Принятие владельцем или автоматическое исправление |

Все виды документов не обязательны для каждой задачи. Применяется минимальный набор, достаточный для контракта и передачи. Каталоги источников и базовые общие каталоги задаются конфигурацией; конкретные документы — заданием и связями документов, записи roadmap — контрактом выбранного трекера. Не выводить адрес из имени скила или считать выбор адаптера его реализацией. Defaults `.sdlc/tasks/<tracker-task-id>/` и `.sdlc/worktrees/<tracker-task-id>/` относятся к обычной исходной папке и предполагают подтверждённый ID; явные workspace leaf overrides заменяют defaults независимо от наличия выходных папок. `ris-proj-op-resolve-context` по [02](02-configuration.md#3-две-базы-путей) вычисляет source folder из actual common `.git`, без saved-primary discovery; возвращает базовые каталоги, ничего не создаёт и не разрешает менять source checkout. Источники читаются в текущем worktree.

В [целевом SDLC MVP](ris-sdlc-mvp-skills.md) первым трекером выбран Beads с явной настройкой адаптера; операции roadmap и необязательные операции задач фичи `tasks` v1 уже реализованы, остальные целевые возможности не следуют из этого. Локальное ревью выбранной задачи сохраняется под настроенным `workspace.tasks/<подтверждённый ID>/`, без дополнительного slug проекта. По принятым S1 §4 / D1 §5 отдельный planner, сохранённый план и implementation-report удалены без замены/распределения полей по другим артефактам. Исполнитель проверяет достаточность входов/актуальный код и выбирает подход; старые планы — optional context. Названия остальных действительно необходимых артефактов определяются их владельцами, не угадываются по имени скила. [Профиль содержания спецификации фичи](templates/feature-spec-content.md) не устанавливает обязательный формат файла и не заменяет проверку принятых решений.

## 3. Статус артефакта

Адресная поправка review-YAML из принятых [S1 §5](../specs/sdlc-feature-lifecycle/spec.md#5-полный-yaml-отчёт-ревью)
и [D1 §6](../specs/sdlc-feature-lifecycle/design.md#6-review-yaml-предлагаемый-контракт-risreview1):
обычное проектное ревью сохраняет один локальный `review.yaml` по
[ris.review/1](../../skills/ris-proj-op-review-task/references/report-format.md).
Единственный авторитет содержания/вердикта — YAML с полной историей раундов;
Beads содержит только адрес/раунд, без копии вердикта/замечаний. Краткий итог,
Git SHA и факты завершения остаются в трекере, не заменяя ревью. По умолчанию путь
`workspace.tasks/<ID>/review.yaml` от проверенной primary; без ID нужен явный
разрешённый путь. Другая локальная сессия может прочитать отчёт; удалённое хранение,
доступ с другой машины и публикация вместе с кодом не требуются. Fast сохраняет
независимое ревью без обязательного файла, optional save — в том же формате.
Исторические отчёты не переписываются. Остальные изменения будущего lifecycle
этим адресным контрактом не вводятся.

**Подготовлен, сохранён, проверен и принят — независимые характеристики, а не обязательная универсальная машина состояний.**

Подготовленный текст может быть не сохранён. Сохранённый черновик может не быть принят. Проверка структуры не является проверкой смысловой полноты. Принятое поведение не означает, что оно уже реализовано.

При завершении указываются относящиеся к результату характеристики и ограничения. Если нужен факт принятия, он устанавливается по принятому в проекте механизму, а не выводится из существования файла или успешной команды записи.

## 4. Сохранение согласованных решений

При разрешённой записи существенные согласованные блоки фиксируются в предусмотренном артефакте по ходу работы, не обязательно после каждой реплики. Перед передачей отдельно сверяется полнота.

Требования и достаточный дизайн имеют независимо адресуемые непересекающиеся области/версии. По [S1 §3 / D1 §4](../specs/sdlc-feature-lifecycle/acceptance.md) один attributable акт может принять оба полных кандидата, явно перечисляя каждый selector/version и принятие. Один decision address тогда допустим для обоих refs; каждый owner проверяет свою запись решения без повторного вопроса. Согласие только с требованиями не принимает дизайн. Короткий достаточный дизайн может занимать отдельную секцию spec.md; design.md/ADR не требуются ради формы. Уже принятое whole-file requirements нельзя молча расширить дизайном без адресного изменения принятия.

Каждое решение, влияющее на выполнение следующего этапа, должно находиться в его предусмотренных входах. Глоссарий и ADR не подтверждают сохранение всех договорённостей.

Для ещё не опубликованного документа сохраняются актуальное принятое содержание и его отдельное фактическое решение с точной версией, доступные следующему этапу. При существенной замене кратко указываются заменённая версия/решение, суть изменения и новое фактическое принятие; принятие не выводится из записи файла. Полный архив промежуточных принятых snapshots, журнал черновиков, промежуточная публикация или commit на каждое согласование не обязательны. Локальные черновики/commits допустимы добровольно.

Уже опубликованные версии и решения сохраняются в Git-истории без её переписывания, их immutable ссылки остаются на исходных ревизиях. Копия решения не возобновляет принятие и не перепривязывает `containing-commit`. При изменении требований владелец дизайна проверяет применимость зависимого дизайна: совместимый неизменённый дизайн сохраняет исходное принятие, содержательно изменившийся требует отдельного решения. Неопределённость блокирует только зависимое продолжение, не независимую разрешённую работу.

Пример распределения:

| Согласованное содержание | Место |
|---|---|
| Значение «попытка выполнения» | Глоссарий, если используется |
| Причина труднообратимого выбора | ADR, если выполнены критерии его создания |
| Не больше трёх повторов | Спецификация поведения |
| Автоповторы исключены из MVP | Границы MVP / эпика |
| Поведение при прерывании ещё не определено | Открытые вопросы соответствующего артефакта |

Нельзя ослаблять смысл при переносе: терять числа, порядок, исключения, отрицательные требования и условия применимости. «Не более трёх повторов» нельзя заменить на «поддерживаются повторы».

Предложения, принятые решения, факты и допущения остаются различимыми. Подтверждение части предложения не превращает остальные части в утверждённые требования.

### 4.1. Воспроизводимое основание bugfix

Admission выбирает достаточные report/criteria/decisions, inspected code revision
и существенную среду. Для mutable tracker-записи используется точная сохранённая
версия истории; для Git-источников и реального отдельного принятия — исходные
immutable commit/path/section. Адаптер независимо читает и сравнивает полные
использованные поля исторической записи. Неполнота, недоступная версия или ссылка
без читаемого содержания блокируют зависимое исполнение; текущий HEAD не замена.
Несохранённое существенное решение сначала сохраняет его действующий owner.

Короткий ordinary basis locator в notes, если нужные адреса ещё не сохранены,
позволяет новой сессии обнаружить входы по project+ID без чата/локальных файлов.
Полная дополнительная копия report/criteria/decisions в notes, новый файл или
обязательный text handoff не нужны. История сохраняется и входит в отдельно
разрешённую Dolt-публикацию; это не гарантирует доступности внешних ссылок.
CLI, проверка полноты исторических полей, targeted append и reconcile после
неоднозначного ответа принадлежат [Beads adapter](../../skills/ris-proj-adapter-beads-tasks/references/bug-execution.md),
а не копируются в flows/предметные wrappers. Нет нового API/реестра/schema record.

Material drift требует только затронутой change/review/evidence reassessment и
нового locator для допущенного basis. Старые locators/full snapshots не
переписываются и могут служить фактическим историческим входом без миграции.
Совместимые evidence переиспользуются с основанием; уже опубликованное/закрытое
не отправляется и не закрывается заново. Отдельные substantive acceptance,
claim/blockers/copy/review/Git/result/close/Dolt gates сохраняются.
Основание: принятые [ris-ppw S1 §7 / D1 §4](../specs/ris-ppw/spec.md).

## 5. Глоссарий и ADR

Новые файлы создаются только при наличии содержимого, необходимости и разрешения. Сеанс без новых терминов или значимых архитектурных решений может корректно не изменить ни глоссарий, ни ADR.

Если проект не задал иных критериев, ADR предлагается для решения, которое одновременно имеет заметную стоимость пересмотра, нуждается в объяснении для будущего читателя и является реальным выбором между альтернативами. Это адаптация подхода domain-modeling, а не требование записывать любую реализационную деталь. [S5](sources.md).

Способ ведения старых ADR и локальных глоссариев определяется проектом. Не следует молча переписывать историю принятого решения или создавать глобальный глоссарий там, где понятия различаются по контекстам.

## 6. Работа без записи и частичный результат

При запрете записи решения включаются в подготовленный ответ с явной отметкой, что они не сохранены. Нельзя создавать скрытые постоянные заметки или менять глоссарий в обход разрешения сохранить только другой документ.

Если последующий этап требует сохранённого артефакта, такой вход пока не готов. Можно передать сам текст, если контракт допускает вход из ответа и получатель действительно его получил. Нельзя предполагать автоматическую передачу всей истории.

При частичной записи перечисляются реально изменённые файлы и несохранённые части, подтверждения, фактическая причина остановки и точная оставшаяся операция. Выбирается `blocked|conflict|error` по причине, без самостоятельного `partial`. Эти статусы не стирают уже совершённых изменений; откат тоже должен быть отдельным разрешённым и проверенным действием. Явно ограниченный успешный вклад может быть `ok` только в своей границе, с отдельным остатком до полного результата, не как скрытое сокращение запроса.

## 7. Обновление существующего документа

До правки читаются актуальный документ и применимые источники. Сохраняются идентификаторы, ссылки и действующие решения, если их изменение не является частью задания.

Незавершённый план другой работы нельзя перезаписывать, закрывать или переименовывать для удобства нового задания. Нужно определить конфликт и разрешённое место нового результата, не уничтожая состояние другого процесса.

Относительные ссылки проверяются от каталога документа. После записи проверяются доступность и содержание результата; существование файла не заменяет проверку обязательных смысловых разделов.

При общих файлах между сессиями соблюдается протокол из [04](04-contracts-and-adapters.md). Фиксация «по ходу разговора» не разрешает удерживать блокировку на всё время интервью.

## 8. Минимальная передача

Передаваемое задание должно позволять установить:

| Сведения | Назначение |
|---|---|
| Цель и текущий этап | Что именно поручено получателю |
| Проект, конфигурация, worktree | Где выполняется работа и как разрешать пути |
| Выбранный скил | Какую методику применять |
| Входные артефакты и состояние | Какие требования и факты являются входом |
| Существенные решения и ограничения | Что нельзя потерять при продолжении |
| Открытые вопросы | Что заблокировано и где допустимо допущение |
| Разрешённые изменения | Где проходит граница действия |
| Ожидаемый результат | Что вернуть и чем подтвердить |

Это состав данных, не новый обязательный `HANDOFF.md` или отдельная база решений. Допустим блок в существующей задаче, сведения оркестратора или входные документы с однозначными ссылками. Нельзя плодить вторую копию всех требований ради передачи.

Для вызова субагента передавай минимальное достаточное задание, а обратно принимай компактный результат: фактические ID и адреса входов/выходов либо применимое соглашение об их обнаружении, статус их принятия, подтверждения и ограничения. Базовый каталог `workspace.tasks/<подтверждённый ID>/` сам по себе не определяет имя любого файла: нужны соглашение владельца действительно необходимого артефакта или точный адрес. Получатель подтверждает ID и заново разрешает используемый shared путь от проверенной primary. Обязательное обнаружение плана/implementation-report или omission-decision не требуется. До появления подтверждённого ID фичи допускается явная сводка ответов и доступные проектные источники; обязательный черновик спецификации или новый каталог памяти не создаётся. Наличие конфигурации не передаёт историю чата и не доказывает возможность чтения файла из другой сессии, worktree или контейнера.

Для многосессионного процесса существенные решения сохраняются в уже предусмотренном постоянном входе. Получатель должен уметь продолжить работу без исходного диалога.

## 9. Контроль полноты передачи

Короткий command+ID начинает discovery: точное чтение kind/key/content/links,
состава и typed blockers через выбранный адаптер, затем actual accepted versions
и отдельные decisions по ссылкам. Доступные факты не спрашиваются заново.
Missing/ambiguous/stale input именуется точно и блокирует зависимую часть.
Структурный parent даёт контекст, но не заменяет собственный scope/criteria/
refs/contracts/seams ребёнка и не делает его feature. Для standalone simple
task достаточны принятые constraints; material design требует отдельного решения.
ID не является snapshot или разрешением на документы. Получатель проверяет
фактическое дерево и доступность локальных reports по соглашению своего owner;
отсутствующий путь/право остаётся явным gap. Session history и OKF root сохраняют
свои самостоятельные locator, ID задачи их не подменяет.

Каждый итог восстанавливаем: фактический result/identity, точный locator либо
проверенное соглашение обнаружения с ключами/именем файла, input/result versions
и отдельные decisions, честные saved/accepted/published факты каждого применимого
канала, limits и точный unfinished remainder. Git, tracker write, completion и
tracker publication/read-back не доказывают друг друга. Вложенный результат
возвращается вызывающему без обязательного next-skill prompt; нового registry,
handoff schema или draft store нет. До ID не выдумывать ID/path/ref. При отсутствии
inspectable authorized source response-only итог содержит discovery gap, а не
обещание доступности новой сессии. Локальные заметки не remote input другой copy.
Primary provenance передаётся как evidence, но получатель заново проверяет
применимость, права и требуемые claim/blockers/защиту; старое окно/lease/worktree
не допуск. После прерывания сначала сверяются actual effects и версии, затем
выполняется лишь недостающее; unchanged decisions сохраняются. Recovery не
ветвится только по статусу: известный ID не создаётся заново, подтверждённое
закрытие не повторяется, неизвестный push сначала сверяется с remote, а при
pending Git read-back проверяется уже отправленный commit; для Dolt свежо
подтверждается достижимость точной требуемой ревизии S из выбранного remote R.
Более новая R не отменяет S; неизвестная S или failed remote/ancestry read не
разрешают повторный push/close. Локальный результат/записи проверяются отдельно:
Dolt receipt не обещает полного равенства полей или точного snapshot отправки
общей moving branch (контракт публикации — [04](04-contracts-and-adapters.md#4-адаптеры)).

Отдельно запрошенная read-only навигация может вернуть короткий prompt с реальным
установленным владельцем и подтверждённым ID либо exact no-ID locator. Она проверяет
текущие факты, версии/отдельные решения и совместимость required inputs; при пробеле
возвращает exact blocker или необходимое человеческое решение. Рекомендация не
сохраняется автоматически, не является разрешением/readiness и не исполняется;
вложенный ответ возвращается caller. Это исключение для самостоятельного результата,
не обязательный next-skill prompt в каждом атомарном handoff.

Перед завершением прикладной скил сопоставляет принятые решения с результатом. Для небольшой задачи достаточно смысловой сверки; для сложной — компактной таблицы «решение → раздел артефакта». Постоянная полная трассировка каждого ответа до теста не требуется.

Проверка должна выявлять не только отсутствующие пункты, но и ослабленные формулировки, неразрешённые противоречия и потерю границ. Ссылка на документ допустима лишь тогда, когда получатель имеет к нему доступ и в нём действительно есть нужные сведения.

Подготовка эпиков roadmap не означает сохранения в трекере, рекомендация эпика — назначения исполнителя, а передача ревью — разрешения на merge.

## 10. Критерии готовности передачи

Передача пригодна, когда определены её цель и область; необходимые решения доступны получателю; источники и статус принятия различимы; открытые вопросы не скрыты; адреса разрешимы в его окружении; фактические изменения и пределы проверки отражены.

При отсутствии обязательного элемента блокируется зависимое продолжение. Не нужно останавливать независимую работу, но нельзя объявлять этап полностью завершённым, если его обещанный вход для следующего исполнителя утрачен.
