# 02. Конфигурация и параметры выполнения

[Оглавление](index.md)

## 1. Назначение и значения по умолчанию

Методика скила, постоянная настройка проекта, параметры задания, проектные правила и текущее состояние — разные категории. `ris-proj-op-resolve-context` готовит настройки и диагностику выбранной операции, но не читает вместо прикладного скила содержание документов, не выбирает конкретный документ и не записывает файлы. `ris.yaml` — необязательное соглашение RIS версии 2, не встроенная функция Agent Skills или OpenCode. Профиль документов и модели Product/Architecture/Delivery описаны в [08](08-sdlc-methodology.md).

Если проектного файла нет, применяются пакетные defaults:

```yaml
version: 2
sources:
  rules: docs/rules/
  product: docs/product/
  specs: docs/specs/
workspace:
  tasks: .sdlc/tasks/
  worktrees: .sdlc/worktrees/
```

Это каталоги, а не файлы документов. В профиле RIS `product` и `rules` — два самостоятельных OKF 0.2-бандла; `rules/architecture/adr/` вложен в rules, а новые feature `specs/<full feature ID>/spec.md` — обычный Markdown по [ris-wcv](../specs/ris-wcv/spec.md). Старые явные source links сохраняются без перемещения. Отдельного поля для ADR или формата OKF нет. Контекст проверяет пути, но не формат, содержательную готовность или принятие документов: их проверяет потребитель. Конкретные документы выбирает прикладной скил. Поставка RIS отдельно, глобально или в составе Gas City Pack не меняет defaults.

Выбранный валидный `ris.yaml` задаёт свои значения; единственное дополнение — два workspace leaf defaults: отсутствующий `workspace.tasks` получает `.sdlc/tasks/`, отсутствующий `workspace.worktrees` — `.sdlc/worktrees/`, включая отсутствие всего `workspace`. Явный валидный leaf заменяет только своё значение. Для `sources.*`, adapters и roles пропуски не дополняются. Наличие каталогов не выбирает настройки; невалидные присутствующие поля не обходятся defaults. Необходимые поля зависят от операции. Пример полной конфигурации другого проекта:

```yaml
version: 2
sources:
  rules: handbook/policies/
  product: handbook/visions/
  specs: plans/features/
workspace:
  tasks: .local/task-notes/
  worktrees: .local/branches/
adapters:
  tasks:
    skill: example-task-adapter
    options:
      board: example
```

Имя адаптера и его `options` здесь лишь пример выбора; его наличие в конфигурации не доказывает установку, поддержку какой-либо операции или существование адаптера с таким именем. Схему `options` определяет конкретный адаптер, когда он нужен.

| Поле | Тип и применимость |
|---|---|
| `version` | Обязательное целое (не boolean), ровно `2`, если файл существует |
| `sources.rules` | Непустой путь каталога; обязателен, когда операция нуждается в проектных правилах из него |
| `sources.product` | Непустой путь каталога авторского описания желаемого продукта; обязателен, когда операция нуждается в нём |
| `sources.specs` | Непустой путь каталога; обязателен, когда операция нуждается в спецификациях |
| `workspace.tasks` | Непустой явный путь либо default `.sdlc/tasks/`, также в выбранном config |
| `workspace.worktrees` | Непустой явный путь либо default `.sdlc/worktrees/`, также в выбранном config |
| `adapters.tasks.skill` | Непустое имя; обязательно только при операции с выбранным адаптером задач |
| `adapters.tasks.options` | Необязательное отображение данных; контракт выбранного адаптера определяет его содержимое |

Разделы `sources`, `workspace`, `adapters` и `adapters.tasks`, если есть, — отображения. Неизвестные ключи вне расширяемого `options` — ошибка; неиспользуемые, но присутствующие поля также должны иметь корректный тип. Пустые строки и `null` не заменяют отсутствующее поле. Поддерживаются только простые YAML-отображения, списки и скаляры; запрещены пользовательские теги, дубли ключей, merge-ключи и алиасы. Нет `extends`, автоматического слияния, сетевых импортов и исполняемых выражений. Ошибочный файл не заменяется defaults.

**Миграция v1 → v2 явная:** конфигурация с `version: 1` или `sources.concepts` отклоняется с диагностикой. Владелец проекта определяет, где находятся действительные авторские материалы, меняет версию на `2`, заменяет старый ключ на `sources.product` с проверенным путём и сверяет прочие поля, ссылки и потребителей. Старый каталог концептов не становится автоматически авторским product. Если `docs/product/` ещё не создан, отсутствие блокирует лишь операции, которым он нужен как существующий вход; не следует подставлять `docs/concepts/`. Ошибочный файл не заменяется defaults; для валидного файла действуют только два workspace leaf defaults выше.

**Собственный проект RIS:** по явно принятому решению `ris-2jn` бандл
`docs/concepts/` переименован в `docs/product/` и служит `sources.product`
уже настроенного корневого `ris.yaml` v2. Нормативная методика и дизайн RIS
остаются частью этого бандла. Это конкретный разрешённый перенос, а не
автоматическая миграция или alias для проектов-потребителей. Наличие бандла
не означает принятия его содержимого или готовности для любой операции;
конкретные входы, версии и достаточность проверяет потребитель.

### Необязательные исполнители ролей

Execution full (bugfix через full) после подтверждённых task close/publication использует
`container-completion` для одного свежего субагента на всю реальную цепочку предков;
init рекомендует `standard`. Без родителя или при явном запрете каскада эта роль
не нужна. Отсутствующий binding не дополняется и не вызывает смену модели:
зависимый каскад остаётся незавершённым, leaf completion сохраняется отдельно.
Существующие проекты согласуют добавление роли, без нового уровня `simple`.
Fast выполняет этот общий каскад основным агентом без обязательной роли/субагента;
`task-review` запрашивает только при активном обязательном ревью по [07](07-quality-and-verification.md).
Default Fast не требует неиспользуемых ролей и не загружает review-format.

Необязательное поле `execution` в том же `ris.yaml` версии 2 задаёт исполнителей делегированных операций. По принятому [T7](../specs/sdlc-audit-remediation/spec.md#t7-уточнить-смысл-executionroles) ведущий может выполнить разрешённую работу через владельца сам либо делегировать её; каждый внутренний шаг не требует отдельного агента. После [ris-a17](../specs/ris-a17/spec.md) подготовка потребляет при делегировании `feature-preparation` или `task-decomposition` (также для необязательных предложений графа фич), независимое ревью — `task-review`. Прямые планирование/навигация не требуют роли селектора; существующие bindings не мигрируются автоматически. Прямое исполнение не требует неиспользуемых ролей. Пример допустимой формы:

```yaml
execution:
  roles:
    task-decomposition:
      agent: standard
    feature-preparation:
      agent: advanced
```

`roles` — отображение смысловых ролей прикладных операций на непустые имена **проектом предоставленных** субагентов OpenCode; значения `standard` и `advanced` здесь лишь пример, не встроенные модели или обязательное соответствие ролей уровням. При делегировании вызывающий применяет настроенную роль и проверяет доступность/полномочия и фактический запуск. Отсутствующая или недоступная необходимая роль блокирует зависимый делегированный маршрут: без молчаливой подмены исполнителя/модели или дополнения проектных bindings пакетными значениями. Разрешённый прямой маршрут выбирается явно, не выдаётся за успешное делегирование. Роль сама не доказывает модель, запуск, независимость или использование Advanced для реализации. Обязательный независимый reviewer фактически запускается отдельно от всех авторов/исправителей даже при общем имени агента или модели; прямое исполнение не заменяет его. Изменения моделей и пользовательских bindings требуют согласования.

Разделы `execution`, `execution.roles` и значения отдельных ролей — отображения; ключ роли — непустой, не состоящий из одних пробелов смысловой идентификатор из контракта операции, допустимый ключ записи роли — только `agent` с непустой, не состоящей из одних пробелов строкой. Пустое отображение ролей допустимо, но не удовлетворяет вызов с требуемой ролью; присутствующая запись без `agent` невалидна. Сохраняются общие запреты дублей, алиасов и неизвестных полей. Эта настройка не даёт полномочий и не определяет порядок этапов. Другие способы запуска, включая отдельную CLI-сессию, не заявлены поддерживаемыми. Исторические [упрощение подготовки](../specs/feature-preparation-simplification.md) и [первый срез](../specs/ris-feature-work-first-slice.md) сохраняют свои версии; текущие правила роли описаны выше, предметные контракты — у вызывающих owners.

## 2. Выбор проекта и конфигурации

Сначала установить целевой проект и его `project_root` из задания, рабочего окружения и применимых инструкций; не выводить его из расположения RIS, установленного скила или файла конфигурации. Поддерживается один Git-репозиторий — один проект: текущий project root совпадает с repository top-level. Monorepo subprojects не поддерживаются; вложенные конфигурации не наследуются. Неоднозначность блокирует зависимую операцию, не запускает поиск копий.

Только после выбора корня выбрать файл в следующем порядке: (1) явно указанный путь из задания; (2) единственный применимый указатель в инструкциях выбранного проекта, например `AGENTS.md`; (3) `ris.yaml` непосредственно в `project_root`. Не искать вверх или вниз. Указатель из родительских инструкций подходит, только если они применимы и однозначно указывают конфигурацию этого проекта. Несколько одинаково приоритетных указателей — неоднозначность, блокирующая зависимую работу.

Относительный путь из задания считается от известной директории запуска, указатель в `AGENTS.md` — от каталога этого файла. Явно выбранный недоступный, отсутствующий или невалидный файл — ошибка; нельзя пробовать соседние файлы или defaults. Отсутствие невыбранного `ris.yaml` в корне — штатное применение defaults. Не создавать конфигурацию автоматически.

## 3. Две базы путей

| Путь | База |
|---|---|
| `sources.*` (проектный или default) | `project_root` выбранного проекта в текущей рабочей копии |
| Относительные `workspace.*` (явные или default) | `primary_root`: обычная исходная папка из фактического общего Git-каталога |
| Путь к файлу конфигурации из задания | Директория запуска |
| Указатель в `AGENTS.md` | Каталог файла `AGENTS.md` |
| Ресурс скила | Каталог установленного скила-владельца |
| Относительный путь документа, переданный в задании | `project_root`, если заданием не установлена другая явная база |

Context получает physical top-level/common-dir текущей копии и проверяет обычную
исходную папку — родителя фактического общего `.git`-каталога: доступность,
non-bare, обратное Git mapping и регистрацию обеих копий в одном репозитории.
Имя ветки, первая строка worktree list и наличие `.sdlc` не выбирают root.
`primary_root` остаётся внутренним совместимым именем базы shared-путей, не реестром.
Нет saved-primary discovery, каскада кандидатов и сканирования диска. Старый явно
переданный root может только подтвердить Git-derived адрес; противоречие — conflict.
Bare, отсутствующая исходная папка, нестандартный common-dir и multi-project mapping
дают короткую диагностику зависимого действия, не выбор другого worktree.
Независимо полезные current-copy settings сохраняются. Context возвращает root,
проверенную Git association и ограничения без сохранения результата. При смене
копии перепроверяется эта связь, а не старые hints. Права/claim/blockers и защита
записи остаются у действующего владельца.
Разрешение адресов review/worktree не даёт права менять файлы/ветку основной копии.
Путь к `ris.yaml` сам по себе не определяет ни один из корней. `workspace.tasks`
и `workspace.worktrees` — только базовые каталоги: пока нет подтверждённого ID
задачи, не выдумывать путь `<id>`, ветку или имя проекта.

Допустимые абсолютные пути остаются абсолютными, но не предоставляют доступ автоматически. `~`, `${ENV_VAR}` и `{{variable}}` не разворачиваются по контракту v2. При `..`, символических ссылках и внешних хранилищах проверить фактическое назначение и разрешённую область; согласованное внешнее хранилище допустимо, незаметный выход — нет. Для Markdown-ссылок пересчитать адрес относительно документа. В другом worktree или контейнере разрешить пути заново по его корням, а не переносить абсолютные адреса из прежнего окружения; `ris.yaml` не служит кэшем абсолютных путей.

## 4. Входы, права и диагностика операции

Вызывающий скил сообщает цель операции, требуемые поля/каталоги, роль каждого каталога (существующий вход или будущий выход), параметры задания и разрешённую область. Если эти сведения нельзя установить, отметить пробел и блокировать зависимое действие; не объявлять все поля обязательными одновременно. Проверить наличие необходимых полей и доступность нужных **входных** каталогов. Если каталог предполагается создать как выход, его отсутствие само по себе не ошибка при разрешённой записи; проверить разрешение на создание и конфликт в момент самой записи у владельца результата. Если записи нет, подготовить только предложение и не утверждать, что выход создан. Существование каталога не доказывает наличия нужного документа или пригодности его содержимого.

`write: false` — исходный режим без разрешения на намеренное постоянное изменение кода, документов, конфигурации или задач. Естественно-языковое поручение может разрешить конкретные изменения; `write: true` не расширяет их область, не обходит ограничения среды или хранилища. Конфигурация не предоставляет разрешений. `ris-proj-op-resolve-context` **никогда не записывает** конфигурацию, каталоги, документы, задачи, worktrees или постоянный контекст, независимо от разрешений вызывающего скила. Побочные эффекты проверочных команд также требуют учёта.

Например, задание `ris-proj-op-plan-roadmap` может содержать `goal`, `mode: create|update` и `write: false`. Это данные задания, не YAML API OpenCode. Неизвестную цель контекст отмечает как пробел; предметный скил может предложить её, не выдавая за принятое решение. Режим и состояние результата определяет потребитель; явный `update` отсутствующего входа не становится `create`, существующий результат при `create` не перезаписывается автоматически. Пути `ris.yaml` не переопределяются временными параметрами задания.

При операции с адаптером проверить выбор `adapters.tasks.skill` и передать `options` контракту действительно доступного адаптера. `ris-proj-op-resolve-context` не вызывает его CLI, не проверяет установку без необходимости и не определяет семантику операций. Планирование эпиков в трекере принадлежит `ris-proj-op-plan-roadmap`, а не контексту.

## 5. Алгоритм и результат

1. Установить цель, выбранный `project_root`, а при потребности в `workspace.*` — `primary_root`; при неоднозначности блокировать зависимую часть.
2. Выбрать конфигурацию по правилу раздела 2. Отсутствие необязательного файла → defaults; выбранный файл → проверить YAML, версию, типы и ключи и дополнить только отсутствующие workspace leaves.
3. Установить параметры, права и требуемые текущей операцией поля; разрешить их от нужной базы, проверить доступность необходимых входов и назначение путей.
4. Вернуть только применимые настройки, их источник для каждого leaf, режим выполнения, диагностику и статус; для primary — проверенную Git association и ограничения. При частичной подготовке перечислить независимую готовую часть и заблокированные зависимости. Не подменять чтение и проверку документов потребителем.

Пример результата для подготовки чтения авторских материалов без `ris.yaml` (при существующем входном каталоге):

```yaml
status: ok
project_root: /work/example
config_source: package defaults
settings:
  sources:
    product: /work/example/docs/product/
run:
  operation: read-product
  write: false
provenance:
  settings.sources.product: package defaults
  run.write: no permission to write
diagnostics: []
changes: []
```

Это иллюстрация, не свидетельство существования каталога. При выборе файла вернуть `config_file` и provenance `ris.yaml`; при нужных общих путях также `primary_root` и применимые `workspace.*`. `status: ok` означает подготовку для указанной операции, не сохранение и не принятие результата. `blocked` — нехватка входа/разрешения, `conflict` — существенное противоречие, `error` — техническая ошибка/невалидная выбранная конфигурация. Диагностика называет конкретный пробел и затронутую операцию; полезные независимые настройки сохраняются с явной границей. Результат — данные текущей сессии, не постоянный файл и не доказательство передачи между сессиями.

При смене проекта, конфигурации, worktree, окружения или параметров контекст готовится заново. Получатель повторно проверяет пути и состояние перед записью; общему хранилищу задач нужен собственный механизм согласованности, который здесь не реализован.
