# 02. Конфигурация и параметры выполнения

[Оглавление](README.md)

## 1. Разделение сведений

Методика скила, постоянная настройка проекта, параметр задания, проектное правило и текущее состояние — разные категории. Путь к правилам является настройкой; сами правила не переносятся в набор параметров. Концепция остаётся документом продукта, а не частью конфигурации.

В ris применяется **необязательный проектный файл `ris.yaml` с контрактом версии 1**. При его отсутствии используются соглашения по умолчанию, поставляемые с RIS и описанные в `ris-context/references/configuration.md`. Отдельный глобальный пользовательский файл не требуется. Это соглашение пакета, а не встроенная настройка Agent Skills или OpenCode. Подготовка выполняется `ris-context`; автоматической подстановки значений в `SKILL.md` нет.

Поставка RIS внутри Gas City Pack или глобальная установка скиллов не меняет значения по умолчанию и не требует редактирования пакета. Проектный `ris.yaml` полностью заменяет пакетные значения: отсутствующие в нём ключи не дополняются defaults. Файл обязан содержать все поля, обязательные для выбранной операции, но не обязан объявлять поля, не относящиеся к этой операции.

Значения по умолчанию версии 1: `sources.concept: docs/product/concept.md`, `sources.rules_index: rules/index.md`, `artifacts.roadmap: .ris/ROADMAP.md`. Они применяются только при отсутствии проектного `ris.yaml`; отсутствующий по настроенному пути файл не вызывает поиск альтернатив.

## 2. Формат

Минимальный пример для roadmap:

```yaml
version: 1
sources:
  concept: docs/product/concept.md
  rules_index: rules/index.md
artifacts:
  roadmap: .ris/ROADMAP.md
```

Тот же прикладной скил в другом проекте использует иной набор путей без изменения собственных инструкций:

```yaml
version: 1
sources:
  concept: documentation/vision.md
  rules_index: documentation/development/index.md
artifacts:
  roadmap: planning/ROADMAP.md
```

Полный пример проектной конфигурации, если операция использует адаптер задач:

```yaml
version: 1
sources:
  concept: docs/product/concept.md
  rules_index: rules/index.md
artifacts:
  roadmap: .ris/ROADMAP.md
adapters:
  tasks:
    skill: ris-tasks-files
    options:
      directory: .ris/tasks
```

Наличие имени адаптера не подтверждает его установку. Поля его `options` определяются контрактом адаптера. Приведённый `directory` — пример для файлового варианта, а не универсальное свойство трекеров.

| Поле | Тип | Условия |
|---|---|---|
| `version` | Целое, не логическое значение | Обязательно; `1` |
| `sources.concept` | Непустая строка пути | Обязательно для планирования по концепции |
| `sources.rules_index` | Непустая строка пути | Обязательно для проектной SDLC-операции |
| `artifacts.roadmap` | Непустая строка пути | Обязательно для операций с настроенным roadmap |
| `adapters.tasks.skill` | Непустая строка имени | Обязательно при использовании адаптера задач |
| `adapters.tasks.options` | Отображение данных | Необязательно, если контракт адаптера не требует настроек |

Разделы `sources`, `artifacts`, `adapters`, `adapters.tasks`, если присутствуют, являются отображениями. Необязательные значения не заполняются `null` или пустой строкой вместо отсутствия. Отсутствующие поля проверяются в соответствии с выбранной операцией, а не для всех возможных скилов сразу.

В первой версии не вводятся `extends`, автоматическое слияние конфигураций, сетевые импорты или исполняемые выражения. Допускаются простые отображения, списки и скаляры; запрещены пользовательские YAML-теги, дубли ключей, merge-ключи и алиасы. Неизвестные поля вне расширяемого `options` являются ошибкой. Добавление новых полей требует обновить контракт и проверяющих его потребителей.

Для новых скилов адреса входных и выходных артефактов передаются в задании как входы операции, если они не являются постоянными настройками проекта. Настройки путей `ris.yaml` нельзя временно переопределять параметрами задания. Не нужно заранее расширять `ris.yaml` всеми возможными видами документов. Если путь становится постоянной настройкой, он добавляется в документированный контракт, а не угадывается по имени скила.

## 3. Выбор проекта и конфигурации

Сначала устанавливается целевой проект и его `project_root` по заданию, рабочему окружению и применимым инструкциям проекта. Корень не выводится из расположения RIS, каталога установленного скила, Gas City Pack или файла конфигурации.

Если для выбранного проекта найдено несколько неразличимых корней, проектные записи блокируются до уточнения; независимое обсуждение допустимо.

После фиксации `project_root` выбирается конфигурация именно этого проекта; поиск `ris.yaml` вверх к родительским или вниз к вложенным каталогам не выполняется. В monorepo задание или применимые инструкции должны однозначно определить корень конкретного проекта. Настройка другого проекта в том же репозитории автоматически не наследуется.

Путь проектного `ris.yaml` выбирается в таком порядке:

1. Явный путь из задания.
2. Единственный указатель в применимых к выбранному проекту инструкциях, например `AGENTS.md`.
3. `ris.yaml` непосредственно в уже установленном корне выбранного проекта.

Указатель из родительских инструкций применим только если эти инструкции распространяются на выбранный проект и указатель однозначно задаёт его конфигурацию. Если для одного проекта обнаружены несколько применимых указателей без однозначного приоритета, конфигурация неоднозначна и проектная операция блокируется.

Относительный путь к конфигурации из задания считается от известной рабочей директории запуска. Относительный указатель в `AGENTS.md` — от каталога этого файла. Нахождение и выбор конфигурации не меняют `project_root`; все пути в `ris.yaml` разрешаются относительно установленного корня проекта.

Нельзя после ошибки явно выбранного файла переключаться на соседний проект, другую конфигурацию или «похожий» файл. Несколько неразличимых кандидатов блокируют проектные записи, но не независимое обсуждение.

Если проектного `ris.yaml` нет, `ris-context` использует пакетные значения по умолчанию. Конфигурацию автоматически не создаёт. Допустимо общее предложение в ответе, однако его нельзя называть исполнением настроенной проектной операции, если обязательный вход недоступен. Создание конфигурации — отдельное разрешённое действие внедрения.

## 4. Базы путей

| Путь | База |
|---|---|
| Значения путей в проектном `ris.yaml` | `project_root` |
| Пакетные значения по умолчанию | `project_root` целевого проекта |
| Путь к конфигурации из задания | Рабочая директория запуска |
| Указатель на конфигурацию в `AGENTS.md` | Каталог этого `AGENTS.md` |
| Ресурс внутри скила | Каталог скила-владельца |
| Относительный путь входа/выхода другого этапа, явно переданный в задании | `project_root`, если контрактом задания не задана другая явная база |

Допустимый абсолютный путь остаётся абсолютным. `~`, `${ENV_VAR}` и `{{variable}}` не разворачиваются автоматически и в контракте версии 1 не являются поддерживаемыми конструкциями пути.

Для инструментов используются разрешённые пути с известной базой. Для Markdown-ссылок путь пересчитывается от каталога документа. Конфигурационный путь нельзя просто вставить в документ, предполагая одинаковую базу.

Настройка пути не предоставляет прав доступа. При `..`, символических ссылках и внешних хранилищах проверяются фактическое назначение и разрешённая область. Явно согласованное внешнее хранилище допустимо, незаметный выход за границы — нет.

## 5. Параметры текущего задания

Пример структурированного задания для прикладного скила roadmap (реализуется после автора скилов):

```yaml
skill: ris-plan-roadmap
parameters:
  goal: MVP для собственного использования
  mode: create
write: false
```

Это представление данных в контексте, не специальная команда, файл запуска или автоматически исполняемый YAML.

`goal` — цель конкретного планирования. При её отсутствии `ris-context` отмечает пробел; предметный скил может предложить цель по своей методике, но не выдаёт её за принятую.

`mode` имеет значения `create` и `update`. Если режим не задан, он устанавливается по заданию и фактическому наличию результата. При явном `update` отсутствующий входной roadmap нельзя молча заменить созданием нового. При явном `create` существующий файл нельзя перезаписать без выяснения разрешённого действия.

Задание не переопределяет значения `sources` или `artifacts`. Если проекту нужны иные постоянные пути, он задаёт полный набор настроек в `ris.yaml`.

## 6. Разрешение записи

`write: false` запрещает намеренные постоянные изменения кода, документов, конфигурации и состояния задач в рамках операции. Это исходный режим до получения разрешения на конкретные изменения.

Естественно-языковое поручение «сохрани roadmap» может быть достаточным основанием для `write: true`. Пользователь не обязан передавать YAML. Агент дополнительно устанавливает разрешённую область: изменение roadmap не разрешает менять задачи, код, правила или глоссарий.

`write: true` не отменяет ограничения среды, подтверждения опасных действий и права хранилища. Доступная функция записи также не является разрешением на её использование.

Тесты, сборки и другие команды могут создавать файлы или изменять окружение. Их побочные эффекты учитываются отдельно: режим анализа не разрешает их автоматически. Временная изолированная проверка допускается только в пределах правил среды и явно разрешённой области; она не служит обходом запрета на изменение проекта.

Конфигурация не может сама разрешить текущую запись. `ris-context` не изменяет исходные файлы ни при каком значении `write`.

## 7. Значения по умолчанию и проектные настройки

```text
Проектный ris.yaml (единственный источник настроек, если файл существует)
                           ИЛИ
            Пакетные значения по умолчанию
```

Наличие проектного `ris.yaml` целиком заменяет пакетные значения, а не дополняет их. Полнота файла определяется выбранной операцией: все её обязательные поля должны присутствовать, но нерелевантные поля не требуются. Отсутствующее обязательное поле является ошибкой; значение не берётся автоматически из пакета. Это исключает неочевидное слияние при сохранении компактной конфигурации.

Приоритет значений не задаёт приоритет инструкций и не делает источник требований утверждённым. Указанный путь к черновику не придаёт ему статус принятой спецификации.

Если проектный `ris.yaml` существует, у отсутствующих или ошибочных значений нет неявной подстановки пакетного default. Настройки не переопределяются и не записываются обратно в `ris.yaml` в рамках обычной операции.

Выбранный адаптер и индекс обязательных правил не переключаются неявно. Изменение постоянной конфигурации является отдельной операцией.

## 8. Алгоритм ris-context

1. Установить целевой проект и `project_root`; определить наличие и путь проектного `ris.yaml`.
2. Прочитать данные, проверить структуру, версию и неизвестные поля.
3. Определить параметры задания, требуемые входы и разрешённую область.
4. Если проектный `ris.yaml` отсутствует, применить пакетные значения по умолчанию; если присутствует — использовать только его значения.
5. Разрешить известные пути и передать настройки адаптера его контракту при необходимости.
6. Проверить нужные поля, доступность обязательных входов и состояние цели записи.
7. Вернуть подготовленный контекст, происхождение значений и диагностику.

Подготовка не равна чтению и анализу всех источников. `ris-context` устанавливает, где лежит концепция, а прикладной скил её читает и оценивает. Условный адаптер не загружается лишь потому, что указан в конфигурации.

## 9. Подготовленный контекст

```yaml
status: ok
config_file: /work/example/ris.yaml
project_root: /work/example
settings:
  sources:
    concept: /work/example/docs/product/concept.md
    rules_index: /work/example/rules/index.md
  artifacts:
    roadmap: /work/example/.ris/ROADMAP.md
run:
  skill: ris-plan-roadmap
  parameters:
    goal: MVP для собственного использования
    mode: create
  write: false
provenance:
  settings.sources.concept: ris.yaml
  settings.artifacts.roadmap: ris.yaml
  run.parameters.goal: текущее задание
  run.write: явный запрет записи
diagnostics: []
```

Этот пример не означает, что такой проект или файлы существуют. При выполнении поля содержат фактические значения. Контекст может быть блоком текущей сессии или объектом существующего оркестратора; постоянный файл контекста не требуется.

Имена `settings`, `run`, `provenance` и состояния результата — соглашение ris. Произвольные параметры не передаются автоматически при упоминании другого скила.

Если проектный `ris.yaml` отсутствует, поле `config_file` опускается, а источник каждого применённого значения в `provenance` обозначается как пакетное соглашение по умолчанию. Отсутствующий файл не представляется как ошибка конфигурации.

## 10. Worktree, monorepo и актуальность

В monorepo выбирается одна конфигурация конкретного проекта. Вложенные конфигурации автоматически не наследуются. Для другой рабочей копии или worktree пути разрешаются заново в окружении получателя.

Общее хранилище задач между worktree настраивается явно и обслуживается предусмотренным механизмом согласованности. Абсолютные пути основной рабочей копии нельзя считать пригодными для субагента в другом контейнере.

Контекст пересобирается при смене проекта, конфигурации, рабочей копии или параметров. Перед записью перепроверяется изменяемое состояние, если оно могло измениться. Снимок контекста не заменяет актуальную проверку конфликта.
