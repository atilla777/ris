# 04. Контракты скилов, адаптеры и инструменты

[Оглавление](index.md)

## 1. Контракт каждого скила

| Часть | Содержание |
|---|---|
| Назначение | Основной результат и его владелец |
| Применение | Когда использовать и где нужен другой скил |
| Входы | Источники, параметры, статус принятия и допустимые пробелы |
| Зависимости | Роль, условие загрузки и форма применения |
| Роль исполнения (если нужна вызывающему) | Смысловая роль работы без модели, имени субагента и обязательного режима запуска при прямом вызове |
| Предусловия | Что нужно до действия; не только существование файлов |
| Методика | Содержательная процедура или её явная композиция |
| Результат | Артефакт или ответ, содержание, адрес и критерии |
| Изменения | Разрешённые побочные эффекты и границы записи |
| Проверка | Наблюдаемые подтверждения именно заявленного результата |
| Ошибки | Отсутствие входов, конфликты, частичное выполнение и восстановление |
| Завершение | Граница ответственности и данные передачи |

Для критичных рисков дополнительно описываются типичные обходы требований и признаки нарушения с реакциями. Необязателен отдельный заголовок для каждой части; обязательна ясность контракта. Пустые разделы не заменяют спецификацию.

Контракт записывается в теле `SKILL.md` и связанных ресурсах. ris не вводит исполняемые `imports`, `depends_on` или автоматические параметры в YAML-заголовке. Дополнительные сведения могут быть соглашением инструментов лишь после реализации их обработки.

В спецификации нового скила зафиксируй, имеет ли предметная методика самостоятельный переносимый контракт или остаётся в одном RIS-скиле. Если выделена пара, базовый скил определяет свою методику, входы и проверяемый самостоятельный результат без RIS-зависимостей; проектный RIS-скил определяет условия применения базового, проектные входы, работу с `ris-context` при необходимости, совокупный результат и остановку. Области ответственности и условия выбора должны быть различимы в обоих `description`; детали методики не дублируются. Критерии решения — в [01](01-architecture.md), правила применения — в [03](03-composition.md).

При проектировании или пересмотре контракта проверь каждый значимый шаг: нужен ли он для заявленного результата, не принадлежит ли существующему владельцу и будет ли его инструкция востребована при обычном запросе. Если шаг требует отдельного результата, решения или разрешений, специфицируй его как отдельную операцию/скил либо вынеси координацию в составной скил. Если шаг нужен только условно, определи точное условие подключения и место хранения деталей. Не дублируй в обёртке базовую методику; сохранение проверяемого общего результата не требует копии её алгоритма. Не дроби на скилы шаги без самостоятельной ответственности.

Прикладная обёртка не объявляет следующего скила как часть собственного выхода и не запускает следующий этап. Её вызов других скилов для **своего** результата остаётся допустимой необходимой зависимостью. Сквозной скил владеет маршрутами и допусками, но не копирует содержание методик и адаптеров. Роль объявляется в контракте операции, когда она нужна реальному вызывающему; не вводить обязательную роль каждому действующему скилу ради единообразия. Инструкция может описать следующий возможный шаг содержательно, без привязки к публичному имени следующего скила.

## 2. Метаданные и description

Устанавливаемый скил имеет обязательные `name` и `description`; имя соответствует каталогу. Остальные поля добавляются только при реальной потребности и поддержке выбранной среды. Базовый формат основан на Agent Skills. [S1](sources.md).

`description` объясняет результат, условия применения и отличие от соседних скилов. Оно не пересказывает процесс, не подменяет `SKILL.md` и не содержит обещаний, которые не покрывает контракт. Само указание «для агентов разработки» не позволяет выбрать скил.

Пример для каталога ris:

```yaml
---
name: ris-plan-roadmap
description: >-
  Формирует или актуализирует roadmap проекта по концепции и целям:
  крупные результаты, границы MVP и зависимости эпиков.
  Используй для планирования проекта, а не для декомпозиции одной фичи.
---
```

Ограничения формата проверяются валидатором выбранной версии стандарта. Практическую различимость описаний проверяют сценарии из [05](05-adoption-and-validation.md), а не только корректность YAML.

## 3. Передача ограниченной операции

Операция получает:

```text
Имя нужной операции
+ актуальный контекст проекта
+ конкретные входные данные
+ разрешённые изменения
+ ожидаемый результат
```

В одной сессии это может быть явный блок контекста; в существующем оркестраторе — его объект задания. Текст «вызови адаптер» не создаёт программную функцию с возвращаемым значением.

Исполнитель обязан получить фактический результат, проверить его и только затем использовать. Нельзя продолжить работу с предполагаемым идентификатором задачи или непроверенной записью.

## 4. Адаптеры

Разные реализации одной роли должны соблюдать одинаковую семантику. Иначе смена имени адаптера в конфигурации не обеспечивает заменяемость.

### Контракт роли `tasks`, версия 1 (roadmap и задачи фичи)

Это **нормативный владелец** общей семантики; условные имена ниже не являются командами RIS CLI или машинным API. Версия 1 первоначально охватывала только roadmap; теперь она совместимо дополнена **необязательным набором операций задач фичи** ниже. Существующие операции эпиков и их связей не меняют смысла. Адаптер заявляет версию, поддерживаемые операции и гарантии **по каждой** операции; частичная поддержка допустима. Потребитель проверяет выбранный установленный адаптер, совместимую версию и все нужные операции и гарантии до зависимого действия. Дополнение необязательной операции совместимо с версией 1; изменение семантики существующей требует новой версии и проверки потребителей. Одно лишь заявление «v1», без нужных операций и гарантий, недостаточно. Отсутствующее требование не заменяется похожим вызовом трекера или другим адаптером.

Общие входы каждой операции: явно выбранный проект/workspace, разрешённая область чтения или записи, подтверждённая цель и идентичность записей; для записи — точное изменение и ожидаемое состояние. Чтение не даёт права записи. **Для операций roadmap ниже** тип записи — `epic`, состояния передаются как фактическое состояние трекера и признак открытости/закрытости, без навязанной таблицы статусов другого трекера. Содержание эпика включает идентичность цели и самого эпика, результат, границу/исключения, критерий завершения и покрытые сценарии либо подтверждённую ссылку на эти сведения. Идентичность проверяется по ID и устойчивому признаку принадлежности цели; одно название или предполагаемая уникальность внешней ссылки недостаточны.

| Операция | Вход и необходимая семантика | Результат и гарантии |
|---|---|---|
| `tasks.epics.list` | Область проекта, тип `epic`, все состояния, включая закрытые; фильтр цели применяется только при сохранении полноты | Полная выборка применимых записей с ID, типом, состоянием и содержанием либо явная неполнота и способ продолжения пагинации; усечённая выборка не подтверждает отсутствие |
| `tasks.epics.read` | Подтверждённый ID | Ровно одна запись с совпавшим ID, типом, состоянием, содержанием и доступными связями либо отсутствие/неоднозначность |
| `tasks.epics.create` | Разрешённые описание и устойчивый признак принадлежности цели, ожидание отсутствия | Фактический ID и прочитанные после записи поля; best-effort без гарантии отсутствия дубликата при конкуренции допустим, строгая уникальность требует отдельно обеспеченной исключительной записи |
| `tasks.epics.update` | Подтверждённый ID, ожидаемое состояние, явно названные поля | Сохранённые поля и неизменность остальных по повторному чтению; защита от потери конкурентного обновления содержания обязательна, кроме отдельно согласованного допуска к конкретному риску |
| `tasks.blocks.list` | ID эпика и область требуемых связей | Типизированные направленные связи: блокируемый эпик → блокирующий эпик; пустая полная выборка отличается от ошибки |
| `tasks.blocks.add` | Подтверждённые ID блокируемого и блокирующего эпиков, тип `blocks`, ожидаемое отсутствие | Проверенная связь в нужном направлении без цикла; если состояние изменилось, сначала сверить факты |
| `tasks.blocks.remove` | Те же ID и тип, ожидаемая существующая **точная** связь, разрешение удалить её | Подтверждённое отсутствие именно этой связи после записи; необходима исключительная запись или другая доказанная защита от удаления конкурентной замены, иначе `conflict` до записи |

Для `create`, `update`, `add` и `remove` адаптер повторно читает затронутые записи и связи; возвращает фактические ID, состояние, содержание и связи в применимом объёме, свидетельства чтения и совершённые изменения. Нулевой код команды сам по себе не подтверждает результат. При неоднозначном ответе сначала сверяет фактическое состояние, не повторяет вслепую создание или удаление. Если запись частична, сообщает подтверждённую часть и прекращает следующие изменения; причины `blocked|conflict|error` и форма отчёта — в разделе 6. Чтение до/после не заменяет атомарную гарантию: для `update` и `remove` без нужной защиты запись блокируется, если только применимый явно разрешённый ограниченный риск не предусмотрен выше. Отсутствие права, операции, совместимой версии или обязательной гарантии — `blocked` либо `conflict` без зависимой записи. Захват и завершение остаются инструментальными операциями, не входят в общий контракт v1.

### Дополнительные операции `tasks` v1: задачи фичи

Это **необязательные возможности v1**, необходимые потребителю [первого сценария фичи](../specs/ris-feature-work-first-slice.md); старый roadmap-потребитель их не требует. Запись задачи фичи и её прямых детей имеет тип `task`; родитель фичи — подтверждённый `epic`. Маленькая фича может исполняться собственной задачей типа `task` без детей. Состояние задачи возвращается как фактическое состояние трекера и открытость/закрытость, не преобразуется в статус результата RIS. Идентичность фичи означает подтверждённые ID, родительский эпик, устойчивый ключ принадлежности/повтора и точную ссылку на **принятую** спецификацию с адресом проверяемого источника подтверждения; адаптер не принимает спецификацию за пользователя. Адрес источника сохраняется в доступном при повторном чтении содержании задачи либо в самой спецификации по её точному адресу; при продолжении проверяется доступность источника и соответствие решения этой версии спецификации, иначе статус принятия не доказан. Детям нужны собственные устойчивые ключи в области родителя, содержательная цель и проверяемый критерий. Одно название, одно существование файла или совпадение только ссылки на спецификацию не устанавливает идентичность. Ключи не обязаны быть глобально уникальны в хранилище, но поиск повтора охватывает все необходимые состояния и соответствующую область.

| Операция | Вход и необходимая семантика | Результат и гарантии |
|---|---|---|
| `tasks.items.list` | Проект, тип `task`, все состояния, в том числе закрытые; область/ключ идентичности с проверкой полноты | Полная выборка задач с ID, типом, состоянием, родителем, содержанием и доступными ссылками либо явная неполнота и способ продолжения; усечённая выборка не подтверждает отсутствие |
| `tasks.items.read` | Подтверждённый ID задачи | Ровно одна задача с совпавшим ID, типом, состоянием, родителем, содержанием, ссылками и доступными связями либо отсутствие/неоднозначность; эпик с тем же ID по смыслу не подходит |
| `tasks.items.create` | Разрешённая область записи, подтверждённый ID открытого эпика для фичи или открытой задачи фичи для ребёнка, утверждённые содержание и устойчивый ключ, для фичи — точная ссылка на спецификацию и проверяемый адрес источника её принятия; ожидание отсутствия соответствующей записи | Либо проверенно переиспользованный ID и неизменённая запись при **полном** совпадении идентичности, родителя, ссылок и существенного содержания, либо созданный ID с повторно прочитанными полями и связью состава; при расхождении `conflict`, а не скрытый update. Best-effort без обещания строгой уникальности при конкуренции; строгая уникальность требует исключительной записи |
| `tasks.children.list` | Подтверждённый ID задачи фичи, только **прямые** дети всех состояний | Полный состав прямых детей с ID, типом, состоянием, родителем и содержанием либо явная неполнота; пустой полный состав отличается от ошибки. Потребитель решает, достаточен ли состав |
| `tasks.dependencies.list` | Подтверждённые ID задач и нужное направление | Полные типизированные направленные связи `blocks`: блокируемая задача → блокирующая задача; не смешивать со связью состава `parent-child` |
| `tasks.dependencies.add` | Подтверждённые ID задач в разрешённой области, ожидаемое отсутствие точной связи `blocks` | Подтверждённая связь в правильном направлении без цикла; повтор уже существующей точной связи возвращает фактическое состояние без фиктивного изменения |

Перед зависимой записью потребитель проверяет версию, **каждую** нужную операцию и гарантию: полные выборки для проверки отсутствия и детей, идентичность с родителем и ссылкой, проверку направления и цикла, прочтение после записи и требуемый уровень конкурентной защиты. Область записи и ожидаемое состояние задаются явно; адаптер проверяет тип и принадлежность обоих концов. Создание по умолчанию best-effort с поиском и сверкой всех состояний до и после записи; параллельное создание может породить дубли, и при их обнаружении результат `conflict` с фактическими ID. При явном требовании отсутствия дублей нужна независимо обеспеченная исключительная запись на весь поиск/создание/проверку. Добавление связи проверяет концы и отсутствие цикла, перечитывает результат; при несовпадении останавливается. Изменение содержания, перенос детей и удаление связей **не** включены в эти новые общие операции; инструментальные способы их выполнить не считаются взаимозаменяемым контрактом. При неоднозначной команде сначала перечитать факты; после частичного успеха вернуть подтверждённые ID и изменения и остановить следующую запись. Отсутствие операции, права, полноты, совместимой версии либо необходимой гарантии останавливает зависимую запись без обхода через конкретный трекер.

### Дополнение `tasks.feature-record` версии 1 (явно объявляемая capability)

Это **не** операции `tasks` v1 по умолчанию и не новая обязательная версия для roadmap. Адаптер отдельно объявляет `tasks.feature-record/1` и поддерживаемые операции и гарантии; потребитель проверяет их до записи. `tasks.items.create` по-прежнему создаёт задачу типа `task` под эпиком. Дополнение применяется только к подтверждённой feature task с постоянным slug и адресом принятой спецификации. Оно не меняет статус задачи автоматически и не управляет жизненным циклом эпика. Старые записи без однозначной связи требуют согласованной миграции, а не выведения slug из заголовка.

В самой записи фичи (а не во втором реестре) хранится читаемый структурированный блок `ris.feature-record/1` с `slug`, `spec_path`, версиями/областями **двух** независимых результатов (`requirements` и `design`: точный путь, однозначный диапазон или отдельный файл, проверяемый digest, адрес и область решения о принятии), а также необязательной `verification` (полная Git SHA общей интегрированной ревизии, AC → результат/свидетельства, интеграционные, архитектурные и документальные проверки, ограничения, адреса доказательств). До принятия дизайна его запись отсутствует, а не подменяется записью требований. Slug уникален в подтверждённой области проекта и не меняется при переименовании title. Пути разрешаются от корня проекта; digest и адрес решения проверяются на фактическом содержимом, а не выводятся из наличия файла. Для двух областей в одном `spec.md` диапазоны и digests не должны включать правки другой области; если выделить их надёжно нельзя, используется отдельный `design.md` либо новое принятие затронутого содержания. При изменении версии свидетельство прежнего принятия сохраняется как история в трекере или доступном опубликованном адресе, но не выдаётся за принятие новой версии.

| Операция | Вход и эффект | Необходимое подтверждение |
|---|---|---|
| `tasks.features.read` | Точный ID; извлечь связь ID ↔ slug ↔ spec/design, отдельные решения и, если есть, приёмку | Ровно одна `task`, тип/родитель, структурированный блок без дублей, проверяемые адреса и версии; неподтверждённое содержимое отмечено явно |
| `tasks.features.update` | ID, ожидаемые старые значения/версия блока, точные изменения ссылок или решений и разрешение; неизменённые области не перепринимать | Сохранены slug, нецелевые поля и история; повторно прочитаны ID, версии, содержимое и адреса; конфликт до записи при расхождении |
| `tasks.features.record-verification` | ID, принятая версия требований и дизайна, интегрированная Git SHA, AC и результаты/адреса проверок; только явное разрешение на запись | Полная читаемая запись приёмки после повторного чтения; неудачные AC не превращаются в успех и не закрывают фичу |
| `tasks.features.complete` | ID, явно подтверждённый обязательный состав, блокеры, сохранённая успешная приёмка на итоговой общей ревизии и разрешение закрыть **именно** фичу | До записи проверены актуальные версия, AC, результат, Git SHA, обязательные дети и блокеры; после — та же запись, статус закрытия и состав; родитель-эпик не закрыт |

Для трёх операций записи нужен подтверждённый исключительный период для **всех** писателей соответствующей записи, связей состава и блокеров от чтения исходного состояния до проверки записи; либо реальная атомарная условная запись содержимого и структуры с эквивалентной защитой. Чтение до/после, `claim`, локальная аренда и проверка только статуса **не** являются такой защитой. При отсутствии гарантии возвращается `conflict` до записи; нельзя молча соглашаться на риск потери acceptance evidence. При изменении ожиданий или неоднозначном ответе перечитать состояние и остановиться, не повторять вслепую. Для `complete` закрытые дети сверяются с подтверждённым обязательным составом: пустой список детей не доказывает, что все необходимые работы существуют. Нужны принятые версии, опубликованная общая Git SHA и успешное свидетельство всех AC; локальные тесты и закрытые дети сами по себе недостаточны. Приемка фичи и эпика имеют разных владельцев: закрытие эпика — отдельная операция с отдельным разрешением.

Запись в Git и публикация записи Dolt — независимые эффекты. Удалённый успех требует проверки соответствующего Git commit и отдельного чтения точного ID, версии, содержания, статуса и связей из другой копии выбранного Dolt remote. Если подтверждён только один канал, результат частичный (`blocked|conflict|error` с перечислением сохранённого), а не `ok` полного сценария. Добавление capability не меняет гарантий `tasks` v1 или настройки удалённого репозитория.

При создании `tasks.items.create` может сохранить явно переданный начальный блок вместе с принятыми требованиями и проверить его чтением; для старой записи без блока требуется отдельно разрешённое начальное обновление с проверкой прежней связи и сохранением текста, а не угадывание slug. Область внутри общего файла указывается единственным точным Markdown-заголовком; хешируются исходные байты UTF-8 от строки заголовка включительно до следующего заголовка того же или старшего уровня (либо конца файла), без нормализации. При неоднозначном заголовке или пересечении областей применяется отдельный файл или повторное принятие. Для закрытия обязательны успешные результаты каждого AC, интеграционных, архитектурных и документальных проверок с доступными свидетельствами; нерешённое ограничение, влияющее на них, исключает успех.

## 5. Владение интерфейсом

Общая семантика `tasks` версии 1 находится в разделе 4 этого документа, без второй нормативной копии в `ris-common`. Прикладной скил знает требуемую операцию и её контракт, адаптер — отображение на реальный инструмент. Установленные скилы содержат достаточные рабочие требования без обращения к этому репозиторию.

В адаптере остаются ссылка на контракт, поддерживаемая версия, настройки и особенности реализации. Не нужно повторять весь интерфейс или создавать скил лишь ради хранения короткой таблицы. Несовместимое изменение требует обновить потребителей и проверки.

## 6. Результат выполнения

Для операций ris используется небольшой набор состояний:

| Состояние | Значение |
|---|---|
| `ok` | Заявленный контракт выполнен и проверен |
| `blocked` | Не хватает обязательного входа, зависимости, разрешения, решения или проверки |
| `conflict` | Конкурентное изменение либо существенное противоречие состояния |
| `error` | Выполнение завершилось технической ошибкой |

Это не статусы задач трекера. Для частичного выполнения выбирается состояние причины незавершённости и перечисляется сделанная часть; полный `ok` не возвращается.

Результат содержит полезные данные, фактические изменения, достаточные подтверждения, ограничения и данные следующего действия. Если операция не меняет состояние, отсутствие изменений указывается явно.

```yaml
status: blocked
operation: tasks.epics.update
value:
  id: E-003
changes: []
evidence:
  - Текущая запись прочитана перед изменением
limitations:
  - У используемого доступа нет права записи
next_action: Получить разрешённый доступ либо передать изменение владельцу
```

Это иллюстрация формы. В реальном отчёте подтверждение ссылается на действительный результат чтения или команды, а не копирует шаблон. Эквивалентные Markdown-разделы допустимы; JSON/YAML обязателен только при программном потребителе.

`ok` для подготовки предложения не означает сохранение или принятие. `ok` для записи не означает содержательное одобрение документа. Границы этих состояний раскрываются в [06](06-artifacts-and-handoff.md).

## 7. CLI и скрипты

Адаптер использует действительно доступный инструмент и проверенный контракт. Команды не сочиняются по условным именам операций. Проверяются необходимые разрешения, совместимость и параметры; не требуется механически повторять `--help` перед каждым вызовом.

Аргументы и данные отделяются от исполняемого кода. Пути, заголовки и тексты не вставляются в небезопасную shell-строку. Конфигурация не исполняется через `eval`; секреты не включаются в отчёт.

После вызова проверяются статус завершения, ответ и достаточные свидетельства изменения. При неоднозначном результате сначала устанавливается фактическое состояние, а не повторяется потенциально дублирующее создание.

Ресурсы инструментов разрешаются от каталога адаптера. Язык скрипта и конкретные детали запуска относятся к реализации; универсальное требование использовать Bash, Go или Python не вводится. При наличии программного потребителя машинные данные и диагностика должны быть различимы, а временные ресурсы — безопасно очищаться.

## 8. Конкурентная запись

До изменения устанавливаются актуальная цель и разрешённая область. Для общего хранилища используется его протокол: транзакция, ожидаемая версия, блокировка или другой согласованный механизм.

Атомарная замена файла защищает от частичной записи, но не сама по себе от потери параллельного изменения. Гарантия отсутствия потерянных обновлений требует дополнительного протокола; инструкция агенту не является таким протоколом.

Блокировка не удерживается во время диалога или длительного анализа. При конфликте выполняются перечитывание и согласование либо возвращается `conflict`. Молчаливая перезапись чужой работы запрещена.

Перед повтором создания исключается уже состоявшаяся операция. Ключ идемпотентности применяется, если его поддерживает инструмент; отсутствие этой возможности не скрывается.

Для адаптера Beads разрешённое создание задач и эпиков без специального требования строгой уникальности работает как best-effort без отдельного согласования конкурентного риска на каждый вызов. Проверка существующей записи и результата остаётся обязательной, но не выдаётся за гарантию отсутствия дублей при параллельном создании: `bd` не обеспечивает уникальность внешней ссылки. Если вызывающий требует такую гарантию, нужен отдельно обеспеченный исключительный период записи; без него создание останавливается. Это правило не отменяет требования предотвращать потерянные правки при обновлении существующих записей.

Прямая запись обычного Markdown допустима при соблюдении правил проекта и конкурентного изменения. Если обязательный CLI обеспечивает согласованность, отсутствие доступа к нему не разрешает обход через файлы. Отдельный универсальный адаптер документов не требуется ради симметрии.

## 9. Готовность входов и выходов

Наличие файла, доступность его чтения и содержательная готовность — отдельные вопросы. Скил проверяет принадлежность выбранной работе, актуальность, статус принятия и достаточность нужных разделов.

Служебная операция может проверить формат, но не должна сама объявлять спецификацию достаточной для реализации. Общий стандарт готовности проекта дополняет критерии конкретного задания и контракт скила; правила подтверждения приведены в [07](07-quality-and-verification.md).

## 10. Завершение

Прикладной скил останавливается после своего проверенного результата либо явного неполного завершения. Он может подготовить передачу, но не запускает следующий этап без основания.

Служебная операция завершает только порученное действие; методика действует в переданной области; общий документ не начинает новый процесс. Эти границы позволяют сочетать компоненты без скрытой рекурсивной оркестрации.
