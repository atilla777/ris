# Execute one ready task

Own selection, transitions, one human dialogue and the sufficiency of the combined
result. This is one project scenario, without a new portable base: component
skills already own the portable stage methods. The tracker owns identity, status,
assignment, membership and blockers; Git owns content versions. Local reports
are evidence, never a second queue. Do not run multiple tasks, prepare unaccepted
requirements/design, integrate Beads formulas, create a workflow engine, migrate
historical records, repair/remove worktrees, deploy, release or substitute a PR.

## Prepare scope and executors before effects

Establish the selected project/current copy, context-checked primary selection
and provenance for shared paths in a worktree (explicit or verified available
saved indication), optional exact task ID, actor, accepted scope, applicable
rules and permissions. Load/apply installed `ris-proj-lib-common` and its conditional
resources before their actions; apply `ris-proj-op-resolve-context` with its owned configuration
resource to prepare sources, workspace, selected tasks adapter and these roles:

| Configured role | Standalone operations |
|---|---|
| `task-execution` | Queue/readiness investigation, copy/claim preparation, plan, Git publication, completion, tracker publication and fresh next recommendation |
| `task-implementation` | Code/text implementation and repairs |
| `task-review` | Independent review and integrated-snapshot reassessment |

For fresh work check all three role mappings and host availability/permissions
before the first mutation. For recovery first reconcile read-only, then gate only
roles and permissions needed by the remaining route; completed implementation or
review does not require launching its role again. Reassess the gate if the remainder
changes. One agent name may serve all roles, but review uses a **fresh invocation**
independent of every implementation/repair author. Missing/unavailable roles block
the dependent route; no fallback, model switch or execution in the leading context.
Do not require feature-preparation/decomposition roles for this task route.

The request for a full run authorizes the agreed single-task cycle, working
artifacts, publication and completion subject to higher-priority/project limits.
Check actual permissions for file edits, claim, Git commit/direct push, exact-ID
completion and **all outgoing tracker history**. Do not infer acceptance from
workflow permission. Let the selected adapter establish operation-specific
guarantees: use fresh reads, targeted native atomic/conditional operations and
read-back, and snapshot-bound tracker publication. Ordinary work needs no manual
window, mandatory global lock or graph/external-evidence transaction.
A claim, lease, sandbox or worktree is not general content/graph CAS. Delegate
read-only preflight to the selected adapter and Git publication owner for actual
capabilities, destination/ref, outgoing scope, restrictions and remote read-back.
Missing guarantees block only dependent effects; preserve usable results.

For **each standalone noninteractive operation**, actually launch the configured
subagent with its bounded owner skill/operation. Do not split internal reads into
agents or load all child methods merely to route them. Pass project/config/rule
provenance, current/primary roots, actor, exact IDs, accepted input versions and
decisions, allowed files/effects, output/evidence addresses and expected result.
The recipient loads/applies its owner and dependencies and returns choices here
instead of interviewing the user or accepting unseen content.

Bound each handoff by a checkable intermediate result and early-return conditions:
an accepted-contract/platform conflict, unavailable essential evidence, or a check
that needs materially more setup or external access than planned. Ordinary
instruction edits use reading, applicable static checks and independent review;
absence of a new live run is not an evidence blocker or a reason to ask again about
one. Apply the target project's prohibitions and permissions. Static source
readiness does not establish observed agent behavior; preserve historical evidence
versions, limits and unmet obligations without importing their gates into an
ordinary text edit. An explicitly accepted behavioral objective needs separately
agreed scope under project rules.
The recipient returns preserved effects, affected criteria and the necessary
decision promptly; it does not bury the issue in a long implementation/evaluation
loop. Continue only independently useful authorized work. Give concise accepted
input/version references and relevant prior evidence, not the entire accumulated
history; recipients still read their applicable rules and owner resources.

Require:

```text
status; operation; exact ID and scope; input versions;
result/evidence addresses; copy and snapshot; executor provenance;
actual effects; limitations; necessary decision; remaining operations
```

Verify actual launch, accessible artifacts and applicable evidence before every
transition; unsupported “done” is insufficient. Preserve history in the authorized
`workspace.tasks/<confirmed-ID>/execution.md` (explicit/project address wins).
Read `references/evidence.md` from this installed folder before the first handoff
or report write. If own unfinished work, previous/partial effects, an interrupted
operation or closed pending-publication work is found, read and apply
`references/recovery.md` before choosing a transition or retry. An ordinary fresh
run does not load that resource.

## Select exactly one target

Delegate a complete all-state task read and relevant epic/typed-edge reads to the
selected adapter. It must advertise actual complete item/child/dependency reads,
feature-record reads where needed, tool-specific claim/complete and separately
verified tracker publication; `tasks` v1 alone does not promise all of these.
Automatic selection remains task-only; never search/select bugs as queue candidates.
An explicit native bug uses the adapter's advertised ordinary typed bug reads,
claim, snapshot/result persistence and separate fix-completion, not task-only
feature APIs. For Beads apply its conditional `references/bug-execution.md` before
these operations. Missing ordinary support blocks that branch without conversion.

With an explicit ID, reread only that **target** for execution (queue reads may
support diagnosis/recommendation). Never replace it. A closed ID gets a verified
state/result report, never reopening or a new implementation; proven own pending
publication resumes only its remaining verification/publication. A foreign active
claim blocks it. Unknown IDs/types return a concrete diagnostic.

Without an ID, first identify confirmed own unfinished executions: actor supplied
explicitly or recovered from verified execution evidence, matching tracker
assignment, task/execution/copy linkage and no contradictory live execution.
OS user, issue `owner`, branch name or assignee alone does not prove ownership.
Uncertain ownership needs one necessary user decision, not silent bypass.
A closed task with proven pending tracker publication can be own unfinished work.

Sort confirmed own work first; otherwise sort ready candidates by tracker
priority, creation timestamp, then stable lexicographic ID. Beads lower numeric
priority wins; another adapter must supply unambiguous semantics. Compare parsed
timestamps, not locale strings; incomplete ordering data needs clarification.
If selected own work is blocked, stop on it instead of selecting a new task.
Route prior effects through the conditional recovery resource; **do not restart
from preparation** or skip blocked own work to choose another task.

## Verify readiness

For the chosen ID, check agreed outcome/scope/criteria, accepted applicable design
or sufficient accepted technical constraints for a standalone task, essential
inputs and current contracts, status, ownership, typed directed blockers and
complete mandatory composition. A missing plan is allowed at admission; decide
its necessity under step 2 before implementation.
For feature-linked work obtain current published requirements/design and separate
acceptance references through the adapter; inspect the referenced versions and
their applicability to current inputs. Do not repin refs or migrate unsupported
historical payloads. Membership is not a `blocks` edge; evaluate parent restrictions
under project rules without inventing an edge.

Discover these inputs from exact selected-adapter ID reads and linked versions,
not a mandatory caller questionnaire. Explicit ordinary standalone leaf/child
uses its own sufficient contract and accepted sources/constraints; structural
parent need not be an epic or feature. A child is not feature-linked merely
because it has a parent. Confirm actual kind before feature-record validation;
malformed/historical payloads are preserved, never converted to standalone.

For an exact native bug discover its full current report (description or exact
published file), aligned criteria, accepted constraints/decisions and full historical
execution-input snapshot in notes. Require expected behavior with authority,
confirmed divergence/applicable code/environment evidence, authorized bounded scope,
meaningful fix/regression checks and sufficient technical constraints. Readiness
alone is neither acceptance nor authority. The sufficient report replaces formal
spec/design; a material technical choice still needs separately accepted design.
Missing inputs/decisions return a precise gap, not silent investigation or feature
preparation. Before starting fresh bug execution require the full adapter-verified
snapshot text and project/tracker + exact ID + marker locator; if absent return
that preparation gap to the caller rather than executing on an unsaved basis.
At transitions/resume compare current report/criteria/decisions with this basis;
material drift requires targeted assessment by affected plan/change/review/evidence
owners before dependent effects. Preserve compatible evidence with reasons and
existing published/closed effects. Do not treat parent membership as feature identity.

A container with unfinished mandatory children is not executable as one task:
report its boundary and recommend a ready child without claiming/starting it.
Do not execute a multi-task container even when its children are closed; container
completion is a separate request. An independently confirmed one-task feature
with no decomposed mandatory children may use the full-feature route below.
No ready candidate means explain specific gaps and recommend a preparation step,
without starting requirements/design acceptance. Announce chosen ID and basis;
continue without formal reconfirmation of already accepted inputs.

## Execution sequence: fresh work or reconciled remainder

Fresh work starts at step 1. Recovery returns the first missing or inapplicable
operation, its proven prerequisites and exact remainder to this same sequence.
Enter the identified operation within a step, not the whole step blindly. The
leading scenario authorizes each transition after inspecting the owner's receipt;
owners retain their full methods. Reconcile again after partial/uncertain effects
or changed facts before deciding the next operation.

1. Delegate `ris-proj-op-prepare-task-worktree` with exact task, actor, permitted claim,
   copy/environment actions and checked primary root with selection evidence. Check its verified claim,
   blockers, copy association, preservation of foreign staged/unstaged/untracked
   changes and separate copy/environment readiness. Use its actual handoff, not
   a guessed branch/path. Refresh context after a copy change. Retain the
   addressable copy witness and primary association evidence; neither replaces
   fresh permission/ownership/blocker/protection gates at the receiving stage.
2. Determine whether a **saved plan** is required by project rules or needed for
   sufficient implementation/handoff. If so, delegate `ris-proj-op-plan-task` in
   the supplied copy with accepted versions/contracts (bug snapshot when applicable)
   and authorized plan address; read the saved plan and coverage. Otherwise record
   the justified omission, applicable rules, sufficient technical inputs and their
   accessible locator/version in execution evidence and every dependent handoff.
   Missing file alone does not require a formal plan when this decision remains
   applicable. In RIS the mandatory persisted local plan remains. Direct plan-task
   always retains its own save contract. Changed scope or missing decisions return
   to this dialogue, not silent redesign.
   When feasibility depends on an uncertain platform behavior or external boundary,
   place the smallest permitted decisive probe before dependent implementation or
   costly evaluation. Use existing applicable evidence first; do not invent a
   preflight experiment for an ordinary local edit or exceed probe permissions.
3. Recheck actor ownership and blockers before each new change batch. Delegate
   code behavior (including mixed code/text) to `ris-proj-op-implement-task-tdd`; require
   observed expected RED before behavior changes, GREEN afterwards, affected
   checks and the exact code/tests/authorized-docs snapshot. Environment errors
   are not RED. For text-only work read `references/text-work.md` and delegate
   its bounded content owner without artificial RED. Check actual artifacts and
   criterion coverage; author evidence is not independent approval.
4. Launch a fresh `task-review` subagent applying `ris-proj-op-review-task` to the exact full
   candidate snapshot, requirements/design or sufficient bug report/snapshot and
   separately accepted decisions, project rules and check evidence.
   Require saved findings, stable finding IDs, one high/medium/low level per
   finding, verdict, version and independence provenance.
5. High/medium findings go back to the implementation owner for fixes, affected
   checks and a new independent review. Record low dispositions collectively or
   individually; low alone does not trigger repair, a new task or a new round.
   Changed snapshots need applicable review. Compare rounds by resolved causes,
   new verified facts and remaining mandatory findings. Repetition without a
   justified new approach needs cause diagnosis; if no viable progress, preserve
   actual effects, stopping cause and exact remainder with the cause's
   `blocked|conflict|error`, or ask the necessary question. There is no fixed round cap.
6. Delegate `ris-proj-op-publish-task` with exact approved full snapshot, independence
   evidence and authorized primary branch/remote. Never stage foreign paths,
   reset/stash their work, bypass hooks or force push. If integration/hook changes
   the snapshot, obtain affected checks and fresh independent reassessment through
   `task-review` **before push**; the publication owner must return the candidate
   for this reassessment, not silently approve itself. Reconcile ambiguous pushes
   by remote reads. Direct-push prohibition blocks this route without PR fallback.
   Record actual integrated commit/ref and independent remote visibility evidence.
7. Only after confirmed Git publication, verify criteria and mandatory scope on
   the published version. For a leaf task, delegate selected-adapter bounded
   result persistence and separate native exact-ID completion (advertised tool-specific
   ordinary operations for standalone tasks or native bug fix-completion, not
   investigation disposition or feature-record/1) with criterion/check/review
   evidence and published commit. Require fresh status, complete child/blocker
   reads, fresh applicable external evidence/mandatory composition and honest
   predicate-specific native limits, without freezing graph/evidence. No future
   `ris-complete-task` dependency is required. For a selected one-task feature,
   delegate `ris-proj-op-complete-container` with explicit **verify-and-close**
   intent for **all** feature AC, integrated revision,
   verification persistence/read-back and separate closure. Diff review or closed
   children cannot substitute for feature acceptance. Never close parents.
8. Delegate **separate** selected-adapter tracker publication. For prior/ambiguous
   publication pass exact requested/recovered snapshot S, inspectable receipt/ref
   and expected records/typed links. Have the adapter confirm S independently
   AS OF S before incoming-only/divergence and new-write gates; a newer remote
   does not block confirmation-only recovery or require a repeated push, closure,
   merge, working-branch update or write window. Unknown S/read failure remains
   unverified. A proven unsent snapshot still needs authorization for the entire
   outgoing history, final inspected immutable snapshot ref and independent selected-remote
   read-back under the adapter's method. Git push and local closure do not prove
   tracker publication. Keep all three channel facts separate.

Stop dependent effects on an ambiguous or failed operation, including timeout or
lost executor response. Apply the recovery resource with the corresponding owner
to inspect actual state and live execution before retry. Save partial effects and
the exact remainder; continue only when reconciliation and the remaining gates
permit it. Do not replay an effect to manufacture success.

For a confirmed contract conflict or materially growing verification effort,
surface the concrete decision in this dialogue before commissioning more dependent
experiments. Do not commission agent tests prohibited by the target project or
make live evaluation an implicit stage of ordinary instruction repair. Reuse
applicable observations within their original limits, checks for unchanged
mechanisms, and rerun affected static/program checks. A mandatory
check cannot be silently dropped: obtain acceptance of any scope/verification
revision and record unrun checks and remaining limits, never a fabricated pass.

## Assess and report

Delegate fresh read-only queue/readiness assessment for the next recommendation,
using the same ordering and readiness rules. Recommend one ready task with its
basis or a concrete preparation step. Do not claim or start it and do not switch
to it when the current target is blocked.

Return `ok|blocked|conflict|error`, ID/title, what was done and the user-visible
change (or explicitly internal-only), checks/review and their applicability,
project/config/actor/copy, component/evidence addresses, published Git commit/ref,
separate closure and tracker snapshot/read-back facts, limitations and next
recommendation. On a stop include the cause, preserved actual effects, first
remaining operation and required recovery/decision. `ok` requires all promised
effects verified for the selected task; never infer it from one channel or an
executor's assertion. Distinguish reused results, reconstructed observations,
new operations and invalidated/unverified evidence in a resumed report.
