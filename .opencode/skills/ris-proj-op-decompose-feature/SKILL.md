# Decompose an accepted feature into verified project tasks

For a confirmed feature read/apply installed specify-feature's owned
`references/stage-prerequisites.md` before dependent decomposition/writes. Check
readable requirements prerequisite contracts separately from native blocks and
preserve the same preliminary ID. Accepted future contracts can support blocked
tasks before implementation; unknown needed contracts stop only dependent parts.
Do not duplicate parent-feature native edges onto children merely for membership.

Own the **combined project result**: confirmed accepted inputs and matching
feature or explicit ordinary standalone task/container, a sufficient single-task
outcome or verified children/blockers, traceable coverage and required tracker
publication. Apply installed
`ris-port-op-decompose-feature-spec` for the substantive work proposal and its coverage
check; use the selected installed `tasks` adapter for bounded tracker reads and
writes. Neither a base proposal nor an adapter success message proves this
combined result. This wrapper owns project input selection, permissions,
reconciliation, verification and handoff, not requirement acceptance or the
base's decomposition method. The semantic execution role is
`task-decomposition` for a caller assigning a subagent; **direct invocation**
runs in the current agent without requiring an `execution` role or claiming
isolation. Do not initiate another lifecycle stage.

## Confirm inputs and scope

Full finished invocation is default and includes required tracker publication.
An explicitly limited contribution instead returns a proposal/read-only
verification or checked authorized local writes; name exact boundary and remaining
effects. Nesting/Gas City is not a mode selector. No Git commit is needed merely
for tracker decomposition. Publication never authorizes implementation.

Before remote-gated mutations preflight the selected adapter's separate
publication operation for actual remote, full outgoing authority and guarantees.
Failure blocks dependent writes, not the read-only coverage proposal.

Identify the selected RIS project and current copy, confirmed `task`
ID and explicit kind (feature, standalone task or task-container), applicable published requirements/design references and their separate
acceptance decisions, relevant technical/project constraints, prior task IDs
and permitted read/write scope. Start from the ID through the selected adapter:
retrieve linked published documents and decisions rather than requiring their
addresses from the previous caller. No prior chat, local plan or ignored working
note is a required input. Resolve ambiguous feature,
project, primary-copy root or acceptance source before dependent action. A
request to decompose does not accept an unapproved specification; a file,
format check, cached summary or a task description alone does not prove
acceptance. Establish the current project Git revision and intended integration
target; assess actual content applicability there rather than requiring every
accepted reference to point to the latest commit. Material changes or uncertain
applicability need reconciliation, not a silent task rewrite.

Apply installed `ris-proj-lib-common` and its conditional resources before dialogue,
artifact work and completion checks. Use installed `ris-proj-op-resolve-context` with its
configuration resource to prepare `sources.rules`, relevant `sources.product`
and `sources.specs`, `adapters.tasks.skill` and, if needed, shared workspace
paths in this project. Inspect status, config provenance, diagnostics and
permission scope; select relevant documents by actual links and content, not
assumed filenames. In a worktree, source paths use its current project root;
shared paths need context's checked Git-derived source-folder association. An invalid explicit
config is an error, not a reason to fall back to defaults. The project decides
its specification format and mechanism of acceptance; verify accessible
evidence addresses and their match to the saved version, not merely a flag.

Ensure the selected adapter is installed and actually available in the chosen
project. For a feature read-only result require compatible `tasks` v1
`tasks.items.read`, `tasks.children.list` and `tasks.dependencies.list` with
exact-ID and complete all-status child selection and full typed directed
blocker reads (including for the feature task itself). Before a needed child
write additionally require `tasks.items.list` and `tasks.items.create`; before
a needed edge write require `tasks.dependencies.add`, with the applicable full
all-status identity search, stable scoped keys, confirmed parent/content
read-back, directed typed blockers and cycle checking. Determine missing work
from reads first, then check each operation and guarantee **before** its
dependent write, including the required concurrency level. A configured
adapter or a similarly named CLI command is not evidence of support; never
bypass the adapter by calling `bd` or editing tracker storage. Read the selected
task; for a feature confirm its `task` type, open status, optional epic parent, scoped identity, exact
spec link and acceptance-evidence address **in either its readable content or the
linked specification**, and reread the saved specification and decision.
Cross-check their identity and status; a closed feature or mismatched link
blocks child creation. Read all existing direct children and relevant blockers,
including closed tasks, before deciding whether new work is needed.

## Check decomposition sufficiency separately from execution readiness

For explicitly identified **ordinary standalone** work, obtain kind/key, own
outcome/scope/criteria, accepted sources/decisions, sufficient constraints and
contracts from exact record reads and its links. No epic/slug/feature JSON is
required. Structural parent is context, not copied global AC or permission to
close it. Check adapter-advertised tool-specific ordinary create/reconcile,
child/link capabilities and guarantees before dependent writes. Apply its owned
standalone resource, not common feature-only create/add semantics. Legacy
payloads stay unchanged; absent or malformed JSON does not prove standalone kind
or block the document route. Independently accepted substantial
design is required where material, especially for multi-task contracts/seams;
a simple task can use sufficient accepted constraints without a design file.
Read each exact accepted source/decision version, verify publication and compare
current applicability as below. Name missing inputs instead of inventing them.

The following document/optional-parent/acceptance gates apply to the **feature branch**;
the shared applicability, readiness, reconciliation and coverage checks apply
to both branches using their actual accepted inputs.

Use native exact task/optional epic/children/blocker reads and supported child/edge
operations without feature JSON capabilities. Apply common's published-inputs
feature convention and bounded legacy discovery. New documents use
`sources.specs/<full feature ID>/spec.md` with sufficient inline or adjacent design;
no slug pin or accepted-ref registry. Read both actual accepted content scopes and
their separate attributable decisions at exact published versions. Match path,
section, revision and acceptor; resolve `containing-commit` at its original decision,
not a later copy. Confirm content and decisions are published in the selected remote.
One decision may explicitly accept both independently selectable complete scopes;
a file/commit alone cannot. Missing actual requirements or sufficient independently
accepted design blocks dependent decomposition. Missing/old/malformed JSON alone
never does. Preserve legacy data/links; no schema gate, replacement block, migration
or invented epic. Identity conflicts trigger bounded wider discovery, not global
registry scans on every invocation.

Apply common's conditional published-input reading method: an absent local
`sources.specs`/file in an older checkout is a copy diagnostic, not missing accepted
requirements/design. Retrieve pinned content and decisions without synchronizing
that checkout. Establish the intended integration target separately; if unknown,
report the applicability gap rather than treating old HEAD as the only target.
Compare each accepted result's actual content with its semantic section at
that target revision (diff plus content review), recording the current checkout
revision separately. Inspect relevant code,
contracts and linked source changes for applicability of the accepted design
and requirements to this decomposition. Changes elsewhere in a shared document
do not invalidate unchanged requirements; matching paths/section labels or
unchanged reference objects alone do not prove applicability. Record the checked
revisions and comparison evidence. Material requirements changes return to the
requirements owner; design gaps return to the design owner. Preserve unchanged
accepted references and decisions, never repin them just to the latest commit.

Compute action-specific sufficiency anew on every invocation; do not write a
`ready` status.
Check sufficient design/test seams, accessible applicable architectural
contracts and versions, related product source currency, and resolved product/
architecture conflicts. Missing source baselines leave currency unconfirmed;
material unconfirmed applicability blocks dependent writes. Read feature and
relevant task blockers and their actual scope/content. A known, sufficiently
defined accepted prerequisite that is not yet implemented does not itself block
describing or creating dependent tasks. Retain necessary directed `blocks`
(blocked unit → prerequisite), with confirmed endpoints and read-back; never
silently mark the prerequisite complete. With active feature blockers, permit
child/edge writes only when every blocker's freshly checked scope/content proves
it execution-only for that exact decomposition action. Unknown applicability or
a real decomposition blocker stops the dependent writes; native refusal and ownership/permission guards are
never bypassed. Unknown or disputed contracts block only dependent units and
coverage claims: preserve independently sufficient analysis and authorized
task/edge results, without claiming complete decomposition or inventing decisions.
Do not confuse parent membership with blockers. Execution readiness is a separate
per-unit check of sufficient accepted inputs, needed integrated prerequisites,
current blockers and execution authority; neither task existence nor successful
decomposition supplies it. With a failed gate return the supported result and
exact affected remainder; do not use an inapplicable design or fabricate
acceptance. Do not repeat the preparation interview without a discovered gap;
ask only for the bounded missing decision and name its owner.

On design revision, compare requirements and design content separately, inspect
impact on existing tasks, AC, seams and blockers, and preserve unchanged
requirements acceptance. Changed task content cannot be silently updated by
v1 create operations: return `conflict` and the specific reconciliation needed.
This wrapper neither accepts/revises design nor starts another skill.

## Apply the method and reconcile actual work

For an ordinary simple task supply its accepted contract-preserving technical
constraints as the base's sufficient short design input, with their actual
acceptance scope/provenance; no separate file is required. If they do not settle
material ownership/contracts/test seams, return that design gap rather than
waiving the base's sufficiency or independent design-acceptance requirements.

Ensure installed `ris-port-op-decompose-feature-spec` is available and **apply** its
method to checked accepted inputs, own criteria (full feature ID/AC for new features), design/contracts/
test seams, feature scope, relevant rules and
technical inputs, and verified existing work. Obtain its bounded work units,
observable checks, requirements mapping, justified directed prerequisites
and explicit gaps. Do not duplicate its partitioning algorithm here. If a
missing criterion or conflicting accepted decision blocks coverage, report
the supported partial proposal without creating tasks for disputed scope.
Compare the proposal with existing children, including their content, state
and source coverage; existing tasks are not automatically completed work.
Unrelated or conflicting children, unknown coverage, duplicate identity or
an unexpected blocker prevent a claim of full readiness; do not silently
delete, update, reparent or replace them. Resolve material changes to the
accepted spec with its owner before writing.

If the bounded feature can be done as **one task**, check that the existing
feature task itself expresses its outcome and completion criteria and covers
the accepted requirements. Inspect its full typed blockers as well as a
complete empty direct-child set (or reconcile any actual children); do not
create a copy of the feature as its own child. An existing feature task that
lacks required content cannot be silently updated under `tasks` v1: return
`blocked`/`conflict` with the gap, even if the base proposal is good. For
multiple units, require exact authorized scope only
for missing child or `blocks` writes; a fully persisted set can be verified
read-only. Agree approved task content and stable retry keys scoped to the
confirmed feature; preserve spec reference, requirement coverage, observable
criteria (`<ID>#AC-nnn` for new features; retain legacy qualifiers), own outcome/scope and exact applicable accepted content selectors and separate
acceptance addresses, technical
contracts/versions, test seams, exclusions and justified edge direction
(blocked → blocker). Do not
invent tracker IDs from titles, equate parent membership with a blocker, or
turn a preferred order into a dependency.

Before each mutation, compare current all-status children, candidate identities
and blockers with expected state. Recheck current accepted references, published
decisions, content applicability and contracts when their inputs have changed;
changes invalidate dependent readiness evidence. Membership/blocker writes use
the adapter's bounded native operations with fresh expected structure and exact
read-back, without a manual window or graph/evidence transaction. A claim,
permission, sandbox or read-back is not a general lock; report actual native limits.
Through the adapter, create only missing
children with `tasks.items.create` under the confirmed open feature task, or
the adapter's explicitly supported ordinary child creation under the standalone
container;
reuse only exact matches on key, type, parent, content and relevant links.
Different content, closed/moved parent, multiple matches or unmatched existing
children are `conflict`, not permission for an implicit update. Default create
is best-effort with full search/read-back; if strict no-duplicates is required,
require proven native support or return that exact unsupported guarantee before
creating, without asking to pause writers. Re-read each ID, parent-child membership and content; only then resolve
the proposal's local labels to real IDs. Add necessary `tasks.dependencies.add`
edges (ordinary tool-specific link operations for standalone) only with confirmed task endpoints in this accepted scope after reading
their existing typed `blocks` edges; verify no cycles and exact direction on
fresh reads. Preserve an already matching edge without a fake change.

On a failed, ambiguous or partial adapter response, **stop further writes**.
Reread all affected IDs, full direct-child set and relevant edges before any
retry, report verified existing children, keys, links, actual added edges and
unwritten work. A subsequent invocation reconciles these facts and the current
accepted specification before attempting only genuinely missing operations;
do not blindly recreate children or overwrite a changed requirement. For a
stronger uniqueness or content-update guarantee than the selected adapter
provides, stop instead of substituting a direct tracker operation.

## Verify and return

For both kinds every child must independently express its result, bounded scope,
observable criteria, exact applicable accepted source selectors/versions and
separate decisions, contracts/test seams, exclusions, stable retry identity and
necessary blockers. A parent reference supplies context, not the child's missing
contract. Do not copy every global AC into every child. For a one-task outcome
verify the existing task's sufficient contract and reconcile the complete child
set; create no artificial child. Preserve the feature branch's stricter refs.

After combined semantic/read-back checks below, full mode invokes the selected
adapter's separate publication operation with exact expected IDs/content/links,
destination evidence and authority for the entire outgoing scope. Inspect the
required revision/remote reachability receipt alongside the locally verified
composition and refs; remote assurance does not independently compare all fields.
No-change checks required existing publication and established debt;
no empty push. Missing authority or failed/ambiguous publication blocks full
success, preserving known children/edges for only missing operations. Limited
mode returns its actual boundary and exact publication remainder.

Fresh-read the selected task/container and full child set, each task's actual content, status,
parent and applicable links, and all required directed blockers. Recheck the
applicable accepted requirements/design or sufficient constraints and their separate decisions for
the same references and content applicability, and applicable contract currency; map
every accepted criterion to the verified feature or child tasks, and name where
combined behavior will be checked. Confirm no contradictory extras or cyclic
dependencies. An unknown/disputed required contract or a missing
criterion prevents full decomposition `ok`; a defined accepted future prerequisite
with verified necessary edges does not, although dependent execution remains
blocked until its requirements are met. Mere presence of children or an adapter
`ok` does not prove coverage. Report `ok|blocked|conflict|error` for **this combined
result**, the project/config source, subject kind and exact task/parent IDs, source address and
version, checked current Git revision, full feature ID where applicable, applicable accepted content
objects/acceptance addresses, publication and applicability evidence, contract
versions/test seams and decomposition sufficiency separately from per-unit
execution gaps/integration prerequisites, actual child IDs/keys and statuses,
directed dependencies, requirement coverage, `changes` (including `[]`),
read-back evidence, limitations and exact next needed substantive result.
For partial outcomes use the reason's non-`ok` status and distinguish confirmed
changes from unmade ones; include sufficient published references, bounded scope,
permissions and open questions for continuation without this chat. Do not
plan technical steps, claim or close tasks, approve the specification, or
launch implementation.
